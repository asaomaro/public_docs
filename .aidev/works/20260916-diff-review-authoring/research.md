# 調査: 指摘を「書く」側の script

> 実測は headless Chromium（`file://`）＋ Python3。入力は `tests/fixture_repo.py` が作る
> **固定のリポジトリ**（新規 / 削除 / 置き換え / 先頭行から始まるハンク / rich の対象を含む）。
> 作業ツリーを入力にすると検査がリポジトリの状態で揺れるので、この work では最初から固定入力を使う。

## 調査課題（requirements の「未確定事項」より）

1. いまの CLI に「書く」経路はあるか（F1）。
2. `check` はアンカーの実在を見ているか（F2）。
3. **どの位置に指摘できるのか**——画面と一致する規則を出せるか（F3）。
4. `side` は省略できるか（F4）。
5. 文脈行に指摘してよいか（F5）。
6. バンドルだけで（git 無しで）検証できるか（F6）。

## F1: 書く経路は**無い**（確認）

`diff_review.py --help` のサブコマンドは `html` / `bundle` / `view` / `template` / `check` / `list`。
**記録に何かを足すコマンドは 1 つも無い。** `template` は空の器を出すだけで、
`threads` を埋めるのは呼ぶ側（AI）が手で行っている。

## F2: `check` はアンカーの実在を見ていない（確認）

`validate()` が見るのは構造・値域・参照（`review_id` / `in_reply_to`）まで。
`identity_mismatch()` は `diff_digest` と `base_commit` を比べるだけ。
**`line: 9999` と書いても検証を通る。** 画面では `slotFor()` がファイル単位の置き場へ落とし、
最終的に「位置不明」欄に出る——つまり**書いた側は気づけない**。

## F3: 指摘できる位置の規則（**画面と 307/307 で一致**）

画面の `anchorOf`（前 work で 1 本にまとめた）と同じ規則を Python で書き、
**画面が実際に提供する位置**と突き合わせた。

規則:

```
1 行がどの位置を持つか:
    削除行             → LEFT + 旧側の行番号
    追加行・文脈行     → RIGHT + 新側の行番号
    旧側しか番号が無い文脈行（削除されたファイル） → LEFT + 旧側の行番号

ファイル全体で指摘できる位置:
    ハンクに出ている全行の位置
  ＋ 展開して出せる行（展開データがあるとき。文脈行なので展開データと同じ側に乗る）
```

照合の仕方: 固定入力の HTML を開き、**rich 表示のファイルを source に切り替え**、
**すべてのファイルを「すべて展開」**してから、`data-key` と `data-threads` を全部集めた。
unified と split の両方で集めて和を取った。

| | 件数 |
|---|---|
| Python の規則が出した位置 | **307** |
| 画面が実際に提供した位置 | **307** |
| 差 | **0**（どちらにしか無い位置は 1 つも無い） |

> 最初の照合では Python が 23 件多かった。原因は**照合側の手落ち**で、
> rich 表示のファイル（`.md` / `.csv`）を source に切り替えていなかったため行が出ていなかった。
> **rich の既定表示は「指摘できる位置」を狭めない**——切り替えれば同じ位置が出る（F5 と対）。

## F4: `side` は**省略できるが、常には推論できない**（実測）

同じ行番号が LEFT にも RIGHT にも存在する場合がある——**その行が置き換えられたとき**
（旧側の N 行目が消え、新側の N 行目が増える）。

| | 件数 |
|---|---|
| RIGHT だけ有効 | 262 |
| LEFT だけ有効 | 25 |
| **両側とも有効** | **10** |

例: `src/api/handler.py:40`（1 行を書き換えた箇所）、`src/core/engine.py:1`（先頭行を書き換えた箇所）。

→ **片側しか無ければそれに決まる。両側あるときは決められない。**
ここで落とすと、**いちばん指摘したい「書き換えた行」で必ず落ちる**ので実用にならない。
GitHub の REST も `side` の既定は `RIGHT`。**既定を RIGHT と決めて文書に書く**のが妥当
（推測ではなく規約になる）。→ decisions で確定する。

## F5: 文脈行には指摘してよい（規則から従う）

F3 の規則どおり、文脈行は RIGHT の位置を持つ。画面でも `+` ボタンが出る。
GitHub も文脈行にコメントできる。**制限を足す理由が無い。**

なお **rich 表示のファイル**（`.md` / `.csv` / `.html` / `.pdf`）も、
source に切り替えれば同じ位置が出る（F3 の注記）。書く側から見れば **rich かどうかは関係ない**。

## F6: バンドルだけで検証できる（実測）

バンドル（`.dreview`）は差分の本体（`files`）をそのまま持っている。
そこから F3 の規則で位置を出した結果を、git から取り直した結果と突き合わせた。

| | 件数 |
|---|---|
| バンドルの中身だけから | **307** |
| git から取り直して | **307** |
| 一致 | **true** |

→ **`.dreview` を渡されたエージェントは、リポジトリが手元に無くてもアンカーを検証できる。**
これは「AI が JSON を受け取って直す」経路にそのまま効く。

## 調査中に見つけた既存の不具合（**この work の前に直した**）

アンカーの規則を画面と突き合わせる過程で、画面側が壊れていることが分かった。
**規則の突き合わせ相手が壊れていては研究にならない**ので、先に直した（コミット `74e47f7`）。

1. **「すべて展開」が効かないファイルがあった**。`gapsOf` が「隙間なし」に返す `null` を
   `expandAll` が飛ばさず TypeError で抜け、ファイルの再描画ごと巻き込んでいた
   （実測: 13 行 → 13 行。本来 60 行）。先頭行から始まるハンクを持つファイルで起きる。
2. **削除ファイルで行が重複していた**。`hunkRange` が新側の行番号で固定されており、
   新側の番号を持たない削除ファイルで範囲が空になって「まだ出ていない」と誤判定していた
   （15 行 → 30 行）。
3. **削除ファイルの展開行が新側に番号を持っていた**。旧側の番号を新側に書いた行ができていた。

あわせて、位置づけの規則を `anchorOf` 1 本に寄せた。**F3 の一致は、この修正の上で取った結果。**

## リスク

- **R1**: 書く側と検証側で規則が二重になると、片方だけ直して食い違う。
  → **既存の `validate()` を必ず通す**設計にする（書く側は独自の検証を持たない）。
  アンカーの規則も **1 か所**に置く。
- **R2**: 記録を上書きするので、**途中で落ちると壊れた記録が残る**恐れがある。
  → 全部検証してから書く。書き込みは 1 回。
- **R3（F4）**: `side` の既定を決めると、**黙って反対側に付く**場合がありうる。
  → 既定を文書に明記し、`list` と `check` で位置が見えるようにする。
- **R4**: アンカー検証には差分が要る。記録 JSON だけを渡されたときは `--repo` が要る。
  → **バンドルを渡せば要らない**（F6）ことを文書で推す。
- **R5**: まとめて足すとき、**途中の 1 件が駄目なら全部やめる**必要がある（R2 と同じ理由）。
- **R6**: 行番号は差分が変われば意味を失う。`diff_digest` が合わない記録に足すのは危うい。
  → 既存の `identity_mismatch()` で警告する（拒否はしない。往復が止まるため）。

## 結論（design への申し送り）

1. アンカーの規則は F3 のとおり。**画面 `anchorOf` と 307/307 で一致**することを確認済み。
   実装は生成側に 1 か所だけ置き、`check` からも `comment` からも呼ぶ。
2. `side` の既定は **RIGHT が有効ならそれ、無ければ LEFT**。両側あるときも RIGHT（規約として明記）。
3. アンカー検証の入力は、**バンドルならその中身**、記録 JSON なら `--repo`。
4. 書いたあとは**必ず既存 `validate()` を通す**。書く側に独自の検証規則を持たせない。
5. 書き込みは**全部検証してから 1 回**。落ちたら入力を変えない。
6. 実在しない位置のときは、**そのファイルで指摘できる位置**を手がかりとして出す（要件 F6）。
