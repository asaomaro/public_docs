# タスク: 指摘を「書く」側の script

## 実装方針

**規則 → 検証 → 組み立て → 書き出し → コマンド**の順に積む。
コマンドから書き始めると、3 つのコマンドが少しずつ違う検証を持つことになる。

1. アンカーの規則（T1）——`check` も `comment` もここを呼ぶ。**1 か所しか無いこと**が要。
2. 失敗の出し方（T2）——手がかりが無い「駄目」は直しようがない。規則と対で作る。
3. 記録を触る土台（T3 id の採番 / T4 入出力の種類）。
4. コマンド（T5 `comment` / T6 `resolve` / T7 `submit` / T8 `--batch`）。
5. `check --anchors`（T9）——既定を変えない。
6. 文書（T10）とテスト（T11・T12）、規則の一致と回帰は test 工程で（T13）。

**各タスクの終わりに既存の性質を確認する**（決定論・正規形・既存 91 件が通ること）。

## 作業順序と依存関係

下の `依存:` に従う。それでは表せない順序の理由だけをここに書く。

- **T1（規則）を何より先に**。書く側が独自の判定を持ってしまうと、あとから 1 本にまとめるのは
  「2 つの正しさ」を 1 つに潰す作業になり、どちらが正かを決める根拠が無くなる。
- **T2（失敗の出し方）を T5 より前に**。あとから足すと、コマンドごとに文言が割れる。
- **T4（入出力の種類）を T5 より前に**。「入力と同じ種類で返す」を後付けすると、
  コマンドごとに分岐が散る。
- **T8（まとめて足す）は T5 の後**。1 件の経路が固まる前に複数件を作ると、
  「全部検証してから 1 回書く」の境目が引けない。
- **T13（規則の一致）は test 工程**。画面と突き合わせるのでブラウザが要る。
- **T11 と T12 を分けているのは依存先が違うから**。T11 は 1 件ずつの経路（T5〜T7・T9）に、
  T12 はまとめて足す経路（T8）に依存する。1 本にすると、前半が書けているのに
  後半の依存待ちで着手できない、という止まり方をする。

## リスク / 留意点

- **R1（research R1）**: 書く側と検証側で規則が二重になると、片方だけ直して食い違う。
  → `validate()` は**触らない**。アンカーの規則も 1 か所（T1）。T13 で画面との一致を固定する。
- **R2（research R2 / R5）**: 途中で落ちると壊れた記録が残る。
  → **全部検証してから 1 回だけ書く**。落ちた経路が書き込みに到達しないことを T11 で検査する。
- **R3（research F4）**: `side` を省いたとき、置き換えた行では両側が有効になる（実測 10/297）。
  → 既定 RIGHT を**規約として**文書に書く（T10）。黙って選ばない。
- **R4**: 記録 JSON だけでは差分が無くアンカー検証ができない。
  → `--repo` を要る形にし、**バンドルなら要らない**ことを文書で推す（T10）。
- **R5**: `--batch` の失敗報告が 1 件目で止まると、AI が何往復もすることになる。
  → **全件ぶんまとめて**出す（T8）。
- **R6**: 本文に改行・引用符・`</script>` が入る。引数・ファイル・標準入力のどれでも同じ結果になること。
- **R7**: この work は画面を触らないが、**触っていないことを実測で示す**必要がある（T13）。

## テスト方針

- **生成側（T11・T12・stdlib `unittest`）**: `comment` の 3 形態・id の採番・排他な引数の拒否・
  アンカーの成功と失敗・**失敗時に入力が 1 バイトも変わらないこと**・`--batch` の全件成功と
  1 件失敗・`resolve` / `submit` の紐づけ・記録とバンドルの往復・`--body-file` と標準入力・
  決定論（2 回実行でバイト一致）・**書いたあと `check` が通ること**。
  入力は `tests/fixture_repo.py`（固定）。
- **規則の一致（T13・test 工程）**: 生成側 `valid_anchors()` の出す位置と、
  **画面が実際に提供する位置**が一致すること（research F3 の 307/307 を回帰として固定）。
- **回帰（T13）**: 既存の生成側 91 件・画面 80＋34 件を再実行する。
