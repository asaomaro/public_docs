# 要件: 指摘を「書く」側の script を用意する

## 背景 / 課題

この skill は「AI がレビューして JSON を出す → 人が画面で確認する」「人が画面で書く →
AI が JSON を読んで直す」の往復を掲げている。読む側（`list` / `check`）と器（`template`）はあるが、
**書く側だけが素手**——AI は `threads` の JSON を手で組み立てている。

そこで踏む落とし穴が具体的にある。

- **`id` の一意性**をAI が自分で管理している（スレッド間・スレッド内コメント間）。
- **`in_reply_to` は同じスレッド内**の `id` でなければならない。別スレッドの id を書いても
  `check` が弾くまで気づけない。
- **`kind: "note"` の制約**（`review_id` も `severity` も `null`）を毎回思い出す必要がある。
- **提出の紐づけ**（`reviews` を足して各コメントの `review_id` を合わせる）が手作業。
- **いちばん痛い穴**: `check` は「その行が差分に実在するか」を見ていない。
  `line: 9999` と書いても検証を通り、画面では黙って「位置不明」欄に落ちる。
  **AI が行番号を数え間違えたときに、気づける場所がどこにもない。**

書く手順が素手であるかぎり、「AI がレビューする」経路は**当たり外れのある工程**のままになる。

## 目的 / ゴール

- **指摘・説明・返信を 1 コマンドで足せる**状態。id も形も script が面倒を見る。
- **存在しない行に指摘を付けたら、その場で落ちる**状態。画面で「位置不明」を見て初めて
  気づくのではなく、**書いた瞬間に分かる**。
- **解決と提出もコマンドで行える**状態（画面を開かずに往復が閉じる）。
- **まとめて足せる**状態（20 件の指摘に 20 回プロセスを起こさない）。
- 上記を足しても、**記録の形（`diff-review/2`）・決定論・既存コマンド**が壊れていない状態。

## ユーザーストーリー

- US1: レビューする AI として、指摘を 1 コマンドで足したい。
  なぜなら、JSON を手で組み立てると `id` と参照の管理が毎回の負担になり、間違えるから。
  （受け入れ: AC1, AC4, AC5）
- US2: レビューする AI として、**存在しない行に指摘を付けたら止めてほしい**。
  なぜなら、行番号の数え間違いは起きるもので、画面で「位置不明」を見るまで分からないのは遅すぎるから。
  （受け入れ: AC6, AC7）
- US3: 差分を書いた AI として、レビュアーへの説明コメントを残したい。
  なぜなら、意図を書いておけば人間のレビューが速くなるから。（受け入れ: AC2）
- US4: 修正する AI として、人間の指摘に返信したい。
  なぜなら、「直した」「ここはこういう理由で直さない」を同じスレッドに残したいから。（受け入れ: AC3）
- US5: レビューする AI として、判定（Approve / Request changes / Comment）を添えて提出したい。
  なぜなら、未提出のまま渡すと、人間の画面で「未提出」と表示されてしまうから。（受け入れ: AC8）
- US6: 修正した人として、解決済みにしたい。
  なぜなら、往復のたびに残りの指摘だけを見たいから。（受け入れ: AC9）
- US7: レビューする AI として、**まとめて足したい**。
  なぜなら、20 件の指摘に 20 回プロセスを起こすのは遅く、途中で失敗すると中途半端に残るから。
  （受け入れ: AC10）
- US8: レビューする AI として、**長い本文をそのまま渡したい**。
  なぜなら、指摘は数行になることがあり、引数に押し込むとシェルの引用で壊れるから。（受け入れ: AC14）
- US9: 往復を自動で回す人として、**同じ入力から同じ結果**になってほしい。
  なぜなら、結果が揺れると「直したから変わったのか、script が揺れたのか」が切り分けられないから。
  （受け入れ: AC13）
- US10: 記録を預けている人として、**失敗したときに記録が壊れていない**ことを保証してほしい。
  なぜなら、途中まで書かれた記録は、直すより作り直すほうが早くなってしまうから。
  （受け入れ: AC15）
- US11: いまの使い方をしている人として、**何も変えずに済ませたい**。
  なぜなら、skill から呼ばれる既存の経路が動かなくなると、いまのフローが止まるから。
  （受け入れ: AC12）
- US12: 拡張やスクリプトから呼ぶ人として、**入力に渡した種類のまま**返ってきてほしい。
  なぜなら、バンドルを渡したのに記録 JSON が返ると、後続の処理が繋がらないから。
  （受け入れ: AC11, AC16）

## スコープ

### 対象

- **コメントを足すコマンド**（指摘 / 説明 / 返信）。
- **アンカーの検証**（`path` と `line` と `side` が、その差分に実在するか）。
- **解決の切り替え**と**提出**のコマンド。
- **まとめて足す**入力（複数件を 1 回で）。
- 記録 JSON とバンドル（`.dreview`）の**両方**を入力にできること。
- 既存の `html` / `bundle` / `view` / `template` / `check` / `list` の互換維持。

### 対象外

- **画面（HTML）の変更**。今回は script 側だけ。
- 指摘の**編集・削除**（足すことと、解決を切り替えることまで）。
- GitHub への書き戻し。
- AI に「何を指摘すべきか」を教えること。**器を用意するだけ**で、中身は呼ぶ側が決める。

## 機能要件

- **F1 指摘を足す**: 位置（ファイル / 行 / 全体）・本文・重大度を指定して、スレッドを 1 本足す。
- **F2 説明を足す**: `kind: "note"` として足す。`review_id` と `severity` は自動で `null`。
- **F3 返信を足す**: 既存のスレッドの、既存のコメントに返信する（返信への返信も同じ形）。
- **F4 id の自動採番**: 記録の中で一意な `id` を script が付ける。呼ぶ側は考えなくてよい。
- **F5 アンカーの検証**: 指定した位置が差分に実在しなければ**足さずに落ちる**。
  バンドルが入力なら**バンドルの中の差分**で照合する（git が要らない）。
  記録 JSON が入力なら `--repo` から差分を取って照合する。
- **F6 近い候補を出す**: 実在しない行のとき、**そのファイルで指摘できる行**を手がかりとして出す。
  「駄目」だけでは直しようがない。
- **F7 解決の切り替え**: スレッドを解決 / 未解決にする。
- **F8 提出**: 判定とサマリを足し、**未提出のコメントをその提出に紐づける**。
- **F9 まとめて足す**: 複数件を 1 回で。**1 件でも駄目なら 1 件も書き込まない**。
- **F10 出力先**: 既定は入力を上書き。別ファイルにも標準出力にも出せる。

## 非機能要件 / 制約

- **Python3 標準ライブラリのみ**・外部依存なし（既存の性質を維持）。
- **決定論**: 同じ入力と同じ引数からは同じバイト列。正規形（キー昇順・UTF-8・LF・末尾改行）。
- **書き込みは全部通ってから**: 検証に落ちたら**入力を 1 バイトも変えない**。
- **既存の検証を使い回す**: 書いたあとの形は既存 `validate()` が通ること。
  **書く側と検証側で規則が二重にならない**こと。
- **本文は長い**（AI が書く）。引数だけでなく**ファイルや標準入力からも**受け取れること。
- 終了コードは既存の規約に合わせる（1=使い方 / 2=git / 3=記録が不正）。

## 完了条件 (受け入れ基準)

- [ ] AC1: 行・ファイル・全体に、重大度つきの指摘を 1 コマンドで足せる。
- [ ] AC2: `kind: "note"` の説明コメントを足せる（`review_id` と `severity` は `null` になる）。
- [ ] AC3: 既存のコメントに返信でき、**返信への返信**も足せる。
- [ ] AC4: `id` が記録の中で一意に採番され、呼ぶ側が指定しなくてよい。
- [ ] AC5: 足したあとの記録が `check` を通る（既存 `validate()` で検証される）。
- [ ] AC6: **差分に無い行**を指定すると、**足さずに**終了コード 3 で落ちる。
- [ ] AC7: そのとき、**そのファイルで指摘できる行**が手がかりとして出る。
- [ ] AC8: 判定とサマリを足せ、**未提出のコメントがその提出に紐づく**。
- [ ] AC9: スレッドを解決 / 未解決に切り替えられる。
- [ ] AC10: まとめて足せ、**1 件でも駄目なら 1 件も書き込まれない**。
- [ ] AC11: 入力は記録 JSON でもバンドルでもよく、**出力は入力と同じ種類**になる。
- [ ] AC12: 既存の `html` / `bundle` / `view` / `template` / `check` / `list` が変わらず動く（回帰）。
- [ ] AC13: 同じ入力・同じ引数から**同じバイト列**が出る（決定論）。
- [ ] AC14: 本文を**ファイルと標準入力**から渡せる（長い本文を引数に押し込まない）。
- [ ] AC15: 検証に落ちたとき、**入力ファイルが変わっていない**。
- [ ] AC16: 出力先を選べる（既定は入力を上書き / 別ファイル / 標準出力）。

## 未確定事項 / 確認したいこと

- アンカー検証で「実在する」とは何か。**文脈行にも指摘してよいか**（GitHub は可）。→ research
- `side` を省略したとき、**行から自動で決められるか**（追加行なら RIGHT、削除行なら LEFT）。→ research
- まとめて足す入力の形（JSON の配列か、行区切りか）。→ design
- 既存コマンドとの語彙の揃え方（`--from` / `--repo` を書く側でも使うのか）。→ design
