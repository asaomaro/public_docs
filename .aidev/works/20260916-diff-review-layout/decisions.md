# 決定記録: 3 ペイン・split・ツリー・テーマ

> autonomous モードのため、人間のゲートで確認するはずだった選択をここに残す。
> 「他の案」は**実際に検討したもの**だけを書く。

## D1: split は画面だけで作り、生成側は触らない

- **決定**: 左右の対応づけを `app.js` の `pairLines()` で行う。`diff_review.py` の出力形式は変えない。
- **理由**: 既存の `{kind, old, new, text}` だけで対応づけが作れることを実測した
  （research F8・88 ハンク / 4,036 行で不変条件の違反 0）。生成側に `split` 用のデータを足すと、
  **同じ情報を 2 通りの形で持つ**ことになり、容量も増え、スキーマの互換問題も増える。
- **他の案**: 生成時に左右の組を作って埋め込む → 容量が増え、`diff-review/2` の互換を壊す。却下。
- **代償**: 対応づけは**行単位**まで。語単位の色分けはしない（要件のスコープ外と一致）。

## D2: split の行は「1 つの `.row` に 2 セル」、現在行は右を優先

- **決定**: `.row` は 1 行 1 つのまま。`data-key` は右（新側）優先、右が無ければ左。
  コメントの入れ物（`.threads` / `.composer-slot`）だけを**左右それぞれ**用意する。
- **理由**: `j` / `k` は `.row` を数えるので、1 組を 2 つの `.row` にすると
  「1 回押すと半行進む」ような挙動になる。一方でコメントの鍵（`line:path:SIDE:n`）は
  左右で別物なので、入れ物は 2 つ要る。**既存の `slotFor()` は鍵で引くだけなので変更不要**。
- **他の案**: 左右を別の `.row` にする → キーボードの移動が壊れる。却下。

## D3: テーマは `data-theme` ＋ メディアクエリ。`light-dark()` は使わない

- **決定**: 値は `:root` に「明の値と `--d-*` の暗の値」を並べて 1 か所に置き、
  暗への割り当てを `@media (prefers-color-scheme: dark) :root:not([data-theme="light"])` と
  `:root[data-theme="dark"]` の 2 か所に書く。
- **理由**: `light-dark()` ＋ `color-scheme` なら割り当てが 1 か所で済み、実測でも 6 通りすべて正しく動いた。
  **しかし対応していないブラウザでは `--bg` が `light-dark(…)` という文字列のまま残り、
  `background: var(--bg)` が無効になって差分の追加 / 削除の色ごと消える**
  （custom property は値を検査せずに格納するので、フォールバックの二重宣言も効かない）。
  現行の `@media (prefers-color-scheme: dark)` は 2019 年から使えるので、
  **今動いている範囲を狭めてまで新しい書き方を採る理由がない**。
- **代償**: 暗への割り当てが 2 か所に重複する。→ **テストで機械的に潰す**
  （2 ブロックの宣言列が文字列一致することを検査。ずれたらテストが落ちる）。
- **補足**: `color-scheme` プロパティ自体は添える（入力欄とスクロールバーの色のため）。
  対応していないブラウザでは単に無視されるだけで、害がない。

## D4: 畳む指定は CSS 変数ではなく `grid-template-columns` の宣言で書く

- **決定**: `.shell[data-left="collapsed"] { grid-template-columns: 0 6px 1fr 6px var(--right); }`。
- **理由**: 幅はドラッグで**インラインの custom property** に入る。
  `[data-left="collapsed"] { --left: 0 }` と書くと**インライン宣言に負けて何も起きない**——
  実測で実際に起きた（research F3。`Enter` を押しても幅 360px のまま）。
- **代償**: 組み合わせ（左だけ / 右だけ / 両方）で 4 つのルールを書くことになる。
  読みにくいが、**黙って効かない**よりはよい。回帰テストで固定する。

## D5: 画面の設定は差分ごとではなく「そのブラウザごと」に記憶する

- **決定**: 保存キーは `diff-review-html/ui/v1/<name>`。**`diff_digest` を含めない**。
- **理由**: 下書き（コメント本文）は差分が変われば意味を失うので digest が要る。
  一方、ペインの幅やテーマは**どの差分を見ても同じであってほしい**人の設定である。
  digest を含めると、レビューのたびに幅とテーマが既定に戻る。
- **代償**: `file://` は全ページが 1 つの origin を共有するので、
  **別のレビュー画面と設定を共有する**。これは意図した挙動。

## D6: 設定が保存できない環境ではバナーを出さない

- **決定**: `localStorage` が使えないとき、下書きについては既存どおりバナーを出すが、
  **画面の設定については黙って既定値で動く**。
- **理由**: 下書きが消えるのは**書いたものが失われる**ので知らせる必要がある。
  画面の幅が既定に戻るのは、開くたびに見れば分かることで、害がない。
  バナーを 2 本出すと、本当に重要な 1 本目が埋もれる。

## D7: ペインとテーマは `ui.js` に切り出し、ツリーとコメント一覧は `app.js` に残す

- **決定**: 新規 `templates/ui.js`（`window.DiffReviewUI`）は DOM と `localStorage` だけを触る。
  ツリー・split・コメント一覧は差分とスレッドの状態を使うので `app.js` に置く。
- **理由**: `app.js` はすでに 1,318 行あり、4 機能を足すと読めなくなる（research R6）。
  切り出す境界は「**レビューの状態を知っているか**」で引くのが自然で、
  知らない部分だけを出せば `window` 越しの結合が最小（`pref()` 1 本）で済む。
- **他の案**: すべて `app.js` に足す → 1,800 行超。却下。
  すべてを機能ごとに分割 → 状態を `window` 越しに共有することになり、結合が増える。却下。
- **代償**: 同梱する `<script>` が 1 つ増える（`rich.js` と違い**常に**入る）。
  容量への影響は数 KB。

## D8: 足すキーは 3 つだけ（`s` / `[` / `]`）

- **決定**: split 切り替え・左ペイン開閉・右ペイン開閉のみ。
  テーマ・ツリー・絞り込み・移動は**ボタンとして `Tab` で届く**形にする。
- **理由**: 前 work の must（`Enter` をページ全体で横取りしてボタンが押せなくなった）は、
  **キーを足したこと自体**が原因だった。要件 AC-I1 が求めるのは「キーボードで到達できる」ことで、
  「専用キーがある」ことではない。
- **代償**: テーマ切り替えは `Tab` を何度か押す必要がある。許容する。
- **test 工程での修正**: `[` / `]` の割り当てを「畳む」から「**そのペインへ移動**」に変えた。
  実測で、差分の行にいる状態から **`Tab` を 60 回押してもコメント一覧に届かなかった**
  （中央ペインの行 1 つ 1 つにコメントボタンがあり、DOM 順で右ペインはその後ろにあるため）。
  AC-I3（キーボードだけで一周できる）が実際には成り立っていなかった。
  畳む操作には他に 2 経路（トップバーのボタン・境界の `Enter`）があるが、**移動には経路が無かった**
  ので、1 つしかない鍵を移動に充てた。畳むのは `Shift` 併用（`{` / `}`）に移した。

## D9: 展開した文脈行は、split でも両側に同じ本文を出す

- **決定**: 展開データは片側しか持たない（前 work D3）ので、
  **知らない側の行番号は空欄**にし、本文は両側に同じものを出す。
- **理由**: 文脈行は定義上、両側で同じ本文である。番号だけが分からない。
  片側を空にすると「削除された行」に見えてしまい、**嘘になる**。
- **代償**: split で展開すると、片側の行番号だけが空いた行が並ぶ。SKILL.md に限界として書く。

## D10: ツリーは「子が 1 つしかないディレクトリ」を畳んで 1 行にする

- **決定**: `docs` → `ClaudeCode` → `skills` → `other` のような連なりは
  `docs/ClaudeCode/skills/other` と 1 行にまとめる。
- **理由**: 畳まないと、このリポジトリの差分では**ファイルに辿り着くまでに 5 段**下る。
  「構造で辿れる」という目的（US2）に対して、段数が増えるだけで情報が増えない。
- **代償**: 中間のディレクトリ単位では畳めない。実用上、困る場面が思いつかない。

## D11: 前 work から残っていた「生成が止まらない」欠陥を、この work で直した

- **決定**: `richdiff.markdown_nodes` の段落取り込みが 0 行を返したとき、
  1 行を段落として消費して必ず前へ進める。回帰テストを 2 件足す。
- **理由**: 直さないと**この work のサンプルを 1 つも作れない**（生成が永久に終わらない）。
  要件の外だが、外に置いたままでは要件（AC1〜AC17 の実測）が果たせない。
  症状も重い——利用者から見ると「コマンドが返ってこない」で、原因の手がかりが何も出ない。
- **範囲の線引き**: 直したのは**進行の保証だけ**。フェンス記法の解釈そのもの
  （4 個以上のバッククォートを正しく扱う等）には手を付けていない。
  今回の行は「段落として出す」が正しい落とし所で、それ以上は別の要件になる。
- **代償**: なし（0 行しか取れない場合だけ経路が変わる）。

## D12: 既に処理されたキーは `document` 側で扱わない

- **決定**: `onKeyDown` の冒頭で `event.defaultPrevented` なら何もせず降りる。
- **理由**: ツリーの `↑` `↓` が、ツリーの項目を移動すると**同時に差分の行送りも起こしていた**
  （実測）。ツリー側は `preventDefault` していたが、`document` の受け口はそれを見ていなかった。
  個別に「対象がツリーなら無視」と書くと、要素が増えるたびに条件が増える。
  **「もう誰かが処理した」を 1 か所で見る**ほうが、増えても壊れない。
- **他の案**: ツリー側で `stopPropagation` する → 他の受け口（将来の機能）にも届かなくなる。却下。
- **代償**: 既定動作を打ち消す目的で `preventDefault` する箇所があると、そこでキーが死ぬ。
  現状そういう箇所は無く、増やすときは気づける（キーが効かなくなるので）。
