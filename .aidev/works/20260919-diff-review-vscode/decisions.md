# 決定記録

## D1: full / autonomous で起こし、編集・保存までを範囲に含める

- **背景**: ユーザーから「当初案にあった、VSCode でファイル差分情報とコメント情報を含んだ
  ファイルを開いて WebView で当画面を表示する VSCode 拡張機能の開発に着手してください」と
  指示があった。当初案は work `20260916-diff-review-bundle` の requirements.md（対象外:
  「VSCode 拡張そのものの実装。この work が作るのは土台（形式とビューアの口）まで」）と、
  `SKILL.md` の「エディタ拡張から使う（土台）」節（`view --readonly` を使う契約）に残っている。
  続けて「html 版と VSCode 版でコードを共有できる箇所は可能な限り共有し、同じコードの実装を
  増やさないようにして」との追加指示があった。
- **決定**:
  - 三層判定は **full**（新しい成果物＝拡張機能一式を作り、ビューア側にもホストとの往復の口を
    足す。影響が複数モジュールにまたがり、light の「振る舞いを変えない小規模」に当たらない）。
  - モードは **autonomous**（ユーザーに「進め方」を確認し「PR作成まで自走」を選択。
    その選択肢の説明には「PR作成・マージまで行う」と書いてあり、直前のラウンドでも
    「mergeまでよろしく」と指示されている）。
  - 範囲はユーザーに確認し、**表示だけでなく、コメントの追加・編集をして `.dreview` へ保存する
    ところまで**とする（選択肢「編集・保存まで」）。当初案の契約は `view --readonly` を
    前提にしていたので、ここは当初案からの**拡張**になる。
  - `dependsOn: [20260916-diff-review-bundle]`（土台の work。deliver 済み）。
- **理由・代替案**: 「表示専用で着手し、編集は次の work」を推奨として提示したが、ユーザーは
  編集・保存までを選んだ。人間の承認ゲートを design に残す案（`humanGates: [design]`）も
  提示したが、ユーザーは自走を選んだ。方針の選択肢と採らなかった案は、design の前に
  この decisions.md へ書いてから進める（`protocol-autonomous.md`「方針の事前承認」）。
- **影響**: 当初案の契約（`SKILL.md` 454-468 行）は読み取り専用前提なので、編集を足す分だけ
  契約を書き足すことになる。コード共有の指示により、拡張側（TypeScript）へビューアの処理を
  移植しない方針が前提になる（design で具体化する）。

## D2: 正規形でない `.dreview` は「開いただけなら触らない・最初の編集で正規形へ」

- **背景**: requirements の独立点検（doccheck ラウンド1）で、F3/AC4「保存した中身は正規形とバイト一致」と
  F4/AC5「開いただけならバイト列は変わらない」が、**正規形でないが読める `.dreview`**
  （CRLF に変わったもの・手で整形したもの・別の版の生成物）を開いたときにぶつかる、と must で指摘された。
- **決定**: 開いただけ（編集していない）なら書き換えない＝未保存にならない。編集した時点で、
  文書全体を正規形に書き換える（正規形を優先する）。AC5 の「バイト列が変わらない」は正規形の
  ファイルに限り、正規形でないファイルには「開いただけでは書き換わらない」を求める。
- **理由・代替案**: 「元の整形を保ったまま差分だけ書き換える」案は、JSON の部分的な書き換えを
  テキストで行うことになり、壊れやすい上に、保存後の中身が `check` の正規形と一致しなくなる。
  `.dreview` は CLI が正規形で書き出すのが前提の生成物なので、編集した時点で正規形へ揃えるのが自然。
- **影響**: requirements.md の F4・AC5 を書き換えた。design では「編集がない限り文書へ書き込まない」
  （開いた直後に正規化を走らせない）ことを守る必要がある。

## D3: 同期は「裏にテキスト文書・画面が正規形の全文を作る」

- **背景**: 画面での編集を `.dreview` に戻す経路の選択（research.md F1, F2, F12-F14, F21-F24）。
- **決定**: **案 A** を採る——`CustomTextEditorProvider`（裏は `TextDocument`）。画面は編集のたびに
  **正規形のバンドル全文**を作ってホストへ送り、ホストはそれを文書へ書くだけ。文書の変更（元に戻す・外部変更）は
  **テキストのまま**画面へ送り、画面が解析する。
- **採らなかった案**:
  - 案 B「画面は記録だけ送り、拡張がバンドルにはめ込む」——拡張側（TypeScript）にバンドルの解析と正規形の
    書き出しが要り、**同じ処理が 2 つになる**（ユーザー指示に反する）。
  - 案 C「`CustomEditorProvider`（独自の文書モデル）」——元に戻す・バックアップ・保存を自前で持つことになる
    （`index.d.ts:9690-9759`）。`.dreview` はテキストなので、公式ガイドの規範（F2）にも合わない。
- **影響**: 拡張はバンドルの形式を知らない（前置きも JSON も解析しない）。文書へ書くときの最小化は
  **形式を知らない文字列の差分**（共通の前後を除いた範囲の置き換え）で行う。

## D4: 画面側の橋渡しは `templates/app.js` の中に置く

- **背景**: 画面（WebView）の中で、ホストとの往復・VSCode の配色・入力欄の `Ctrl+Z` を扱うコードの置き場所。
- **決定**: **`app.js` の中**に「ホストがいるとき」の分岐として置く（`acquireVsCodeApi` の有無で判定）。
  配色だけは画面の設定を持つ `ui.js` に置く。拡張は**スクリプトを差し込まない**（CSP と nonce を付けるだけ）。
- **採らなかった案**:
  - 「拡張が別のスクリプトを差し込む」——記録・下書き・描画は `app.js` の閉包の中にあり、外から触るには内部を
    公開する口が要る。`acquireVsCodeApi` は 1 回しか呼べない（F11）ので、呼ぶ場所が 2 つに割れる危険もある。
  - 「`templates/host.js` を新設」——同じく閉包の外になり、`app.js` の内部を公開する口が要る。
- **影響**: HTML 版では `acquireVsCodeApi` が無いので、足した分岐は一切動かない（HTML 版の振る舞いは変わらない）。

## D5: 拡張が載せるビューアは、ビルド時に `diff_review.py view` で生成し、コミットしない

- **背景**: 拡張の画面を「`diff_review.py` がテンプレートから生成したものそのもの」にする方法（要件 F9・AC11）。
- **決定**: 拡張のビルド手順で `python3 ../diff_review.py view --out media/viewer.html` を実行して生成し、
  `media/viewer.html` は `.gitignore` する。テストで「同梱物 == `view` の出力」を確かめる。
- **採らなかった案**: 生成物をコミットする（テンプレートの写しが 2 つになり、片方だけ古くなる）／
  拡張が実行時に Python を呼ぶ（利用者の環境に Python を要求し、起動も遅くなる）。
- **影響**: 拡張をビルドする人の環境に Python 3 が要る（`diff_review.py` 自体の前提と同じ）。

## D6: 拡張は TypeScript・`diff-review-html/vscode/`・実行時依存ゼロ

- **背景**: 拡張のソースの置き場所・言語・依存。
- **決定**: skill のディレクトリ直下に `vscode/` を置く（ビューアの生成元 `../diff_review.py` を相対で指せる）。
  言語は TypeScript（`tsc` でコンパイル。実行時依存が無いのでバンドラは使わない）。実行時依存はゼロ、
  開発時の依存は `vscode/` の `package.json` に閉じ、`vscode/.gitignore` で `node_modules` と生成物を外す
  （ルートの `.gitignore` は `/node_modules` しか外していない）。
- **採らなかった案**: 別のトップレベルに置く（生成元への参照が遠くなる）／素の JS（型の支えが無い。VSCode の
  拡張の標準は TypeScript）／esbuild で束ねる（束ねる依存が無い）。
- **影響**: `engines.vscode` は `^1.90.0`（調査で使った型の版。実機は 1.138.0 で確認）。

## D7: 検査は 3 層。実機の VSCode を CDP で操作する e2e をリポジトリに置く

- **背景**: AC14（実機での自動テスト）と AC-I3/AC-I5（実キー入力）を、どこまでリポジトリの自動テストにするか。
- **決定**:
  1. Python の unittest（既存）に、`view` の出力が変わっていないこと・画面の橋渡しが HTML 版で眠っていることを足す。
  2. 拡張の純粋な関数（CSP/nonce の付与・最小の書き換え範囲）を `node:test` で検査する（VSCode 不要）。
  3. **実機の VSCode**（`@vscode/test-electron` で取得）を `--remote-debugging-port` で起動し、playwright-core の
     `connectOverCDP` で**実キー入力**を送る e2e（開く・コメント・保存・元に戻す・外部変更・配色）。
- **採らなかった案**: 拡張ホスト上の API テストで画面の中を検査する——画面は隔離されていて、中を見るには
  製品コードに**テスト用の口**を足すことになる。実キー入力も送れない（F15-F20 はキー入力でしか確かめられない）。
- **影響**: e2e は画面（WSLg 等）とネットワーク（初回の VSCode 取得）が要る。開発依存に playwright-core が加わる。

## D8: 正規形のバンドルは既存の `sortDeep` + `JSON.stringify` に U+2028/2029 の退避を足して作る

- **背景**: 画面の JS で Python とバイト一致するバンドルを作る方法（F21-F23, R4）。
- **決定**: 記録の書き出しで既に使っている `JSON.stringify(sortDeep(x), null, 2)`（`app.js:205-261`）を
  そのまま使い、`js_safe` と同じ U+2028/2029 の退避を足す。Python との一致は e2e（保存したファイルを
  Python の `bundle_text` で作り直して比べる）で固定する。
- **採らなかった案**: Python と同じ並び順（符号位置順）を持つ自前の直列化——整数風のキー・BMP 外の文字を含むキーは
  スキーマ上現れず、実データにも 0 件（F23）。**起きない食い違いのために別の直列化を足さない**。
- **影響**: スキーマに「利用者のデータをキーにする辞書」を足すときは、この決定を見直す（その時点で
  e2e の一致検査が落ちる）。

## D9: VSCode 版では「文書が唯一の真実」。HTML 版だけの操作は出さない

- **背景**: HTML 版だけの操作（F34）の VSCode 版での扱い（requirements の未確定事項）。
- **決定**: ホストがいるときは、ファイルを開く（`#btn-open-file`）・下書きの初期化（`#btn-reset-draft`）・
  JSON のダウンロード（`#btn-download`）を**DOM から外す**。D&D での取り込みは受けない（VSCode 自身が
  エディタ領域へのドロップを扱う）。`beforeunload` の確認はしない（閉じるときの確認は VSCode が出す）。
  起動時に `localStorage` の**記録（`state`）は復元しない**（文書と食い違うため）。下書き（書きかけ）と
  「確認済み」は `localStorage` に残す（F7 で開き直しても残ることを確認済み）。「JSON を書き出す」の画面
  （テキスト表示とコピー）は残す。
- **採らなかった案**: 別のバンドルを同じエディタで開けるようにする——画面と文書が指すものが食い違う。
  下書きの初期化を「元に戻す」に読み替える——VSCode に「元に戻す」「ファイルを元に戻す」が既にある。
- **影響**: `wire()` は既に「あれば繋ぐ」形（`app.js:2588-2590`）なので、外した要素は結線されない。

## D10: 画面と拡張の同期に文書の版（`document.version`）と ack を使う

- **背景**: design の独立点検（doccheck ラウンド1・17 件）で、テキストの一致だけで同期する初版の設計に
  次の穴が指摘された: (1) 文書が壊れた → 元の正しいテキストに戻ったとき、画面が「前と同じテキスト」として
  無視し、壊れた表示のまま動かなくなる（must）。(2) 画面の編集と外部変更・VSCode の元に戻すがすれ違うと、
  古い内容を基にした編集で新しい変更を上書きし、しかも画面と文書が食い違ったままになる。
  (3) 編集を続けざまに送ると、古いテキストに対して最小の書き換え範囲を計算しうる。
- **決定**: 拡張は文書を渡すたびに `document.version` を添え、画面は編集に**基にした版**（`baseVersion`）を添える。
  拡張は編集を**1 本ずつ**処理し、`baseVersion` が今の版と違えば**適用せずに退け**（`rejected: true` 付きで今の文書を
  送り直す）、適用したら新しい版を `ack` で返す。画面は**送った編集の返事（`ack` か文書）が来るまで次を送らず**、
  その間に記録が変わったら返事のあとに最新の全文を送り直す（全文を送るので間の変更はまとめてよい）。
  画面は受け取ったテキストを、正しくても壊れていても**必ず「いま受けているテキスト」として覚える**。
  壊れている間は差分を**空にして理由だけ出し**、画面で編集できるものを残さない。
- **採らなかった案**:
  - テキストの一致だけで同期する（初版）——上の (1)(2) が起きる。
  - 退けずにその場で 3-way マージする——記録の構造を知るマージが拡張側に要り、実装が 2 つになる（D3 に反する）。
    すれ違いは「画面で操作した瞬間に外で書き換わった」ときだけで、まれ。退けたことは画面に出す。
  - 壊れている間も古い表示を残す（HTML 版の「いまの表示を壊さない」）——残った表示に書いた変更はどこにも
    保存されず、直ったあとに黙って上書きされる。VSCode 版では文書が唯一の真実なので、無いものを見せない。
- **影響**: 拡張の同期の判断は VSCode に依存しない純粋なクラス（`src/sync.ts`）に置き、`node:test` で
  すれ違い・元に戻す → やり直し・壊れる → 戻る、の順序を検査する。メッセージに `version` / `baseVersion` /
  `ack` / `rejected` が加わる（design.md のメッセージ表）。

## D11: design の独立点検は上限（2 ラウンド）で打ち切り、残りは unit テストと review に委ねる

- **背景**: design の doccheck はラウンド1で 17 件、ラウンド2で 14 件（must 1）。どちらも中心は同期の手順
  （すれ違い・返事の対応づけ・壊れる → 戻る・作り直しの途中の編集・版だけ進む）だった。ラウンド2の指摘を受けて、
  編集に id を付けて返事を 1 つに対応づける・拡張側を 1 本の列にする・版だけ進んだときも送る・バナーの置き場を分ける・
  壊れている間に書いたものは保存されないと知らせる、に直した（design.md「振る舞いの詳細」）。
  `maxDocCheckRounds`（2）に達したので 3 ラウンド目は打たない。
- **決定**: 残る疑問（直した手順に新しい穴が無いか）は、**`src/sync.ts` の `SyncSession` を VSCode に依存しない
  純粋なクラスにして `node:test` で順序を検査する**ことで確かめる（tasks に入れる。すれ違い・元に戻す → やり直し・
  続けざまの編集・退け中の重ね書き・作り直し中の編集・版だけ進む・書けない、の各順序）。画面側の同じ手順は e2e で
  実機に通す。判断は 60 review にも委ねる。
- **理由・代替案**: 3 ラウンド目を打つのは上限の趣旨に反する（`protocol-check.md`）。文書の点検は「読んで分かる穴」を
  拾うのが役目で、順序の組み合わせは実行で確かめる方が確実。
- **影響**: tasks に `SyncSession` の順序のテストを明示的に置く。

## D12: 任意工程 architecture は挟まない

- **背景**: `protocol.md`「4.5」の architecture の条件のうち「インターフェース／データモデルが複雑（状態遷移の設計に
  踏み込む）」に、同期の手順が当たりうる。
- **決定**: 挟まない。architecture が扱う中身（モジュールの分け方・依存の向き・メッセージの契約・状態の遷移）は、
  design.md の「対象範囲」「インターフェース / データ構造」「振る舞いの詳細」に既に書いてあり、2 ラウンドの独立点検も
  そこに当てた。別の文書に同じものを書き直すだけになる。
- **理由・代替案**: 挟むと、同じ状態遷移が design.md と architecture.md の 2 か所に書かれ、片方だけ直る危険が増える。
  他の 3 条件（モジュールの境界を動かす／新しい構造の選択／tasks に割るには粗い）には当たらない——拡張は新しい
  ディレクトリで既存モジュールの境界を動かさず、構造の選択は D3-D7 で済み、design はファイルと関数の粒度まで
  具体化している。
- **影響**: 次工程は tasks。

## D14: VSCode の文書へ書く記録は id を振り直さない

- **背景**: T6 のタスク点検で、送る記録を `canonicalRecord()`（id を r1.. / t1.. / c1.. に振り直す）で作ると、文書を採用し直した
  ときに画面が id で覚えている状態（`editingReviewId`・`threadCollapsed`・返信／編集の下書きの鍵）が別のものを指すと指摘された
  （「保存する」で別のレビューを上書きする手順が再現された）。
- **決定**: `canonicalRecord(keepIds)` を足し、VSCode の文書へ書くとき（`bundleText`・比較用の `hostRecordText`）は id を
  振り直さない。キーの並びと整形（正規形の規則）は同じ。HTML 版の「JSON を書き出す」は今どおり振り直す。
- **理由・代替案**: Python の `bundle_text` も id を振り直さない（`diff_review.py:114-117`）ので、AC4（Python の正規形との
  バイト一致）は保たれる。送るたびに画面側の状態の鍵を振り直し後の id へ付け替える案は、鍵の形（`reply:` / `edit:` 等）を
  知る処理が増え、漏れた鍵が同じ事故を起こす。id を動かさないほうが単純。
- **影響**: design.md の「`bundleText()` の `review: canonicalRecord()`」は `canonicalRecord(true)` になる（この記録が正）。
  画面で足したスレッドの id は `nextId`（採番は記録の最大値から続く。`templates/app.js` `adoptRecord`）なので重複しない。

## D15: 文書へ書く記録はスレッドを並べ替えない

- **背景**: coding の横断点検（cross）で、`canonicalRecord(true)` がスレッドを path / line で並べ替えるのに対し、Python の
  `bundle_text` と `comment` は配列の順のまま（新しいスレッドは末尾に足す）ことが分かった。CLI で書いた `.dreview` は Python では
  正規形だが、画面での最初の編集でスレッドの順がすべて動き、打ち消し合う操作でもバイト列が元に戻らない。
- **決定**: `keepIds` のとき（VSCode の文書へ書くとき）は並べ替えず、画面の配列の順（文書の順。画面で足したスレッドは末尾）で書く。
  HTML 版の「JSON を書き出す」は今どおり並べ替えと id の振り直しを行う。
- **理由・代替案**: Python 側を並べ替えに合わせる案は、既存の CLI の出力（既に配っているファイル）を変えることになり、この work の
  対象外（requirements「形式の変更」は対象外）。D14 と同じく「文書の中身は Python の書き方に合わせ、画面の都合で動かさない」。
- **影響**: AC4 の「同じ内容を Python の正規形で書き出したものとバイト一致」は、配列の順も含めて成り立つ。
