# 要件: 差分を「ファイル」として切り出し、ビューアと分ける

## 背景 / 課題

`diff-review-html` は「差分 ＋ 画面 ＋ 指摘」を**1 枚の HTML に焼き固めて**出す。
読むだけなら十分だが、次にやりたいことに対して形が合っていない。

- **VSCode 拡張の土台にならない**。拡張は「ファイルを開く → ビューアが立ち上がる」形になるが、
  いまは差分ごとに HTML を作り直すしかない。**ビューア（画面）と中身（差分・指摘）が分かれていない**。
- **差分と指摘が別々のファイルに散る**。いまは HTML（差分）と `review.json`（指摘）の 2 本立てで、
  「このレビュー」を 1 つの物として渡せない。受け渡しのたびに 2 つ添付することになる。
- **スクリプトが人間向けでない**。`--unstaged` / `--staged` / `--range` / `--commit` が
  別々のフラグに散っており、「どこから差分を取るか」が 1 つの軸として見えない。
  将来 GitHub の PR を足すと、フラグがさらに増える。
- **配布すると編集できてしまう**。指摘を書き込んだ HTML をそのまま渡すと、受け取った側が
  書き換えて再書き出しできる。**「読むだけ」で渡す形が無い**。

## 目的 / ゴール

- **差分と指摘が 1 つのファイル**にまとまっていて、それだけを渡せば内容が再現できる状態。
- **ビューア（画面）とファイルが分かれていて**、同じビューアが別のファイルを開ける状態。
  VSCode 拡張が「ファイルを読んでビューアに渡す」だけで成立する状態。
- **いまの「全部入り 1 枚 HTML」も、これまでどおり作れる**状態（壊さない）。
- **人間がそのままコマンドを打てる**状態。差分の取得元が 1 つの軸で指定でき、
  将来 GitHub を足しても形が変わらない。
- **配布用に「読むだけ」の HTML** が出せる状態。書き込みの導線が**そもそも積まれていない**。

## ユーザーストーリー

- US1: 拡張機能を作る人として、差分と指摘を 1 つのファイルとして読み書きしたい。
  なぜなら、エディタが扱う単位は「ファイル」であり、2 つに分かれていると
  どちらが正かの管理を拡張側で抱えることになるから。（受け入れ: AC1, AC2, AC3）
- US2: 拡張機能を作る人として、ビューアにデータを**渡す**口が欲しい。
  なぜなら、webview はファイルを直接読めず、拡張が読んで渡す形になるから。（受け入れ: AC4, AC5, AC14）
- US3: レビューする人間として、ビューアを開いて手元のファイルを選びたい。
  なぜなら、拡張を入れていない相手にも同じビューアで見てもらいたいから。（受け入れ: AC6, AC7, AC15）
- US7: 受け取ったバンドルを開く人として、**それを開くと何が起きるかが分かる**状態でいたい。
  なぜなら、他人から受け取ったファイルを開く行為に、知らないうちに「実行」が混ざるのは困るから。
  （受け入れ: AC14, AC15）
- US4: 差分を作る人間として、取得元をコマンドの引数で選びたい。
  なぜなら、フラグが機能ごとに増えると、覚えることが増えて使わなくなるから。（受け入れ: AC8, AC9）
- US5: レビューを受け取る人として、書き換えられない形で配れるものが欲しい。
  なぜなら、確定した指摘を共有したいのであって、相手に編集させたいわけではないから。（受け入れ: AC10, AC11）
- US6: いまの使い方をしている人として、**何も変えずに済ませたい**。
  なぜなら、skill から呼ばれる既存の経路が動かなくなると、いまのフローが止まるから。（受け入れ: AC12, AC13）

## スコープ

### 対象

- **バンドル形式**（差分 ＋ 指摘 ＋ 対象情報を 1 ファイルに。独自拡張子）。
- **ビューアの 3 つの取り込み口**: 埋め込み済み / ホストからの注入 / ファイルを開く。
- **`file://` での自動読み込み**（`<script src>`）——**やるかどうかを含めて決める**。
- **CLI の整理**: 取得元を 1 つの軸にする。`bundle`（バンドルを出す）と
  `view`（ビューアだけを出す）のサブコマンド追加。
- **参照専用 HTML**（書き込みの導線を積まない）。
- 既存の `html` / `template` / `check` / `list` の互換維持。

### 対象外

- **VSCode 拡張そのものの実装**。この work が作るのは土台（形式とビューアの口）まで。
- **GitHub からの差分取得**。引数の形だけ将来に備え、実装は入れない。
- 差分の**編集・適用**（パッチとして当てる機能）。
- バンドルの**圧縮**（容量は既存のフラグで調整する範囲に留める）。

## 機能要件

- **F1 バンドル形式**: 差分（`files`）・対象（`target`）・指摘（`reviews` / `threads`）を
  1 ファイルに持つ。スキーマ名とバージョンを持ち、`check` で検証できる。
- **F2 独自拡張子**: バンドルは専用の拡張子で書き出す。
- **F3 JSON として読める**: 生成側（Python）・拡張（Node）・他のツールが、
  **JS を実行せずに**中身を取り出せる。
- **F4 ビューア単体の出力**: 差分を持たないビューア HTML を出せる。
- **F5 ホストからの注入**: ビューアは、ホスト（VSCode 拡張など）が渡したバンドルを表示する。
- **F6 ファイルを開く**: ビューアは、ファイル選択と D&D でバンドルを開ける（実行を伴わない）。
- **F6b 失敗を黙らせない**: 取り込みに失敗したとき（壊れている / 別の形式 / 版が違う）、
  **何が起きたかを画面に出す**。白い画面やコンソールだけのエラーで終わらせない。
- **F7 取得元の指定**: `--from` 1 つで `unstaged` / `staged` / `range` / `commit` を選べる。
  `github-pr` は**受け付けて「未対応」と明示して落ちる**（将来の場所を予約する）。
- **F8 参照専用 HTML**: コメント入力・返信・解決・提出・JSON 入出力の導線を**積まない**。
  読む機能（展開・rich・split・ツリー・テーマ・コメント一覧）は残す。
- **F9 既存の互換**: `html` / `template` / `check` / `list` と既存のフラグは、これまでどおり動く。

## 非機能要件 / 制約

- **単一 HTML・オフライン・第三者ライブラリなし・Python3 標準ライブラリのみ**（既存の性質を維持）。
- **決定論**: 同じ入力から同じバイト列（HTML もバンドルも）。
- **正規形**: バンドルも UTF-8・LF・キー昇順・末尾改行。往復でバイト一致する。
- **XSS 非解釈を保つ**: 取り込み口が増えても、描画は `textContent` のまま。
  外から来たバンドルは**必ず検証してから**使う。
- **危険の明示**: 実行を伴う取り込み口を用意する場合、**それと分かるようにする**
  （黙って便利にしない）。
- **参照専用は「隠す」ではなく「積まない」**: DOM を隠すだけだと、開発者ツールで戻せる。

## 完了条件 (受け入れ基準)

- [ ] AC1: 差分と指摘を 1 つのバンドルファイルに書き出せる（専用の拡張子）。
- [ ] AC2: バンドルから、元の差分と指摘が**同じ内容で**再現される。
- [ ] AC3: バンドルを `check` で検証でき、壊れていれば理由を出して落ちる。
- [ ] AC4: 差分を持たないビューア HTML を出せる。
- [ ] AC5: ホストが渡したバンドルを、ビューアが表示する（実行を伴わない口がある）。
- [ ] AC6: ビューアで、ファイル選択 / D&D からバンドルを開ける。
- [ ] AC7: 壊れたバンドル・別の形式のファイルを開いたとき、**理由が画面に出る**（黙って白くならない）。
- [ ] AC8: `--from unstaged|staged|range|commit` で取得元を指定できる。
- [ ] AC9: `--from github-pr` は「未対応」と明示して落ちる（黙って別の差分を出さない）。
- [ ] AC10: 参照専用 HTML を出せ、コメント入力・提出・JSON 入出力の**導線が DOM に存在しない**。
- [ ] AC11: 参照専用 HTML でも、読む機能（展開・rich・split・ツリー・テーマ・コメント一覧）は動く。
- [ ] AC12: 既存の `html` / `template` / `check` / `list` と既存フラグが、これまでどおり動く（回帰）。
- [ ] AC13: 生成物が決定論的で、外部リクエストが 0 件のまま（回帰）。
- [ ] AC14: バンドルが**JS を実行せずに**読める（Python と Node の両方で実測）。
- [ ] AC15: 実行を伴う取り込み口を用意する場合、**既定では無効**で、使うと分かる形になっている。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開く / 閉じる: ビューアの「ファイルを開く」はキーボードで到達でき、
      読み込み中・成功・失敗が画面に出る。
- [ ] AC-I2 確定 / 取り消し: バンドルを読み込んだあと、**書きかけの下書きが失われない**。
      既存のビューアは書きかけのコメントを**差分ごと**にブラウザへ保存している
      （保存キーに差分の digest を含めている）ので、別のバンドルに切り替えたら
      **そのバンドルの下書きに切り替わる**のが正しい振る舞いになる。
- [ ] AC-I3 キーボードだけで完結: 「ビューアを開く → バンドルを開く → 指摘を読む」が
      マウス無しで通せる。
- [ ] AC-I4 フォーカスの行き先: バンドルを読み込んだあと、フォーカスが**差分の先頭**へ移る
      （読み込んだのに、キーボードの現在位置がボタンに残らない）。
- [ ] AC-I5 既存の操作を妨げない: 参照専用でも、既存のキー（`j`/`k`/`e`/`t`/`f`/`s`/`[`/`]`/`?`）が
      **書き込み系以外は**同じに働く。書き込み系（`c`/`Enter`/`r`）は**何も起きない**（誤爆しない）。

## 未確定事項 / 確認したいこと

- **`<script src>` による自動読み込みを入れるか**。`file://` で唯一動く経路だが、
  **バンドルを実行することになる**。入れるなら既定で無効か、そもそも入れないか。→ research / decisions
- 拡張子の名前と、**バンドルのスキーマ名**（既存の `diff-review/2` との関係）。→ research
- **VSCode の webview が実際に何を要求するか**（データの渡し方・CSP）。→ research
- 参照専用で「解決ボタン」をどうするか（読むだけなら不要だが、既存の見た目が変わる）。→ design
- バンドルの容量（差分 ＋ 展開データ ＋ rich が 1 ファイルに入る）。→ research
