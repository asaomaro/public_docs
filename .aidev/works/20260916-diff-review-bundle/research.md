# 調査: 差分ファイルとビューアの分離

> 実測は headless Chromium（Playwright 同梱）で **`file://` のまま**行った。
> Node は `v22.22.2`（VSCode 拡張と同じ実行系）。検証スクリプトは使い捨て（scratchpad）。
> 数値はすべてこの環境で取ったもの。

## 調査課題（requirements の「未確定事項」より）

1. `file://` で開いた HTML が、**隣のファイルを読めるか**（F1）。
2. 読めるなら、その形式は **JS を実行せずにも読めるか**（F2）。
3. ホスト（VSCode 拡張）から**渡す**経路は成り立つか（F3）。
4. VSCode の webview は何を要求するか（F4）。
5. バンドルにすると**容量**がどうなるか（F5）。
6. 参照専用を「積まない」で作れるか（F6）。

## F1: `file://` で効く経路は **`<script src>` だけ**（実測）

同じ内容を 4 通りの方法で読ませた。

| 方法 | 結果 |
|---|---|
| `<script src="data.dreview">`（**独自拡張子**） | **読める**（`window.__…__` がオブジェクトとして入る） |
| 同上・**別ディレクトリ**（`../bundles/rev-abc.dreview`） | **読める** |
| 同上・**日本語（UTF-8）と改行** | **そのまま読める**（`<meta charset>` に従う） |
| `fetch("data.json")` | ✗ `TypeError: Failed to fetch`（`Fetch API cannot load file:…`） |
| `XMLHttpRequest` | ✗ `NetworkError` |
| `import("./data.js")`（モジュール） | ✗ `Failed to fetch dynamically imported module` |

古典的な `<script src>` だけが CORS の外にある（モジュールは CORS の対象なので**落ちる**）。
拡張子は何でもよい——`file://` では MIME の推測が緩く、`.dreview` でも実行された。

**含意**: 「テンプレート HTML ＋ 差分ファイル」をブラウザだけで成り立たせるなら、
差分ファイルは **JSON そのものではなく「代入文に包んだ JS」**でなければならない。
そしてそれは、**そのファイルを実行する**ということでもある（→ R1）。

## F2: 同じ 1 ファイルが「JS としても JSON としても」読める（実測）

固定の前後で包む形を試した。

```
window.__DIFF_REVIEW_BUNDLE__ = {  ← 前置き（固定）
  …正規形の JSON…
};                                  ← 後置き（固定）＋改行
```

読み手 3 者で、**同じファイル**から同じ内容が取れることを測った。
本文には `</script>`・バックスラッシュ・絵文字・改行・**U+2028 / U+2029** を混ぜた。

| 読み手 | やり方 | 結果 |
|---|---|---|
| Python（生成側・`check`） | 前後を剥がして `json.loads` | **一致**（実行しない） |
| Node（VSCode 拡張） | 前後を剥がして `JSON.parse` | **一致**（実行しない） |
| ブラウザ（`<script src>`） | 実行して `window.__…__` を読む | **一致**（エラー 0） |

前後が一致しなければ**その時点で拒否できる**ので、他人のファイルを JSON として読む経路は
「実行しない」ことが構造的に保証できる。

**ただし 1 点、生成側で手当てが要る**——`U+2028` / `U+2029` は **JS では行終端文字**で、
ES2019 より前のエンジンでは文字列リテラルの中に生で置けない。
今回の Chromium では通ったが、**JSON としての意味を変えずに ` ` / ` ` へ退避できる**
（退避しても `JSON.parse` の結果は同じ）ので、包むときは退避する。

## F3: ホストから**渡す**経路は成り立つ（実測）

`file://` のページを `iframe` に入れ、親から `postMessage` でバンドルを渡した。

| 測った項目 | 結果 |
|---|---|
| 正しい形のバンドル | **受け取って表示が変わった** |
| 形の違うデータ（`schema: "wrong/9"`） | **拒否された** |
| コンソールのエラー | 0 |

`file://` は origin が opaque なので **`event.origin` での検査はできない**。
検査は**形**（スキーマ名と構造）で行うことになる。
これは VSCode の webview でも同じ構図（拡張が読んで webview へ渡す）で、
**実行を伴わない**——この work の本命の経路。

## F4: VSCode の webview（**一次情報は未取得・要実機確認**）

検索で得た範囲（`code.visualstudio.com` の Custom Editor API ほか）:

- 読み取り専用のカスタムエディタは `CustomReadonlyEditorProvider`。
  `openCustomDocument` で**リソースを読んで内部モデルを作り**、
  `resolveCustomEditor` で `WebviewPanel` に**初期 HTML を流し込む**。
- 拡張 ↔ webview のやり取りは `postMessage`。
- CSP は**拡張が meta タグで付けるもの**で、付けた場合は
  `script-src 'nonce-…'` の形が推奨される。**nonce を付けない inline script は落ちる**。

> **未確認**: 「CSP meta を付けなかったときの既定」がどうなるかは、この環境では確かめられない
> （VSCode が無い）。上は検索結果の要約で、**一次資料は取得していない**。

**含意（設計へ）**: 生成する HTML は inline `<script>` を使っている。
拡張が CSP を付けるなら nonce が要る。**ビューア側で nonce を持つのではなく、
「拡張が `<script` を `<script nonce="…"` に置換する」契約**にすれば、
通常のブラウザ用の出力を汚さずに済む（`nonce` 属性は CSP が無ければ無害）。
この点は**実機で確かめるまで「そうなるはず」以上には言わない**。

## F5: 容量——バンドルは「全部入り HTML − テンプレート分」（実測）

| 入力 | バンドル | 全部入り HTML | 差（テンプレート分） |
|---|---|---|---|
| この skill の前 work のコミット（19 ファイル） | 3,496,478 B | 3,625,312 B | 128,834 B |
| rich work のコミット（20 ファイル） | 3,241,858 B | 3,368,692 B | 126,834 B |

テンプレートの内訳（合計 121,427 B）:

| ファイル | バイト |
|---|---|
| `app.js` | 77,988 |
| `style.css` | 20,393 |
| `ui.js` | 8,826 |
| `page.html` | 7,660 |
| `rich.js` | 6,560 |

**分離の効き方**: ビューア 1 本 ＋ バンドル N 本にすると、テンプレート分（約 127KB）が
**N 回ではなく 1 回**で済む。10 件のレビューを配るなら約 1.1MB の節約。
ただし**データ側が MB 単位**なので、**容量が分離の主な理由にはならない**——
主な理由は「エディタが扱う単位がファイルであること」。

**ビューア単体には落とし穴が 1 つ**: 現行は「rich の対象が無ければ `rich.js` を積まない」が、
**ビューアは何を開くか事前に分からない**ので、**`rich.js` を常に積む**しかない（+6,560 B）。

## F6: 参照専用は「積まない」で作れるか

現状、書き込みの導線は 2 か所に分かれている。

| どこ | 何 |
|---|---|
| `page.html` | 「レビューを開始 / 提出 / JSON を書き出す / 読み込む」のボタン、提出パネル、書き出しパネル、全体コメントの「コメントする」 |
| `app.js` | 行 / ファイルの `+` ボタンの生成、入力欄、返信、解決、提出の処理 |

`page.html` 側は**印で囲んで生成時に切り落とせる**（静的なので確実）。
`app.js` 側は**コードを外科的に削るのは危険**（依存が絡む）ので、
**描画時に導線を作らない**形にする。要件が求めているのは
「**導線が DOM に存在しない**」（AC10）なので、これで満たせる。

> つまり **HTML は積まない・JS は作らない**の二段で、
> 「開発者ツールで `hidden` を外せば戻る」形にはしない。
> **JS の本体は残る**ので、容量はほとんど減らない——この点は正直に書く（誇張しない）。

## リスク

- **R1（F1 から直結・この work の中心的な判断）**:
  `<script src>` で読むということは、**バンドルを実行する**ということ。
  「ビューアは信頼できる／データは信頼できない」という直感が成り立たなくなる。
  他人から受け取った `.dreview` を開くのは、**他人の HTML を開くのと同じ危険度**。
  → 既定でどうするかを decisions で決める。
  **［結末］この口は deliver 後に取りやめた（decisions D9）。**
  決め手は危険ではなく**決定性**——ビューアがファイル名を指すと、`.dreview` が複数あるときに
  どれを見ているのかが決まらない。口を持たないことで R1 は**解消**した。
- **R2**: `file://` は origin が opaque なので、`postMessage` の送り主を検査できない（F3）。
  検査は形だけになる。**受け取ったものは必ず `validate` を通す**。
  **［結末］一度撤去したが（D10）、ホストが再読み込みなしで差し替えられる価値のほうが
  大きいと判断して戻した（D11）。** R2 は**残る**——送り主は検査できないので、
  **形が合うかどうかだけ**で受け、必ず `validateBundle` を通す。
  ブラウザで直接開く分には投げ込む経路が無く、webview ではホストが親なので、
  実害のある経路は今のところ見当たらない。
- **R3（F4）**: VSCode の CSP まわりが**未検証**。実機で試すまで、契約は「たぶんこうなる」に留まる。
- **R4**: バンドルと `review.json`（`diff-review/2`）の**2 つの形式**ができる。
  片方だけ直す事故が起きうる。→ **バンドルは `diff-review/2` を内側にそのまま持つ**形にして、
  検証を 1 本で済ませる設計にする（design）。
- **R5**: ビューアは「どの差分でも開ける」ので、**`rich.js` を常に積む**（F5）。
  現行の「対象が無ければ積まない」との一貫性が崩れて見える。→ 文書で理由を書く。
- **R6**: 下書きの保存キーは差分の digest ごと（前 work）。バンドルを切り替えると
  下書きも切り替わる——これは**正しい振る舞い**だが、「消えた」と誤解されうる。→ design で見せ方を決める。

## 結論（design への申し送り）

1. バンドルは **1 ファイル**。`window.__DIFF_REVIEW_BUNDLE__ = <正規形 JSON>;` の形。
   **JS としても JSON としても読める**（F2 で 3 者すべて実測）。`U+2028`/`U+2029` は退避する。
2. ビューアの取り込み口は **4 つ**——埋め込み（現行） / `window.__…__`（`<script src>` かホストの注入） /
   `postMessage`（F3 で実測） / ファイルを開く（実行なし）。**どれも `validate` を必ず通す**。
3. **`<script src>` の自動読み込みをどう扱うかが、この work の中心的な判断**（R1）。
4. バンドルは `diff-review/2` を**内側にそのまま持つ**（R4）。検証を 2 本にしない。
5. ビューア単体は **`rich.js` を常に積む**（F5）。
6. 参照専用は **HTML を積まない ＋ JS が導線を作らない**の二段。**容量はほとんど減らない**（F6）。
7. VSCode の CSP は**未検証**。契約は最小（`<script` への nonce 挿入 1 か所）にして、
   実機で確かめるまで断定しない（R3）。
