# 決定記録: バンドルとビューアの分離

> autonomous モードのため、人間のゲートで確認するはずだった選択をここに残す。
> 「他の案」は**実際に検討したもの**だけを書く。

## D1: バンドルは「JS としても JSON としても読める」1 ファイルにする

- **決定**: `window.__DIFF_REVIEW_BUNDLE__ = <正規形 JSON>;\n`。前後は固定。拡張子は `.dreview`。
- **理由**: `file://` で隣のファイルを読める手段は **`<script src>` だけ**（`fetch`・XHR・
  モジュール import はすべて CORS で落ちる。research F1 で実測）。だからブラウザ経路を成り立たせるには
  **JS でなければならない**。一方、拡張（Node）と `check`/`list`（Python）は
  **実行せずに読めなければならない**——他人から受け取ったファイルを検証するのに実行は要らない。
  前後を固定すれば両立する（3 者で実測）。
- **他の案**: 純 JSON ＋ 読み込み用のラッパを別ファイルで出す →
  「差分と指摘を 1 ファイルに」という要望に反する（ファイルが 2 つに戻る）。却下。
- **代償**: 中身が「素の JSON ファイル」ではない。`jq` などにそのまま食わせられない。
  `check` / `list` が受けるので、実務上の不便は小さいと判断した。

## D2: バンドルは記録（`diff-review/2`）を**内側にそのまま**持つ

- **決定**: `review` キーに記録を丸ごと入れる。`target` が二重になるのを許す。
- **理由**: **検証を 1 本で済ませる**ため。バンドル用の検証と記録用の検証が分かれると、
  片方だけ直す事故が起きる（research R4）。既存の `validate()` をそのまま呼べる。
- **代償**: `target` の重複（数百バイト）。MB 単位のファイルでは無視できる。

## D3: `<script src>` の焼き込みは **`--load` を明示したときだけ**（→ **D9 で取り消し**）

- **決定**: `view` は既定で**どのバンドルも自動で読まない**。`--load <path>` を指定したときだけ
  `<script src>` を焼き込み、そのとき **CLI が警告を出す**。
  「ビューアの隣に決まった名前のファイルを置けば読む」形には**しない**。
- **理由**: `<script src>` で読むのは**そのファイルを実行する**こと。
  危ないのは「自動読み込みがあること」ではなく、**「他人がくれたファイルをビューアが勝手に実行すること」**。
  焼き込みを生成時の行為にすれば、指すのは**バンドルを作った本人**なので、新しい信頼境界が生まれない。
  一方「決まった名前のファイルを読む」形にすると、受け取った `.dreview` を置くだけで実行されてしまう。
- **他の案**: 焼き込みを一切やらない → ユーザの狙い（テンプレート HTML ＋ 差し替え可能な差分ファイル）が
  ブラウザ単体で成り立たなくなる。却下。
  既定で有効にする → 上の危険を既定にすることになる。却下。
- **代償**: ブラウザ単体で「差分ファイルを差し替えて見る」には、そのつど `view --load` を打つ必要がある。
  VSCode 拡張の経路（本命）では `postMessage` を使うので、この代償は効かない。
- **その後（D9）**: この代償の見積もりが甘かった。**deliver 後に取り消した**。下記 D9 を参照。

## D4: 参照専用は「隠す」ではなく「積まない / 作らない」の二段

- **決定**: `page.html` の書き込み導線を印で囲んで**生成時に切り落とし**、
  さらに `readonly` のとき **`app.js` が導線を作らない**。
- **理由**: `hidden` を付けるだけだと、開発者ツールで外せば戻る。
  配布物として「読むだけ」を名乗るなら、**出力に入っていない**ほうがよい。
  一方、`app.js` を外科的に削るのは依存が絡んで危険なので、そちらは「作らない」で満たす
  （要件 AC10 が求めるのは「**導線が DOM に存在しない**」こと）。
- **代償**: **容量はほとんど減らない**（実測 −2,256 B ＝ 0.1%）。
  「軽くなる」と書かないこと——目的は容量ではなく「書き換えて再配布されない」こと。

## D5: 取得元は `--from` 1 軸。従来フラグは残すが**併用は落とす**

- **決定**: `--from unstaged|staged|range|commit|github-pr` ＋ `--rev`。
  従来の `--unstaged` / `--staged` / `--range` / `--commit` は別名として残す。
  **両方を指定したら落とす**。
- **理由**: 取得元が増えるたびにフラグが増える形だと、覚えることが増えて使われなくなる。
  一方、既存の呼び出し（skill・スクリプト）を壊すのは論外なので別名として残す。
  併用でどちらかを黙って優先すると、**「指定したはずの差分と違うものが出た」**という
  気づきにくい事故になる。落とすほうがよい。
- **代償**: 同じことを 2 通りで書ける状態がしばらく続く。文書では `--from` を主に書く。

## D6: `--from github-pr` は**受け付けて落とす**

- **決定**: 選択肢として存在し、指定すると「まだ実装していません」と言って終了コード 1。
- **理由**: 黙って別の差分（未コミット）を出すのが最悪。
  選択肢に無いとエラーメッセージが「そんな値は無い」になり、**将来対応するのかどうかが伝わらない**。
  「ある。まだ動かない」が、いちばん情報量が多い。
- **代償**: 実装が無いのに名前だけある。テストで終了コードを固定してある。

## D7: `html` の出力が**バイト単位で変わる**ことを受け入れる

- **決定**: テンプレートに「ファイルを開く」「差分が無いときの案内」「`<script src>` の口」が入るので、
  既存の `html` 出力はバイト単位では変わる。**約束するのは意味の不変**
  （同じ差分から同じ画面が出て、同じ操作ができること）と、**既存 60 件のテストが通ること**。
- **理由**: design では「バイト単位で変わらない」と書いていたが、**実装したら成り立たなかった**。
  約束のほうを現実に合わせて直した（隠して「変わっていない」と言うより正直）。
- **代償**: 以前の出力と `cmp` で比べる運用があれば壊れる。`SKILL.md` に変更点を書いた。

## D8: 「ファイルを開く」を `<label>` から `<button>` へ（test 工程での修正）

- **決定**: `<label class="filebtn" for="file-import">` をやめ、
  `<button>` が `input.click()` を呼ぶ形にした。
- **理由**: `<label>` も `hidden` な `<input type=file>` も**フォーカスを受けない**ので、
  **`Tab` でどれだけ押しても到達できなかった**（実測: 20 回押しても届かない）。
  これは**前 work から存在していた欠陥**で（当時は「JSON を読み込む」）、
  この work の AC-I3（キーボードだけで完結）を実際に押して確かめて初めて出てきた。
- **代償**: なし（見た目は同じ、`.filebtn` の CSS は不要になったので削除）。


## D9: `<script src>` の焼き込み（`--load`）を**やめる**（D3 の取り消し・deliver 後）

- **決定**: `view --load` と `__BUNDLE_SRC__` の口を**まるごと削除**した。
  生成物はどのファイルも自動では読まない。ビューアへの取り込みは
  **ファイル選択 / D&D・埋め込み・ホストからの受け渡し**の 3 系統だけになる。
- **理由（利用者からの指摘）**: **ビューアが特定のファイル名を指すと、
  `.dreview` が複数あるときに「このビューアはどれを見ているのか」が決まらない。**
  D3 では危険（実行されること）だけを見ていて、**決定性**を見落としていた。
  配布物としての HTML が、隣に何が置かれているかで表示を変えるのは、
  この skill が守ってきた「同じ入力から同じ出力」と相容れない。
- **副次的な効果**: **実行を伴う経路が 1 つも無くなった**。
  「他人のバンドルを開いたら実行される」という注意書き自体が不要になり、
  SKILL.md の WARNING を NOTE に落とせた。研究で見つけた R1（research.md）は**解消**。
- **他の案**: ビューアに「読み込むファイル名」を引数で渡す（`?src=` など）→
  `file://` ではクエリを使っても `<script src>` を動的に足すことになり、同じ問題に戻る。却下。
- **代償**: ブラウザ単体で「ダブルクリックだけで開く」形は作れない。
  **1 回ファイルを選ぶ操作が要る**（`Tab` 9 回で到達・実測）。
  VSCode 拡張の経路（本命）では拡張が渡すので、この代償は効かない。
- **回帰の固定**: 生成物（`view` / `view --readonly` / `html` / `html --readonly`）に
  `<script src=` が出ないこと、`render_html` に `load_src` 引数が無いこと、
  `--load` が argparse に弾かれること、画面が外部スクリプトを読まないこと（実測）をテストにした。


## D10: 取り込み口を**手動と埋め込みの 2 つだけ**にする（deliver 後・利用者の指示）

- **決定**: `postMessage` の受け口と、生成物が読むグローバル変数（`window.__DIFF_REVIEW_BUNDLE__`）を
  **両方とも撤去**。取り込みは——
  1. **手動**: ファイル選択 / ドラッグ＆ドロップ
  2. **埋め込み**: `html` の出力（`#diff-data` / `#review-data`）、
     またはホストが組み立てた HTML の `#bundle-data`

  の 2 系統だけにした。

- **理由**: D9 で `<script src>` を落とした理由（**同じ HTML を開いたときに何が出るかが決まる**）を
  最後まで通すと、押し込み型の口も同じ性質を崩す——`postMessage` を受けると、
  同じ HTML を開いても**外からの操作で表示が変わりうる**。
  読む口と押し込み口の両方を持たないことで、
  **「その HTML の中身」と「人が選んだファイル」だけで表示が決まる**という一言に収まった。

- **ホストはどうするか**: `view` の出力に**空の `#bundle-data`** を最初から入れてある。
  ホストは `.dreview` を読み（実行せず）、このブロックにバンドルをそのまま書き込んで
  `webview.html` に渡す。**これは VSCode の webview の標準的な作り方そのもの**
  （`resolveCustomEditor` で初期 HTML を組み立てる）なので、拡張側の負担は増えない。

- **代償（正直に）**: **開いたあとに外から中身を差し替えられない**。
  ファイルが更新されたときに拡張が表示を更新するには、**HTML を組み立て直して渡す**ことになる
  （webview の再読み込み。スクロール位置と書きかけは失われる）。
  `postMessage` があれば部分更新できたが、その代わりに決定性を取った。
  なお**下書きはブラウザに差分ごとに保存されている**ので、再読み込みしても書きかけ自体は復元される。

- **私の説明の誤り**: 直前の回答で「口①を消せば手動＋埋め込みだけになる」と書いたが、
  `postMessage` を数え落としていた。指示はその誤った前提の上に出されたものなので、
  **文字どおりの指示（手動と埋め込みだけ）を優先**し、代償を上に明記した。
