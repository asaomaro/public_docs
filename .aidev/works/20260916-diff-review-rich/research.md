# 調査: オフライン・依存ゼロで rich diff とハイライトと文脈展開をどこまでやれるか

> **すべてこの環境での実測**（Python 3.11.15 / git 2.43.0 / Chromium 1194 ＋ Playwright 1.56.1）。
> 前 work（`20260915-pr-review-html`）の `research.md` の事実（`file://` の制約・決定論・性能）は
> 前提としてそのまま引き継ぐ。ここでは**この work で新たに必要になった事実だけ**を足す。

## 調査の問い

- Q1: 外部ツール（`mmdc` / `pdftotext` 等）はこの環境にあるか。前提にしてよいか。
- Q2: **PDF のテキスト**を Python 標準ライブラリだけで抽出できるか。日本語は出るか。
- Q3: **HTML の rich diff** を、スクリプトを実行させずに描画する手段はあるか（`file://` で動くか）。
- Q4: **CSV / TSV のセル単位の差分**を標準ライブラリで出せるか。
- Q5: **シンタックスハイライト**を正規表現ベースで実用になる粒度でやれるか。
- Q6: **文脈展開**のために両側の全文をどう取るか。埋め込むと**どれだけ重くなる**か。
- Q7: **mermaid** を自前で描くとしたら、どの図種が対象になるか（実際に使われているのは何か）。

## 判明した事実

- **F1: 外部ツールは 1 つも無い。** 実測: `mmdc` / `pdftotext` / `pdfinfo` / `qpdf` すべて `command -v` で不在。
  → **外部 CLI を前提にした設計は採れない**（あれば使う任意の最適化としてのみ成立する）。
  一方、標準ライブラリは `zlib` / `csv` / `difflib` / `html.parser` / `base64` /
  `xml.etree.ElementTree` がそろっている。

- **F2: PDF のテキストは標準ライブラリだけで取れる。** 実測: Chromium が出力した PDF
  （英数字＋日本語）から、`zlib` でストリームを展開し、**ToUnicode CMap の `beginbfchar` /
  `beginbfrange`** を読んでグリフ番号 → Unicode に変換したところ、
  `'Sample Report Hello PDF world 123 日本語の テ キ ス ト'` を復元できた。
  2 つ目の PDF からも `'… 456 …（変更）2 ペ ージ 目へ'` を取得。
  - **限界（設計に効く）**: 語間の空白は復元しきれない（`テ キ ス ト` のように割れる）。
    **ToUnicode を持たない PDF**（スキャン画像・一部の生成器）では**テキストが 1 文字も取れない**。
    → 「取れた場合はテキスト差分、取れない場合は理由を出す」の二段構えが要る。
  - ページ数は `/Type /Page` の出現数で数えられる（実測: 1 / 1）。

- **F3: HTML は `<iframe sandbox="" srcdoc="…">` で安全に描画できる。** 実測（`file://`）:
  srcdoc 内に仕込んだ `window.parent.document…` を書き換えるスクリプトは**実行されず**、
  親の表示は `safe` のまま。親から `contentDocument` を読もうとすると `(cross-origin)`
  （不透明なオリジンとして隔離されている）。コンソールにブロックのエラーが 1 件出るだけ。
  → **`sandbox=""`（すべて禁止）＋ `srcdoc`** が HTML rich diff の描画手段になる。

- **F4: CSV / TSV のセル単位の差分は `csv` ＋ `difflib` で出せる。** 実測:
  行を組（tuple）にして `SequenceMatcher.get_opcodes()` で対応付け、`replace` の組で
  セルを突き合わせると、`['1','りんご','3'] → ['1','りんご','4']` の **3 列目だけ**が変化と判定できた。
  行の追加・削除（`insert` / `delete`）も分離できる。

- **F5: 正規表現のトークナイザで実用の粒度に届く。** 実測: 1 本の正規表現
  （`comment` / `string` / `kw` / `num` / `name` の名前付きグループ）を `diff_review.py` の
  先頭 1200 字に当てて、コメント 6・文字列 10・キーワード 7・数値 4・識別子 24 を分類できた。
  - **行単位で当てる**ので、複数行にまたがる文字列（`"""…"""`）やコメントは**行をまたぐと崩れる**。
    → 状態（「いま複数行文字列の中か」）をファイル単位で持ち越す設計が要る。

- **F6: 両側の全文は git だけで取れる。** 実測: `git show HEAD:<path>`（コミット側）、
  `git show :<path>`（index 側）、作業ツリー側は**ファイルをそのまま読む**。
  - **埋め込みの重さ（実測）**: `HEAD~1..HEAD`（4 ファイル）で、差分データ JSON が **20KB** に対し、
    新側の全文は **68KB**。つまり**全文を無条件に埋めると差分データの 3〜4 倍**になる。
    → 無条件に全文を埋める設計は採れない。**ファイル単位の上限**（行数しきい値）か、
    **生成時のフラグ**で選ばせる必要がある。

- **F7: 自前で描く mermaid の対象は 2 種類で足りる。** 実測（このリポジトリの Markdown を走査）:
  使われているのは **`flowchart` / `graph`** と **`sequenceDiagram`** と **`stateDiagram-v2`**。
  - `flowchart` と `stateDiagram` は「ノード＋矢印」で同じ描き方に落とせる（層ごとに並べる）。
  - `sequenceDiagram` は参加者を列、メッセージを行にすれば素直に描ける。
  - それ以外（`gantt` / `erDiagram` / `classDiagram` / `pie` …）は**対象外にしてコードのまま出す**のが妥当。

## 実現性 / リスク

- **R1: 容量（最大のリスク）**。F6 のとおり全文の埋め込みは高い。**rich diff の機構**（描画コード）は
  対象が無ければ落とせるが、**文脈展開のデータは対象の有無で切れない**——展開は全テキストファイルが対象。
  → しきい値（行数）＋フラグで**払う量を選べる**設計にし、要件の「+15%」は
  **rich diff の機構に対する基準**として design で読み替える（`decisions.md` に残す）。
- **R2: PDF の不確実性**。ToUnicode を持たない PDF ではテキストが取れない（F2）。
  「ページ数だけ出して、テキストは理由付きで諦める」経路を最初から設計に入れる。
- **R3: ハイライトの行またぎ**（F5）。ファイル単位で状態を持ち越さないと、docstring の途中の行が
  文字列として色付かない。**差分は「連続しない行の集まり」**なので、
  **全文を 1 度トークナイズしてから行に切り分ける**のが正しい（差分行だけを個別に当てない）。
- **R4: mermaid の見た目**。自前描画は mermaid 本体の出力とは違う絵になる。
  「図として読める」ことを目標にし、**忠実な再現は狙わない**（design に明記する）。
- **R5: 画面の複雑化**。展開・rich/source・重大度・返信・説明の 5 つが同じ行の近くに増える。
  前 work のレビューで **Enter の横取り**が must になった教訓があるので、
  **キー割り当てを増やすときは既定操作を奪っていないかを毎回実測する**。

## 実装時の注意

- **ハイライトはファイル全文に対して行い、結果を行に切る**（R3）。差分行だけに当てない。
- **PDF は「取れない」が普通にある**（F2）。取れなかったことを画面に出す。黙って空にしない。
- **`sandbox=""` を外さない**（F3）。`allow-scripts` を足した瞬間に XSS の経路になる。
- **rich diff のデータも `<` の退避を通す**（前 work F6 の実測）。埋め込み口が増える分、
  退避を通す関数を 1 箇所に保つ。
- **`git show` はバイト列で受ける**（前 work D13）。テキスト判定は自前で行う（NUL を含むなら binary）。
- 展開で現れる行の**行番号は、ハンクの外側も含めて連番で正しく**なければならない（AC13）。
  ハンクヘッダの `old_start` / `new_start` から数えるのではなく、**全文の行番号**で持つのが安全。

## design への申し送り

1. **容量の払い方を決める**（R1）: 展開データのしきい値（例: 2,000 行）とフラグ（例: `--expand-max-lines`）。
   要件 AC9 の「+15%」は **rich diff の機構**に対する基準として読み替え、`decisions.md` に記録する。
2. **rich diff の同梱単位**（要件の未確定事項）: 形式ごとに切るか、rich 全体で 1 つか。
   実装量と容量の両方に効く——**形式ごと**にすると条件分岐が増え、**全体で 1 つ**にすると
   CSV しか無い差分でも Markdown の描画コードを積む。
3. **PDF は二段構え**（R2）: テキストが取れたら差分、取れなければページ数とサイズだけ＋理由。
4. **mermaid は 3 図種**（F7）: `flowchart` / `graph` / `stateDiagram` を「ノードと矢印」、
   `sequenceDiagram` を「列と行」。それ以外はコードブロックのまま＋理由。**忠実再現は狙わない**。
5. **スキーマ移行**（要件の未確定事項）: `diff-review/1` を読んだときの既定値は
   「重大度なし（`null`）」「説明コメントなし」。書き出しは常に `diff-review/2`。
6. 前 work の **`walkthrough.md` の「リスク / 確認したい点」**に挙げた CI 未搭載は、この work でも解消しない
   （スコープ外のまま）。
