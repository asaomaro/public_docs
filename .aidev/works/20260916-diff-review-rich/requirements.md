# 要件: diff-review-html に「読むための表示」と「レビューの語彙」を足す

## 背景 / 課題

`diff-review-html`（前 work `20260915-pr-review-html`）で、差分を読んで指摘を JSON で往復させる
最小の器はできた。実際に使うと、**読む側の負担**と**指摘の粒度**の 2 つが足りない。

- **読む側**: 色の付かない unified diff で、文脈は前後 3 行に固定されている。
  変更行の少し外を見たいだけで生成し直しになる。CSV・Markdown・HTML・PDF は
  「テキストとしての差分」しか出ないので、**表の 1 セルが変わった**ことや
  **見出しの構造が変わった**ことが読み取りにくい。
- **返す側**: 指摘に**重大度が無い**ため、直さないと着地できないものと好みの問題が同じ重みで並ぶ。
  AI が JSON を読んで直すときも、どこから手を付けるかを本文の語調から推測することになる。
  また、**差分の作者が「ここはこういう意図です」と添える場所が無い**——説明を指摘として書くと、
  未解決スレッドとして数えられてしまう。

## 目的 / ゴール

- 差分が**そのファイルの形で読めている**状態（コードは色が付き、表は表として、Markdown は
  描画された姿として、必要なら元のテキストとしても読める）。
- **見たいところまで文脈を広げられる**状態（生成し直さずに、押した分だけ前後が見える）。
- 指摘に**重大度という共通語彙**があり、人間も AI も「まず何を直すか」を JSON から機械的に決められる状態。
- **作者の説明と、レビュアーの指摘が混ざらない**状態。
- 上記を足しても、**単一 HTML・オフライン・追加依存ゼロ・決定論**という前 work の性質が壊れていない状態。
  とくに **rich diff の対象が無い差分では、その描画コードが生成物に入っていない**（容量を払わない）。

## ユーザーストーリー

- US1: レビューする人間として、コードに色が付いた差分を読みたい。
  なぜなら、構文の切れ目が見えると読み違いが減り、長い差分でも目が滑らないから。（受け入れ: AC1, AC2, AC3）
- US2: レビューする人間として、CSV や Markdown を**そのファイルの形**で見比べたい。
  なぜなら、テキスト差分では「表のどのセルが変わったか」「見出し構造がどう変わったか」が読み取れないから。
  （受け入れ: AC4, AC5, AC6, AC7, AC8, AC10）
- US3: レビューする人間として、変更行の前後をその場で広げたい。
  なぜなら、関数の頭やクラス宣言を見るためだけに生成し直すのは往復が多すぎるから。（受け入れ: AC11, AC12, AC13, AC14）
- US4: レビューする人間として、指摘に must / should / nit を付けたい。
  なぜなら、直さないと着地できないものと好みの問題を、受け取る側が区別できるから。（受け入れ: AC15, AC16）
- US5: AI エージェントとして、JSON から重大度と返信関係を機械的に読みたい。
  なぜなら、着手順を本文の語調から推測せずに決められるから。（受け入れ: AC16, AC17）
- US6: 差分の作者（人間または AI）として、**指摘ではない説明**を差分に添えたい。
  なぜなら、意図の説明を指摘として書くと未解決として数えられ、レビューの残件が濁るから。（受け入れ: AC19, AC20）
- US7: この skill を使い続ける人として、**軽いまま**でいてほしい。
  なぜなら、毎回のレビューで数 MB の HTML を開くことになると、そもそも開かなくなるから。（受け入れ: AC9, AC22）

## スコープ

### 対象

- **シンタックスハイライト**（生成時に行い、画面側でライブラリを読まない）。
- **rich diff**: CSV / TSV（表）、Markdown（描画・**mermaid**・**GitHub alert 記法**）、HTML（描画）、PDF（可能な範囲の要約）。
  **rich / source の表示切り替え**と、**対象が無ければ描画コードを含めない条件付き同梱**。
- **文脈の段階展開**（前後を押した分だけ広げる）と**ファイル全体の展開**。
- **重大度**（must / should / nit）をレビューコメントに持たせる。
- **コメント単位の返信**（返信への返信を含む）。
- **レビューの明示的な開始**（Start review）と、Approve / Request changes / Comment での提出。
- **作者の説明コメント**（レビューの提出対象に含めない注記）。
- スキーマの版上げと、旧版（`diff-review/1`）の読み込み互換。

### 対象外

- side-by-side 表示（unified のみ。前 work の `decisions.md` D8 を維持）。
- 画像・docx・xlsx の rich diff（今回は上記 5 形式のみ）。
- 構文解析器レベルの厳密なハイライト（**正規表現ベースの近似**で十分とする）。
- GitHub PR / API との連携（前 work のスコープ外を維持）。
- サーバ常駐・複数人同時編集・認証。

## 機能要件

- **F1 ハイライト**: 拡張子から言語を決め、生成時にトークン分割して span 化する。
  未対応の拡張子は素のまま出す。対応言語は「この repo とよくある構成で実際に出るもの」を最低限
  （py / js / ts / json / yaml / sh / css / html / md / sql）。
- **F2 rich diff（表）**: CSV / TSV を表として並べ、**変更されたセル**を見分けられるようにする。
- **F3 rich diff（Markdown）**: 見出し・段落・リスト・表・コード・引用・リンクを描画する。
  **GitHub alert 記法**（`> [!NOTE]` / `TIP` / `IMPORTANT` / `WARNING` / `CAUTION`）を専用表示にする。
  **mermaid** ブロックは図にする（生成時に SVG 化。できない環境ではコードのまま＋理由を表示）。
- **F4 rich diff（HTML）**: 描画結果を**スクリプトを実行しない形**で見せる。
- **F5 rich diff（PDF）**: 少なくともページ数とテキストの差分要約を出す。できない場合は理由を出す。
- **F6 条件付き同梱**: rich diff の対象ファイルが 1 つも無ければ、rich diff 用のコード・データを生成物に含めない。
- **F7 表示切り替え**: rich diff を持つファイルは rich / source を切り替えられる。
- **F8 文脈展開**: 各ハンクの上下に展開ボタンを置き、押すたびに N 行ずつ広げる。端に達したら消える。
- **F9 全展開**: ファイル単位で全行を一度に展開するボタンを置く。
- **F10 重大度**: コメントに `must` / `should` / `nit`（および無印）を持たせ、画面と JSON と `list` に出す。
- **F11 返信**: コメント 1 件ごとに返信でき、返信先を `in_reply_to` に正しく記録する。
- **F12 レビューの開始と提出**: 「レビューを開始」で下書き集合を開始し、Approve / Request changes / Comment
  のいずれかで提出する。
- **F13 説明コメント**: レビューの提出対象に含まれない「作者の説明」を、行 / ファイル / 全体に付けられる。
- **F14 スキーマ**: 上記を表現する `diff-review/2` を定義し、`diff-review/1` の記録も読める。

## 非機能要件 / 制約

- **単一 HTML・オフライン**（外部 CDN・外部リクエストゼロ）を維持する。
- **追加依存ゼロ**: 生成側は Python3 標準ライブラリのみ。**第三者ライブラリを同梱しない**
  （ハイライトも Markdown 描画も自前。mermaid だけは外部 CLI があれば使う任意の最適化）。
- **決定論**: 同じ入力から同じ HTML / JSON（時刻・乱数を混ぜない）。
- **UTF-8 / LF 固定**、日本語が化けない。
- **差分・コメント・rich diff の内容が HTML / JS として解釈されない**（前 work の性質を維持）。
- **容量**: rich diff 対象が無い差分で、生成物の増分を**現行比 +15% 以内**に抑える。
- Python3 標準ライブラリだけで完結し、`sh` / `pwsh` の二重実装を持たない。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開く / 閉じる: 展開ボタン・rich/source 切り替え・重大度の選択は、いずれもキーボードで
      到達でき、`Esc` で閉じられるものは閉じたときに値を失わない。
- [ ] AC-I2 確定 / 取り消し: 重大度を選んでからコメントを確定でき、取り消すと重大度ごと記録に残らない。
- [ ] AC-I3 キーボードだけで完結: 「行へ移動 → 前後を展開 → コメントを書く（重大度つき）→ 確定 → 提出」を
      マウス無しで通せる。
- [ ] AC-I4 フォーカスの行き先: 展開後もフォーカスが失われず（展開のきっかけになった位置に留まる）、
      コメント欄を閉じたら開いたボタンへ戻る。
- [ ] AC-I5 既存の操作を妨げない: 追加したキー割り当てが入力欄・ボタンの標準操作を奪わない
      （前 work のレビューで must になった Enter の横取りを再発させない）。
