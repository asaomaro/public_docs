## D1: 実行プロファイルは full、実行モードは autonomous

- **背景**: 9 件の機能追加（ハイライト / rich diff / 文脈展開 / 重大度 / 返信 / resolve /
  レビュー判定 / 説明コメント）。ユーザーの指示は「autonomous で」。
- **決定**: `aidev new diff-review-rich --mode autonomous --depends 20260915-pr-review-html`（profile full）。
- **理由・代替案**: 触るファイルは既存 7 本＋新規で 3 を大きく超え、**公開 I/F（JSON スキーマ）を版上げ**する。
  light の条件を 2 つ外れるので full 以外にならない。
- **影響**: 上流 4 文書の独立点検（`doccheck`）が必須。人間ゲートは置かない。

## D2: 9 件のうち 4 件は「対応済み / ほぼ対応済み」として実装しない

- **背景**: 指示は「既に対応出来ている場合は対応不要」。現物を読んで仕分けた。
- **決定**:
  - **7（resolve ボタン）は対応済み**——`templates/app.js` のスレッド見出しに「解決にする / 未解決に戻す」がある。追加実装しない。
  - **4（大きい差分の展開ボタン）は対応済み**——2,000 行超のファイルは既定で折りたたみ、
    クリックで描画する（`LAZY_LINE_LIMIT`）。ただし**「すべて表示」の導線を 3 の全展開と統合**する。
  - **6（返信）はほぼ対応済み**——スレッドと `in_reply_to` はあるが、返信ボタンが**スレッド単位**で、
    返信先は常に最後のコメントになる。**コメント単位の返信**に直す（差分は小さい）。
  - **8（Approve / Request changes）はほぼ対応済み**——提出時に 3 判定を選べる。
    **明示的な「レビューを開始」だけが無い**ので、それを足す。
- **理由・代替案**: 作り直すと退行の危険だけが増える。足りない差分だけを埋める。
- **影響**: requirements の AC14（大きい差分の折りたたみ維持）・AC17（コメント単位の返信）・
  AC18（開始）は「既存の上に足す」形の受け入れ基準になる。

## D3: 文脈展開のデータは「ファイル単位の上限つきで全文を埋める」。AC9 の +15% は rich 機構に対する基準と読む

- **背景**: `research.md` R1 / F6 の実測——差分データ 20KB に対し新側の全文は 68KB。
  展開は**全テキストファイル**が対象なので、rich diff のように「対象が無ければ落とす」ができない。
- **決定**:
  - 展開用のデータは **1 ファイルあたり `--expand-max-lines`（既定 2,000 行）まで**埋める。
    超えるファイルは展開データを持たず、画面で「このファイルは大きいので展開できません（生成時に
    `--expand-max-lines` を上げてください）」と出す。
  - `--expand-max-lines 0` で展開データを一切埋めない（前 work と同じ容量に戻せる）。
  - requirements AC9 の「**+15% 以内**」は、**rich diff の機構（描画コードとデータ）**に対する基準として読む。
    展開データは別枠で、上記のフラグで払う量を選べることをもって満たすとする。
- **理由・代替案**: 「全文を無条件に埋める」は容量が読めない。「展開のたびに再生成」はオフライン単一 HTML の
  前提に反する。gzip＋`DecompressionStream` で圧縮して埋める案もあるが、対応ブラウザの前提が増え、
  この work の主目的（読みやすさ）に対して割に合わない。
- **影響**: requirements の AC9 に読み替えを明記する。test は「rich 対象なしの生成物が +15% 以内」と
  「`--expand-max-lines 0` で前 work と同等」の 2 点で見る。

## D4: rich diff の描画コードは 1 ブロックにまとめ、対象が無ければブロックごと落とす（形式ごとには切らない）

- **背景**: requirements の未確定事項「条件付き同梱の単位」。
- **決定**: **重い処理（Markdown 解析・mermaid のレイアウト・PDF のテキスト抽出・CSV の対応付け）は
  すべて生成時の Python 側で行い、画面には「描けるだけの構造」だけを渡す**。
  画面側の rich 描画コードは「ノード木 → DOM」「表」「iframe」「img」の 4 つで、合わせて数十行に収まる。
  よって**形式ごとに切らず、rich 対象が 1 件も無ければ rich のコードとデータをまとめて落とす**。
- **理由・代替案**: 形式ごとに切ると条件分岐が 4 倍になり、得られる削減は数十行分しかない。
  **削減が効くのは「ブラウザに解析器を積まない」という設計そのもの**で、そこは形式によらず成立している。
- **影響**: `render_html` のプレースホルダに `__RICH_JS__` / `__RICH_DATA__` を足し、
  対象が無いときは空文字と `null` を入れる（AC9 の検証はこの 2 つの有無で行える）。

## D5: PDF は二段構え。取れなければ理由を出す

- **背景**: `research.md` F2——ToUnicode CMap があればテキストを復元できるが、無い PDF では 1 文字も取れない。
- **決定**: ①ページ数とバイト数は常に出す、②テキストが取れたら**行単位の差分**を出す、
  ③取れなければ「この PDF からはテキストを抽出できませんでした（ToUnicode を持たない可能性）」と出す。
- **理由・代替案**: 「取れないときに黙って空を出す」のが最悪。外部 CLI（`pdftotext`）前提は F1 で不可。
- **影響**: AC8 は「要約が出る **または** 理由が出る」の二択で満たす。

## D6: mermaid は 4 図種を自前で描き、忠実再現は狙わない

- **背景**: `research.md` F1（`mmdc` 無し）/ F7（実際に使われているのは flowchart / sequenceDiagram / stateDiagram）。
- **決定**: `flowchart` / `graph` / `stateDiagram(-v2)` を「ノードと矢印」、`sequenceDiagram` を「列と行」として
  **生成時に SVG を組み立てる**。それ以外の図種はコードブロックのまま＋「この図種は描画対象外」と出す。
  SVG は `<img src="data:image/svg+xml;base64,…">` で貼る（**img 内の SVG はスクリプトを実行しない**ので安全）。
- **理由・代替案**: mermaid 本体（1MB 超）の同梱は「第三者ライブラリを同梱しない」という要件に反し、
  容量の要求とも正面から衝突する。忠実再現を狙うと沼なので、**読める図**を上限とする。
- **影響**: 見た目は mermaid 公式と異なる。SKILL.md に明記する。

## D7: ハイライトは「全文を 1 度トークナイズしてから行に切る」

- **背景**: `research.md` F5 / R3——行単位に正規表現を当てると、複数行文字列やコメントの途中行が崩れる。
- **決定**: ファイルの**全文**に対してトークナイザを 1 回走らせ、結果を行ごとに切り分けて
  各差分行に `tokens: [[クラス, 文字列], …]` として持たせる。トークンが無い行は素のテキストで描く。
- **理由・代替案**: 差分行だけに当てる実装は安いが、docstring の中が壊れるのが目に見えている。
- **影響**: 全文の取得が必要（展開データと同じ経路を使えるので追加コストは小さい）。
  `--expand-max-lines 0` などで全文を持たないファイルは**ハイライトも行われない**（素のまま）。

## D8: スキーマは `diff-review/2`。`/1` は読めるが、書き出しは常に `/2`

- **背景**: requirements の未確定事項（旧記録の既定値）。
- **決定**: `threads[].kind`（`review` / `note`）と `comments[].severity`（`must` / `should` / `nit` / `null`）を足す。
  `/1` を読んだときは `kind: "review"` / `severity: null` を補う。書き出しは常に `/2`。
- **理由・代替案**: 版を上げずに任意項目として足すと、「無いのか、古いのか」が区別できない。
- **影響**: `check` は `/1` と `/2` の両方を受け、`/1` には「旧版です（読み込みは可能）」と注意を出す。

## D9: 説明コメント（note）は「提出されない・未解決に数えない」スレッドとして表す

- **背景**: 要望 9——レビュアーへの説明を指摘として書くと、未解決の残件が濁る。
- **決定**: `threads[].kind = "note"` を使い、①レビュー提出（Approve 等）の対象に含めない、
  ②`list` の既定の未解決一覧に出さない（`--notes` で出せる）、③画面では見た目を分ける（解決ボタンを出さない）。
- **理由・代替案**: 別の配列（`notes: []`）にする案もあるが、**位置（path / line / side）の表現が
  そっくり同じ**なので、同じスレッド構造に種別を持たせる方が検証もレンダリングも 1 本で済む。
- **影響**: `validate` は `kind` の値域と「note に `review_id` が付いていないこと」を見る。

## D10: subtask には分割しない

- **背景**: `aidev-30-tasks` 手順3の split 判定（autonomous は自律判定）。
- **決定**: 分割しない。単一 `tasks.md` ＋ 段階的なコミットで進める。
- **理由・代替案**: 生成側（Python）と画面（JS）とスキーマは**相互依存で、共同でしか検証できない**
  （rich の payload の形が両者の契約）。単独でデリバリ可能なピースが無いので、判定軸
  「そのピースは単独で検証・デリバリ可能か」に照らして分割の条件を満たさない。
- **影響**: 1 PR に収まる。前 work と同じブランチに積むので PR #21 が育つ（deliver で最終判断）。

## D11: T22（画面の受け入れ確認）は coding ではなく test 工程で消化する

- **背景**: 前 work D14 と同じ形（`aidev-30-tasks` 手順6 が `decisions.md` に 1 行残すことを求めている）。
- **決定**: T22 は coding では未チェックのまま残し、test 工程で消化する。

## D12: 実装は 3 モジュールに分ける（`diff_review.py` / `highlight.py` / `richdiff.py`）

- **背景**: design の「対象範囲」は `diff_review.py` 1 本を想定していたが、ハイライトと rich 化を
  同居させると 1 ファイルが 1,500 行を超えて読めなくなる（T5 は「新規モジュール可」としてあった）。
- **決定**: `highlight.py`（トークナイザ）と `richdiff.py`（CSV / Markdown / mermaid / HTML / PDF）を分ける。
  どちらも標準ライブラリのみで、CLI は持たない（`diff_review.py` から呼ばれるだけ）。
- **理由・代替案**: 責務が明確に割れており、テストも別々に書ける。1 本に押し込む理由が無い。
- **影響**: `SKILL.md` の「ファイル」表に 2 本を追記した。

## D13: ハイライトは `--expand-max-lines` の制限を受けない（cross 点検での修正）

- **背景**: D7 と SKILL.md は「上限を超えるファイルはハイライトもされない」と書いていたが、
  実装はハイライトを続けていた（cross 点検で実測）。
- **決定**: **実装を正**とし、文書を直した。上限が落とすのは**展開データ（全文ぶん）だけ**で、
  ハイライトは差分行にしか乗らないので残す。
- **理由・代替案**: 容量の問題は全文の埋め込みにあり、トークンは差分行ぶんしか増えない。
  大きいファイルだけ色が消える方が、利用者にとって不可解。
- **影響**: `SKILL.md` の 2 箇所を修正。D7 の記述はこの D13 が上書きする。

## D14: 差分行のトークンを展開データと二重に持たない（test ラウンド 1 で気づいた容量の無駄）

- **背景**: 受け入れ確認の途中で生成物の大きさを測ったところ、このリポジトリ自身の差分で **2.49MB**。
  内訳を見ると、**差分行の `tokens`** と **展開データの `tokens`** が同じ配列を 2 回運んでいた。
- **決定**: 展開データが同じ側の全文トークンを持っているなら、**差分行にはトークンを付けない**。
  画面は「行が持っていればそれ、無ければ展開データから行番号で引く」規則で描く
  （生成側 `attach_tokens` と画面側 `tokensFor` が対になる）。
- **理由・代替案**: 展開データを素のテキストにする案もあるが、展開して現れた行だけ色が消えて不自然。
  重複を外すほうが、見た目を保ったまま容量だけ落とせる。
- **影響**: **2.49MB → 1.86MB（−25%）**。テストは「新側の行はトークンを持たないが、それでも引ける」ことを
  検査する形に変えた（画面と同じ規則をテスト側にも置いた）。
