# 軽量 SDD フレームワーク（sdd-mini）方針

> 講習で SDD を説明し、受講者が手を動かすための自作フレームワークの設計方針です。
> 実物は [`sdd-mini/`](sdd-mini/)。

---

## 大原則

**主役は SDD の理解であって、フレームワークの習得ではない。**

覚えることを**5つのコマンドだけ**に絞る。フレームワーク自体の使い方に説明が要るなら、
それは教材として失敗している。

一方で、**機能を削ったせいで基本的なことがうまく回らない、という作りにはしない。**
少ないのは段の数と仕組みであって、各段の中身ではない。

---

## なぜ既存の SDD ツールをそのまま使わないか

SDD ツール（Spec Kit など）は CLI の導入が要る。これが講習で2つの問題を起こす。

| | CLI を持つツール | sdd-mini |
|---|---|---|
| 導入 | CLI インストール（Python 環境等） | **Markdown を5枚置く** |
| 講義中の実習 | 環境差で詰まる → デモ主体になりがち | 全員が手を動かせる |
| **持ち帰って宿題** | **各自の環境構築が壁** | **○** |
| 講習後に実務で使う | 別途導入が要る | そのまま自分の PJ に置ける |

**3行目が効く。** 「仕様駆動で小機能を1つ作ってくる」を宿題にしたとき、
受講者が自席で CLI を入れ直すところで脱落する。宿題が回らなければ SDD は「見た」で終わる。

また、プロンプトファイル（`.prompt.md`）は「**定型プロンプトを自分で書く**」仕組みなので、
組み込みスラッシュコマンドを習った後の自然な続きになる。
**「また新しいツールが出てきた」ではなく「習った仕組みで SDD が組める」**に着地する。

> SDD は**手法であってツールではない**——これを受講者が自分の手で実証する形にしたのが sdd-mini。

### 既存ツールを否定するものではない

フェーズの語彙は一般的な SDD ツールに揃えてある（Specify → Plan → Tasks → Implement）。
講習後に本家を触っても**そのまま転移する**。「軽い方で概念を掴み、必要なら本家へ」の順にする。

## 設計判断

### 1. コマンドは5つ

| コマンド | 段 | 出力 |
|---|---|---|
| `/sdd-specify` | 何を作るか | `.sdd/<機能名>/spec.md` |
| `/sdd-plan` | どう作るか | `.sdd/<機能名>/plan.md` |
| `/sdd-tasks` | 手順に割る | `.sdd/<機能名>/tasks.md` |
| `/sdd-implement` | 作る | コード |
| `/sdd-verify` | 確かめる | `spec.md` のチェックが埋まる |

一般的な SDD ツールの4フェーズに **`verify` を1つ足した**。理由は次項。

### 2. implement と verify を分ける（最重要）

4フェーズだと、実装した本人がその場で「受け入れ条件を満たしました」と宣言する形になる。
**書いた文脈がそのまま合否を出す**ので、確かめたことにならない。

そこで検証を独立させ、次を課している。

- `/sdd-implement` は**受け入れ条件のチェックを触らない**。付けるのは `/sdd-verify` だけ。
- `/sdd-verify` は条件ごとに**根拠**（テスト結果／読んだコードの該当箇所）を示す。
  根拠を示せない条件は**満たしていない扱い**。
- 満たさなかった条件は、原因（実装不足／条件が曖昧／条件が誤り）で仕分けて**戻り先を示す**。

段は1つ増えるが、**これが無いと「確かめた」が成立しない**ので入れた。
「少なくする」は「基本が回らなくてよい」ではない。

### 3. 状態管理を持たない — チェックリスト3つで足りる

`state.yml` も進捗ファイルも CLI も持たない。

| 見るところ | 何が分かる |
|---|---|
| `.sdd/<機能名>/` にあるファイル | どの段まで進んだか |
| `tasks.md` のチェック | 実装の進み |
| `spec.md` の受け入れ条件のチェック | **何が確かめ済みか** |

**受け入れ条件のチェックが最後に結果表になる**のがこの設計の要。
仕様書が検証記録を兼ねるので、別のレポートを作らずに済む。

状態管理の仕組みを見せると、受講者の関心が「仕組みの使い方」に逸れる。
SDD の骨格は「**段が分かれ、各段の成果物が次段の入力になる**」であって状態管理ではない。

### 4. ゲートは「AI が止まる」ことで表現する

各プロンプトの末尾に「ここで止まる」節を置き、AI が次に進まずユーザーの判断を待つ。

**ゲートを機械に検査させない。** 検査させると受講者は「通った/落ちた」を見るだけになる。
自分で読んで判断する行為そのものが体験の中身なので、そこを自動化しない。

> 講習の後半の背骨が「**検証点の上流化**」（素直な指示 → plan → SDD）なら、
> sdd-mini はその終着点で、**止まる回数の多さがそのまま検証点の上流度**になる。

### 5. 前提チェックと対象選択はプロンプトの文章で行う

各コマンドは `.sdd/` を見て対象を自分で決め（フォルダが1つならそれ、複数なら
その段の入力があって出力が無いもの）、前提が無ければ止まって前の段を案内する。

CLI のガードは持たない。順序が守られる保証は無いが、**守られなかったときに何が起きるかを
体験させる**方が教材としては価値がある。

### 6. 戻る道を各段に書く

一方通行にしない。「後ろの段で前の段の誤りに気づくのは正常」を各プロンプトに明記し、
戻り先（ほとんどは `/sdd-specify`）と、戻ったときに古くなるファイルの扱いを書いてある。

**SDD の値打ちの半分は「戻れること」**なので、ここは削らない。

### 7. instructions を1枚添える

「**呼び出して使う手順**（プロンプトファイル）」と「**常に効く規約**（instructions）」の
区別が、1つの実習の中で対比できる。`/sdd-plan` `/sdd-implement` `/sdd-verify` が
これを読む作りにしてある。

サンプルは**空欄ではなく実際に使える内容**で書いた。空のテンプレートを渡すと
「何を書く場所か」が伝わらず、結局書かれない。

## 分量の考え方

**行数の上限は決めない。** 削るために内容を落とすと、削った先で基本が回らなくなる。

判断基準は次の2つ。

1. **その節が無くても同じ結果になるか。** なるなら削る。
2. **受講者が読まずに使えるか。** プロンプトは AI が読むもので、受講者が
   熟読する前提にはしない。読まないと使えない作りなら、それは説明が足りていない印。

コマンドを増やしたくなったら、**まず既存のどれかに畳めないか**を先に考える。
`verify` は畳めなかった（畳むと「作った本人が合否を出す」になる）ので足した。

## 一周した先に何が起きるか（発展・中堅向け）

sdd-mini はガードと記録を持たない。**続けて回すと必ず次が起きる**ので、
最後に「これを続けるとこうなる」と道標だけ示す（実装は見せない）。

| sdd-mini に無いもの | 続けると起きること | 実務では何で塞ぐか |
|---|---|---|
| 承認の記録 | 誰がいつ何を通したか消える。手戻りが測れない | 承認をイベントとして記録する |
| 順序の強制 | spec を飛ばして implement する日が来る | 前提を機械的に検査する |
| 規約が守られたかの検証 | instructions に書いても守られない日がある | 検査を CLI/フックに降ろす |
| 複数機能の把握 | `.sdd/` が増えると今どこか分からなくなる | 横断ステータス |
| 効果の検証 | 規約を足しても、効いたか分からない | 指標を取り、前後で比べる |

> **この表が「ハーネスエンジニアリング」の入口。**
>
> 順序が大事。**先にガードを見せると、まだ経験していない痛みへの処方箋にしか見えない。**
> 一周して足りなさを感じた直後だから、必要性として理解される。

## 講習で使うときの想定

- **題材は継続プロジェクトに小機能を1つ足す**。新しい題材を作ると文脈説明に時間を取られる。
  大きさは **画面1つ・触るファイル1〜2枚**が目安。
- 完成例（`example/`）は**別題材**にしてある。実習・宿題のネタバレを避けるため。
- **講義で全段をやる枠が無いなら、`/sdd-specify` の1段だけを踏ませる。**
  仕様の段階で気づく体験が SDD の全部なので、そこだけ確実に取り、残りは宿題に回す。

### 拾うべき発言

実習中に出たら**必ず全体に共有する**。SDD の値打ちがそこに出ている。

- 「受け入れ条件を書こうとしたら、決まっていないことに気づいた」← **最重要**
- 「やらないことを書いたら、話が早く終わった」
- 「plan の触るファイルが思ったより多かった」＝仕様が大きすぎたサイン
- 「実装したら仕様の方が間違っていた」＝仕様は不変の正解ではない、という学び

---

## 保守方針

- **これは 2026-08 時点のスナップショット**として扱う。SDD の考え方は変わらないので、
  最新のツール事情に追随させる必要はない。追随させ始めると教材が肥大する。
- 直すのは「**基本が回らない**」が見つかったときだけ。機能追加の要望では直さない。

---

## 未確認事項

- **プロンプトファイルの frontmatter キー**（`mode` / `description`、instructions の `applyTo`）は
  ツールのバージョンで変わりうる。**配布前に実機で1度確認すること。**
  frontmatter が無視されても本文だけで動くように書いてあるので、最悪でも壊れはしない。
- `/` 候補にプロンプトファイルが出るには設定の有効化が要る場合がある（受講者環境での事前確認事項）。
