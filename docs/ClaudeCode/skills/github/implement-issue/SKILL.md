# Implement Issue

issueの内容を読み取り、コードベースを調査したうえで実装方針をユーザーと確認してから実装を進める。

## ステップ1: issue番号の特定

ユーザーがissue番号を明示した場合はそれを使う。

指定がない場合は現在のブランチ名から取得する:

```bash
git branch --show-current
```

ブランチ名のパターン: `{prefix}/issue-{番号}`（例: `feature/issue-5`、`fix/issue-12`）

正規表現 `/issue-(\d+)/` で番号を抽出する。ブランチ名から番号を特定できない場合はユーザーに確認する。

## ステップ2: issueの内容取得

```bash
gh issue view {番号} --json number,title,body,labels,comments
```

タイトル・本文・ラベル・コメントを読み込む。

## ステップ3: コードベースの調査

issueの内容から変更が必要な箇所を特定し、関連ファイルを調査する。調査の観点:

- キーワード（コンポーネント名・関数名・ファイル名など）で検索して対象ファイルを絞り込む
- 変更箇所の現在の実装を確認する
- 類似の実装パターンがあれば参照する（一貫性維持のため）

## ステップ4: 実装方針の提示とユーザー確認

調査結果をもとに以下をユーザーへ提示する:

```
【issue #N: タイトル】

概要: (1〜2行でissueの要旨)

対象ファイル:
- path/to/file.tsx  ← 変更内容の説明
- path/to/other.ts  ← 変更内容の説明

実装方針:
(具体的に何をどう変更するかを箇条書きで)
```

### 規模判定と次のアクション

**軽微（目安: 1〜3ファイル・変更量が少ない）の場合:**  
提示後に「軽微な対応です。すぐに実装に移りますか？」と一言確認し、承認を得たら即実装する。

**中程度〜大規模の場合:**  
実装計画を提示してユーザーの承認を得てから実装を開始する。

## ステップ5: 実装

承認後、issueの内容・実装方針・プロジェクトの既存パターンに従って実装する。
