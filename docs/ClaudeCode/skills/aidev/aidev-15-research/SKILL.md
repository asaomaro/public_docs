AI 開発ワークフローの **research（事前調査）工程**（任意）。
design を書く前に、既存コード・外部情報・実現性を調査し、不確実性を事実で解消する。
手戻り（誤った design → 差し戻し）の予防が目的。

**開始前に共通プロトコル `../aidev-00-start/protocol.md` を読み、その規約に従うこと。**

## 位置づけ

- 任意工程（番号末尾5、requirements と design の間に差し込む）。毎回は不要。
- 起動経路は2つ（protocol.md「4.5」）: ユーザー指定、または requirements 終了時の AI検知＋推奨。
- 重く対話の少ない調査が多いため、サブエージェントへの委譲（protocol.md「2.6」）と好相性。

## 起動判定（検知ロジック）

requirements 終了時（requirements 工程の終了ゲート）に、**protocol.md「4.5」の5条件**の
いずれか1つ以上に該当したら research を発火対象とする。

> **条件の本文はここには置かない。** かつてここと `protocol.md`・`aidev-10-requirements` の
> 3箇所に写しており、UI の条件をここだけに足した結果、**判定する側（requirements 終了時）に
> 届かず一度も発火しなかった**。UI の条件で来たときの進め方は下記「UI の規範」。

- **interactive**: 上記検知時、遷移ゲートに `承認して research(任意) を挟む`（推奨）を理由付きで加える。却下されれば design へ直行。
- **autonomous**: 上記検知時、**推奨ではなく自動で実施**する（protocol.md「10.」）。いずれにも該当しなければスキップして design へ進む。

## 前提

- `requirements.md` が存在すること。

## 入力

- 対象フォルダの `requirements.md`（特に「未確定事項」）。
- 既存コード、外部ドキュメント、PJ ルール。

## 出力

対象フォルダに `research.md` を生成する（**design と coding の両方の入力になる**）。

- **design 向け**: 設計判断（how）の材料となる事実。
- **coding 向け**: 実装の起点となる**実装アンカー**（`file:line` / シンボル名）と、コードに書かれていない注意点。
  実装工程が同じ探索をやり直さずに済むことが、この工程の回収ポイントの1つ
  （中断からの再開・test/review からの差し戻しで特に効く）。

## 手順

1. protocol.md「1. 対象作業の特定」に従い対象フォルダを確定。
   `aidev guard research` で前提を検査し、`aidev event research start` を記録する（exit≠0＝未充足。start が無いと `verify --strict` が落ち、ts は後から復元できない）。
2. 調査すべき問い（unknowns）を列挙する。典型例:
   - 既存コードの実装把握 / 影響範囲（どのコードが対象挙動を担うか、変更が波及する箇所）
   - **出力先の仕様（生成・変更する対象のスキーマ・型・フォーマット・既存実装）**。
     成果物が既存の型/スキーマに準拠する必要がある場合、その定義を必ず読む
     （外部情報源だけでなく、PJ 内の出力先仕様を確認しないと後段で手戻りになりやすい）。
   - 技術的実現性（API・ライブラリで実現可能か）
   - **UI の規範**（利用者が操作する部品を作るとき。**プロトコルや既存コードと同じ重みで調べる**）:
     - **確立したパターンは何か**（WAI-ARIA APG の該当パターン・OS のネイティブ部品・
       広く使われている実装が 2〜3 個）。**開く / 確定 / 取り消し / キーボード / フォーカスの行き先**を、
       それぞれがどう決めているかを並べる。
     - **食い違うなら、どちらを採るか理由を書く**（この画面に固有の事情があるなら明記する）。
     - 調べずに作ると test も review も通ったまま deliver 後に作り直しになる（実例は DESIGN「6.」）。
   - requirements の未確定事項のうち、調査で解消すべきもの
   - **実装の起点はどこか**（変更・参照することになる具体的なファイル / シンボル）。
     位置が特定できたものは「実装アンカー」として残し、coding が同じ探索をやり直さずに済むようにする。
3. 各問いを調査し、**事実**で答える（推測と区別する）。重い調査はサブエージェントに委譲してよい。
   - 委譲する場合、**探索の過程（空振りの検索結果・無関係なファイルの中身）は持ち帰らず、
     根拠付きの結論だけを `research.md` に残す**。後続工程のコンテキストを汚さないことがこの委譲の主目的。
4. 下記テンプレートに沿って `research.md` を記述する。設計判断（how）は design に回す。
   既存構造・呼び出し関係・影響範囲は、明確になるなら mermaid で図示する（protocol.md「9.」）。
   - **全ての事実に根拠（`file:line` / シンボル名 / 出典）を添える**。この文書は下流（design → tasks → tasks → coding）で
     要約を重ねられるため、後続工程が記述を疑ったときに**一次資料へ戻れること**が唯一の保険になる。
     「要約」ではなく「**索引付き要約**」にする。
   - 記述は**変更前のスナップショット**である。「判明した事実 / 実装アンカー」（現状）と
     「design への申し送り」（変更後の想定）を混ぜない。
5. protocol.md「3. 工程終了プロトコル」に従って終了する（次工程: `design`）。

## research.md テンプレート

```markdown
# 調査: <タイトル>

## 調査の問い
- Q1: <明らかにしたいこと>

## 判明した事実
- F1: <Q1 に対する事実。根拠（ファイル/行・出典）を添える>

## 影響範囲
- <変更が波及する箇所・関連コンポーネント>

## 実現性 / リスク
- <技術的に可能か。制約・懸念>

## 実装アンカー
<coding の起点。位置が特定できたものだけを書き、特定できなかったものは「未特定」と明記する>
- A1: <何をする箇所か>（`path/to/file.ts:120` `symbolName`）— <そこに何があるか>
- A2: <何をする箇所か>（未特定 — coding 側で探索が必要）

## 実装時の注意
<コードを読んでも分からない / 読み落としやすいこと。design には載らないが実装者が知りたいこと>
- <触ってはいけない箇所とその理由 / 暗黙の前提 / 周辺の慣習 / 踏みやすい罠>

## design への申し送り
- <設計時に踏まえるべき点。残った未確定事項>
```

## 完了の目安

- requirements の「調査で解消すべき未確定事項」が事実で埋まっている。
- **UI を作る work では、確立したパターンとの突き合わせが済んでいる**
  （requirements の「相互作用の受け入れ基準」に答えが出せる状態になっている）。
- design が誤った前提で書かれるリスクが下がっている。
- 実装の起点が「実装アンカー」として特定できている（**特定できなかったものは「未特定」と明示**されている。
  空欄にすると coding 側が「調査済みで対象なし」と誤読する）。
