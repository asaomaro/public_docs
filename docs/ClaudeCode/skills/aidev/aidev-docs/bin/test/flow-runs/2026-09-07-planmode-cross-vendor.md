## 1. 文書は実態に追いついているか

**外部製品の事実を一次資料で取り直した**（issue とベンダー文書）。plan モード自体は Claude Code /
Codex CLI / Copilot CLI / Copilot（IDE）のどれにもある。分かれるのは**エージェント側に入口があるか**で、
入れるのは **Claude Code の主エージェントだけ**。Codex は要望（openai/codex#11180）が OPEN のままで、
その要望者の用途が「skill がエージェントを plan モードへ入れたい」＝ aidev とまったく同じだった。
Copilot（IDE）は人がモードを選ぶだけで、しかも**人が切り替えてもエージェントに伝わらない**不具合が複数 OPEN。
Copilot CLI だけ第三の道があり、起動時の `--plan --mode autopilot` / `COPILOT_PLAN_THEN_AUTOPILOT` で
**ハーネスが plan モードで始めさせられる**——ただし**セッション単位**で、aidev の判定は工程単位なので粒度が合わない。

**古びた記述が 1 件見つかった**: `aidev-docs/README.md` の「Copilot CLI には plan モードが無い
（github/copilot-cli#934）」は、**#934 が close され 2026-01 に載った**ので誤り。
**外部製品の事実を根拠に書いた行は腐る**——根拠の issue 番号を残していたから追えた。今回も番号を残す。

食い違いは**正典の置き場**にも出た。サーフェス別の一覧を正典（`protocol-autonomous.md`）に書くと
「判定条件の正典は 1 箇所」に反するので、**一覧は `README.md`・正典には基準の読み替え方だけ**に割った
（入口が無ければ `guard` の促しは**人への依頼文**になり、従えなくても工程の失敗ではない）。

## 3. 実走（サブエージェント）

テスト PJ（`scratchpad/pjxvendor`・`mode: autonomous` / `humanGates: [design]`）で
`requirements → design → tasks` の 3 工程を 1 本完走。`verify --strict` は exit 0、`doctor` は `fail=0`。
`guard design` で plan モードの促しが出て、`guard tasks` では出ない（`has_approver()` どおり）ことも確認できた。

**このゲートを選んだ理由**: サブエージェントには `EnterPlanMode` / `ExitPlanMode` が渡らないので、
**サブエージェント自身が「入口の無いサーフェス」そのもの**になる。今回の改修は入口が無い側の
振る舞いを決めるものなので、**射程の外どころか、いちばん当てになるゲート**だった。

**実走が改修の穴を 1 つ突いた（修正済み）**。入口の無い実行主体を「Codex CLI・Copilot」とだけ書いたため、
**サブエージェントが自分を該当と読み取れなかった**——`README.md` のサーフェス表で Claude Code 行の判定が
「入れる」で、実態（サブエージェントは入れない）は**行末の括弧の中**にしかなかったので、
「表の判定列だけ見て閉じると自分の話ではないと読み違える」と報告された。
分かれ目は製品ではなく**実行主体**なので、**表を主エージェント／サブエージェントの 2 行に割り**、
正典側にも「Claude Code でもサブエージェントは入口が無い側」を明記した。
（結論自体は 2 ステップで一意に決まっており、`protocol-autonomous.md` の「委譲で代用しない」が
「plan モードを持つ主エージェントに投げ直す」という誘惑も塞いでいた、との報告。）

**CLI の不具合は見つからなかった**。`.claude/skills/` 配下の差分は 0 件。

**射程の外に 1 件残った（この改修の対象外・要判断）**: `humanGates` が要求する人間承認を、
**人間に到達できない実行主体がどう扱うか**が文書に無い。`aidev-00-start` は「人間がいない起動では
確認できない」を `new` より前の判定についてだけ規定しており、**ゲート側の規定が無い**。
`aidev approve design` は無言で通る（人間承認の有無は第二層から観測できない）。
実走は「自動承認として記録し `decisions.md` に残す」と決めたが、**それは文書から導いた結論ではなく
自分で埋めた穴だ**と申告している。決めるべき論点として残す。

### 独立監査（もう 1 本のサブエージェント）

差分だけを渡して読ませた。**must 4 件・should 5 件・nit 8 件**が出て、**すべて自分が入れた欠陥**だった。
`must` と `should` は全件直した（この記録は修正後の状態）。

- **[must] 同じファイルの 24 行下に、直したはずの記述が残っていた**——`DESIGN.md` は
  「Copilot CLI には無い（#934）」を 2 箇所に書いており、**README だけ直して DESIGN を取り残した**。
  同一ファイル内の正面衝突を、自分では見つけられなかった。**同じ事実を 2 箇所に書いたのが原因**。
- **[must] 否定したはずの軸が正典に残っていた**——`protocol-autonomous.md` の別の箇条書きが
  「**持たない環境**は README の表」のままで、新しい正典では**持たない環境は空集合**になる。
  Codex / Copilot のエージェントはこの行で「自分は持っている」と判断し、フォールバックに到達しない。
  **教訓として「軸を取り違えていた」と書いたその軸が、同じ改修の中に残っていた。**
- **[must] 「ここに写さない」と宣言した 18 行下に規則を写していた**——しかも**強さが食い違った**
  （正典「従えなくても失敗ではない」／写し「既定にする」）。README は**事実の一覧**に戻した。
- **[must] L9 の語彙を足し忘れた**——`PMKEY` に新しい軸の語（`承認を挟` / `人への依頼`）が無いので、
  **今回導入した軸の写しは機械には一件も見えなかった**。監査が工程 SKILL に写しを仕込んで実証した。
  `lint-docs.sh` のコメント自身が「改修のたびに語彙を足す。足さないと新条件の写しは全部素通りする」と
  警告している、まさにその形。語彙を足し、**同じ仕込みで NG が出ることを確認**してから戻した。
- **[should] `RET_OK` に他社の `` `/plan` `` を足したのは射程が広すぎた**——`RET_OK` は**行全体**への
  `grep -vE` なので、その行の `spec.md` / `plan.md` まで免除される（監査が再現した）。
  このリポジトリの流儀どおり `lint-docs.allow` の `L10:` に**理由つきで 1 行ずつ**登録し直した。
- **[should] 「人が切り替えるものだけ」が Copilot CLI の起動時強制を否定していた**（2 箇所）。
- **[should] 同じ issue（microsoft/vscode#312668）を 2 つの主張の根拠にしていた**。題名どおり
  **承認は済んでいる**ので「承認者がいなかった」事例ではない。旧記述の根拠づけを直した。
- **[should] 「`README.md` の表」が指す表が 2 つになった**（フォールバック表とサーフェス表）。名前で呼び分けた。
- **[nit]** HEAD 比較は `harness_rev` が実際に読む **tree hash** に合わせ（docs 全体を持つ木では
  無関係なコミットでも HEAD が動く）、**両端が取れたときだけ**言うようにした（片側が空の偽 NOTE を監査が再現）。
  終了コードへの影響が無いことは監査が骨組みを切り出して確認済み。

**残した指摘（この改修の対象外・別途）**: `lint-docs.allow:56` の L9 免除が `bin/README.md` の
巨大な `guard` 行を丸ごと隠しており、今回そこに書き足した記述も L9 から永久に見えない。
免除キーの射程を絞る話で、今回の軸とは別の改修。日付の無い外部事実（Spec Kit / Kiro 対応表など）が
まだ残っている点も、腐り方は同じなので同様に別途。
