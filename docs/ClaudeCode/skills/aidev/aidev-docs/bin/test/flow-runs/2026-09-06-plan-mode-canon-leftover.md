読み直して見つけた。

```

  …（同じセルの後半）…
**見るのは「その工程に承認者がいるか」（`has_approver`）で、`mode` そのものではない**
```

**同じセルの中で前半と後半が矛盾していた。** 後半が正しく、前半の括弧が `d0f5ed6` 時点のまま。
セルを頭から読むと、`humanGates` の部分自律で「促しは出ない」と読める。

対応は**括弧の削除のみ**。条件は同じセルの後半（`has_approver` / `light` の扱い）が
正確に説明しているので、情報は落ちない。**ここに条件を書き直さない**のが今回の趣旨と整合する

### なぜ L9 が捕まえなかったか

L9 の対象は `runtime_docs`（`aidev-00-start/*.md`）と `aidev-*/SKILL.md` で、
**`aidev-docs/bin/README.md` は範囲外**。

対象を工程 SKILL に絞ったのは意図的な判断（`profile: light` 等の正当な言及が 13 ファイルあり、
全部を弾くと誤検知だらけになる）なので、**この判断自体は変えない**。
ただし「条件の写しは工程 SKILL にしか生えない」という前提は今回崩れた。
`bin/README.md` は CLI の仕様を説明する場所なので条件を書くこと自体は正当で、
**正当な記述が古くなる**という別の型の欠陥である。L9 の拡張では捕まえられない
（`bin/README.md` の条件記述を一律に禁じることはできない）。

## 3. 実走（サブエージェント）

### 検証できたこと

正しい 3 条件を、この行だけから導出した:

1. 工程が `spec` / `design` であること
2. **その工程に承認者がいること（`has_approver`）**——`humanGates: [spec]` の部分自律も
   「承認者がいる」側として拾えている
3. `profile` が `light` でないこと

**「食い違いなし」と明示的に判定した。** 修正前に読ませていれば、
冒頭の括弧（`profile: full` × `mode: interactive` のときだけ）を現行条件として拾い、
部分自律で「促しは出ない」と答えたはずの箇所である。

### 実走が指摘した、記録として残す価値のある点

同じ行に条件の書き方が **3 通り**現れることを指摘したうえで、
`mode != autonomous` と `full × interactive` は
**いずれも「〜していた頃は」「写した条件が残った」の形で過去の誤りとして否定されており、
現行条件として並立していない**と正しく読み分けた。

**経緯を残すこと自体は読みを壊さない**——否定の形で書いてあれば、読み手は現行と区別できる。
壊れていたのは、冒頭に**否定されないまま**古い条件が置かれていたことだった。
