# 実走記録（ハーネス改修の必須ゲート）

ハーネスを改修したら、**着地させる前に**この 3 つを満たし、1 ファイルに記録する。
`lint-docs.sh` の **L8** が「最後の改修より記録が古くないか」を検査する。

なぜ機械に渡したか: 「改修のたびに実走を1本通す」は `DESIGN.md`「3.5」に書いてあったのに、
**次の改修で破られた**（`doccheck` の追加。テストと lint で止めた）。
分類 G（散文にしか無い規約）そのもので、扱いも同じ——**観測点を作る**。

## 3 つのゲート

1. **文書が実態に追いついているか** — 実装を正として、規約・手順・キー名・終了コードの食い違いを潰す。
   L1〜L7 が見るのは表面（コマンド名・config キー・参照・schema・同一行の重複・行数・help）だけで、
   **説明の中身**は見ていない。ここは人／エージェントの担当。
2. **README のメンテナンス** — `bin/README.md`（CLI リファレンス）と `aidev-docs/README.md`（概観）。
   概観に一度も出てこない機能は、**存在しないのと同じ**になる（`limits` で実際にそうなった）。
3. **サブエージェントでの実走** — テスト PJ で aidev フローを 1 本通す。
   lint も CI も「書いてあることの整合」しか見ないので、**書いてある規約が実際に発火するか**は
   通り道を歩かないと分からない（`DESIGN.md`「3.5」の分類 G）。

## 書き方

`<YYYY-MM-DD>-<slug>.md` で 1 改修 1 ファイル。下の 3 見出しは**必須**（L8 が実在を見る）。

```markdown
---
date: 2026-09-05
change: <何を変えたか 1 行>
---

## 1. 文書は実態に追いついているか
<誰が/何で確かめたか。見つかった食い違いと、直したか>

## 2. README のメンテナンス
<bin/README.md と aidev-docs/README.md に何を足したか。不要なら「不要」と理由>

## 3. 実走（サブエージェント）
<どの PJ で何工程回したか。見つかった欠陥と、直したか>
```
