# 振り返り: `host` パッケージ — Windows / WSL 差の吸収点

## サマリ

`@acc/host` を新設し、Windows / WSL 差の吸収点を 1 パッケージに閉じた。
実装 8 ファイル・テスト 6 ファイル・配線 4 箇所（24 ファイル / +2,438 / −7）、テスト 240 件 green。
`feature/host` の `2c704f9` に着地（**remote が無く PR は未作成・人間のレビュー未実施**）。

**この work の性格は「実装量」ではなく「検査の密度」だった。**
3 種の点検で **139 件**の指摘が出て、うち **must は 26 件**（doccheck 由来を含む）。

| 段 | 件数 | 内訳 |
|---|---|---|
| 上流の独立点検（`doccheck`） | **56** | requirement 12 / spec 30 / plan 14（各 2 ラウンド） |
| タスク点検（`taskcheck`） | **76** | 17 タスク・must 24 / should 29 / nit 20 |
| review（ラウンド指摘） | **7** | must 2 / should 4 / nit 1 |

漏斗としては意図どおり狭まっている（56 → 76 → 7）。**しかし review に残った must 2 件は、
どちらもタスク点検の修正が作った退行だった**——これがこの work 最大の学びである。

| 指標 | 値 |
|---|---|
| リードタイム | 23,886 秒（約 6.6 時間） |
| coding | 18,648 秒（**全体の 78%**） |
| 手戻り（reworks） | 6 |
| 差し戻し（sent_backs） | 2（spec→requirement / review→coding） |
| `ac_drift` | **0**（plan からの乖離なし） |
| `unplanned_lookups` | 2 / 18 アンカー（的中率 89%） |

## うまくいった点

- **research の 3 時間が spec 以降を安定させた。** `-EncodedCommand` 経路を実測したことで
  F3（終了コードが 1 に潰れる）/ F4（CLIXML）/ F9（インジェクション）が出て、
  **spec を書く前に**テンプレートの形が決まった。`ac_drift 0` はここに効いている。
- **`/proc/mounts` という第 3 の道**（decisions D5）。requirement は「`wslpath` か自前か」の
  二択で書いていたが、research が「同じ表が同期・0ms で読める」ことを見つけた。
  **未確定事項を二択で書いても、調査が三択目を出すことがある。**
- **差し戻しが 2 回とも「正しい方向」だった。** spec→requirement は AC の欠落（AC14）、
  review→coding は退行。どちらも黙って進めていたら着地していた。
- **一次資料の直読みが 3 回効いた。** backlog の要約が AGENTS.md と食い違っていた件（D2）、
  `/proc/mounts` の欄ごとのエスケープ差、`$ProgressPreference` の測定経路の誤り（D15）。
  いずれも「要約を信じていたら間違えていた」。

## 課題 / 手戻り

### 1. タスク点検が「修正の影響」を構造的に見られない（最大の課題）

review の must 2 件はどちらも**タスク点検で直した箇所が原因**だった。

- `exec.ts` の `exited` ガード（T8-1 の修正）が、同じ猶予窓の `output-limit` まで無効化。
  **1KiB 指定に 100MB が `code: 0` で返る**——元のバグより悪化。
- `createWindowsHost` の表の複製漏れ。**`createWslHost` は T10 で直したのに片側だけ。**

**前段で防げたか**: 防げない。タスク点検は「1 委譲 = 1 タスクの差分だけ」と規約で決まっており
（`protocol-check.md`）、**修正が別の枝や別ファイルに及ぼす影響を見る視野が構造的に無い**。
76 件を出した点検が、その修正が作った退行を 2 件とも見逃した。
review が work 全体の差分を見る工程として機能した、と読むのが正しい。

さらに **should を塞ぐために足した eslint ルールが既存のルールを黙って無効化した**（D19）。
これも「修正が別のものを壊す」型で、`guard-must-fire-on-every-class` の射程外である。

### 2. 同じ work の中で決定を覆したのに、それを指す記述が 7 箇所残った

D15 で「規約 6 = `$ProgressPreference`」を撤回し「規約 6 = スマートクォート」に差し替えた直後、
**それを指す記述が 3 箇所（`powershell.test.ts` の `describe` 名 / `smoke.mjs` のコメント /
引用ブロックの出典）で古いまま**になった。同種を数えると 7 件:

| 箇所 | 食い違い |
|---|---|
| `types.ts` 冒頭 | 「値を持たない型だけ」と宣言しつつ定数 2 つを持つ |
| `index.ts` コメント | 「eslint の禁止は core 限定」——**同じ work で変えた直後** |
| AGENTS.md 規約 5 | 「2.」の**存在しない文字列**を引用 |
| AGENTS.md 引用ブロック | 432 バイトの出典を research F4（実際は 384） |
| `powershell.test.ts` | `describe` 名が旧規約 6 |
| `probe.ts` 見出し | 「FR1 の 7 型」と core 限定のまま |
| `smoke.mjs` | `$ProgressPreference` を「規約 6」と表記 |

**前段で防げたか**: 防げた。**決定を覆した時点で、それを指す記述を機械的に探す**手順があればよい。
これは「よく考える」では再発しない類（チェックリストの不足）。

### 3. `taskcheck start` を打って委譲を忘れても、誰も気づかない

T17 は `aidev taskcheck start` を記録したのに**委譲を出し忘れていた**。
`taskcheck status` の表示は `rounds 1 / findings 0` で、これは
**「点検して 0 件だった」と見分けがつかない**。気づいたのは偶然 status を眺めたときで、
`approve coding` も止めなかった。

### 4. 記録の取りこぼしが 3 件

`taskcheck` の集計は 76 件だが、`review.md` のタスク点検ログは **73 行**。3 件が個別行として
残っていない（統合して書いた分）。件数の正典は metrics 側なので集計は狂わないが、
**内容が残っていない指摘が 3 件ある**のは事実として記録する（捏造で埋めない）。

### 5. `doccheck report` を修正の後に打った（1 回）

plan のラウンド 1 で、規約（「**直す前に**打つ」）に反して修正後に打った。件数は変わらなかったので
数値への影響は無いが、**規約を破っても何も起きない**ことが確認できてしまった。

## 改善提案

### 製品 / コード（→ issue 候補）

- **公開 API の広さを狭めるか判断する。** 低レベル関数 9 個（PowerShell 5 / マウント表 4）を
  公開しているのは smoke とテストを環境非依存にするためで、上位からの使用は eslint で塞いだ。
  **機械ガードで足りるか、API 自体を狭めるべきか**は未決（`walkthrough.md`「リスク」）。
  `sources` / `adapter-claude-code` を書くときに判断するのが自然。
- **`WSLInterop-late` を実機で確認する。** 一時ディレクトリで両綴りの検出は確かめたが、
  systemd-late で登録された機械で `powershell.exe` が動くかは未検証。
- **interop の無い環境で 12 件がスキップされる。** CI を持つなら、そこでの緑を
  「全数検証」と読まないための表示が要る（`test-result.md` に既記）。
- **`exports` の `types` 条件だけを壊しても検出できない**（TS の解決仕様）。
  実行時側と 2 経路で見ているが、型側単独の穴として残る。
- **`toWslWith` の `İ` 添字ずれ防御は発火を作れなかった。** 防御は残したが、
  次に触る人が「遠回り」と見て最短路に直しても検査が止めない。

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項）

**まず `guard-must-fire-on-every-class` は条項を追記しない。**
`review.md` のタグ集計で **`[conv:guard-must-fire-on-every-class!]` が 26 件**（`!` 無しを含め 36 件）。
これは「規約はあるのに守られていない」であって、**追記しても効かない**
（`protocol.md`「12.」の表）。打ち手は**層を下げること**——下記「ハーネス自体」で扱う。

条項の候補は `[conv:-]` 41 件の類型化から 2 つ。

- **条項案 1: `sweep-references-when-reversing`（決定を覆したら参照を掃く）**
  - **仮説**: work の途中で決定を覆した（規約の内容を差し替えた・数値を訂正した・
    ファイルの責務を変えた）とき、**その決定を指している記述を grep で洗い出して同じコミットで直す**と、
    「文書の主張が実態と食い違う」型の指摘が減る。
  - **baseline**: 本 work で 7 件（`[conv:-]` 41 件中 17%）。うち 3 件は D15 の撤回の直後に発生し、
    1 件（`index.ts` のコメント）は**同じ work で変えた設定を、変えた本人が古いまま説明していた**。
  - **根拠にした指摘**: `types.ts` 冒頭 / `index.ts` コメント / AGENTS.md 規約 5 の引用 /
    引用ブロックの出典 / `powershell.test.ts` の `describe` 名 / `probe.ts` 見出し / `smoke.mjs`。
- **条項案 2: `fix-the-class-not-the-instance`（1 箇所直したら同型を探す）**
  - **仮説**: 欠陥を 1 箇所直すとき、**同型の箇所を全部探し**、かつ**その修正が既存の検査や
    別の枝を壊していないか確かめる**と、「片方だけ直る」型と「修正が退行を作る」型の指摘が減る。
  - **baseline**: 本 work で 6 件。うち **review の must 2 件が両方これ**
    （`createWindowsHost` の複製漏れ / `exited` ガードの巻き込み）。
    他に `typecheck` の非対称・`windows-host.test` の TIMEOUT 非対称・`WindowsHost.exec` の
    `opts` 素通し・eslint の後勝ち上書き。
  - **`guard-must-fire-on-every-class` との違い**: あちらは「**検査**の対象集合」を問う。
    こちらは「**修正**の影響集合」を問う。本 work は前者を 36 回破りながら、
    後者の穴で review まで欠陥を通した。**別の軸である。**

**両方とも起票済み**（`aidev convention new`）。本文と索引（`AGENTS.md`）も書いた。
- `.aidev/conventions/sweep-references-when-reversing.md`
- `.aidev/conventions/fix-the-class-not-the-instance.md`

**未確認事項**: `.aidev/config.yml` に `docsRoots` が未設定のため、
**PJ の既存ドキュメントとの内容重複を機械的に確認していない**（CLI が両方で警告した）。
本 PJ は `AGENTS.md` 以外に docs を持たないので実害は無いが、確認していない事実として残す。

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

- **提案 1: `taskcheck` / `doccheck` の「開始したまま報告なし」を検出する。**
  `start` を打って委譲を忘れても、`status` の `findings 0` は「点検して 0 件」と見分けがつかず、
  `approve` も止めない（本 work の T17 で実際に起きた）。
  **`start` と `report` の対を追い、未報告があれば `verify` が WARN・`approve` が促す**のが妥当。
  「0 件」と「未実施」を区別できないのは、`task_checks=0` を明示させている
  protocol.md「8.」の思想と整合しない。
- **提案 2: `guard-must-fire-on-every-class` を第二層へ下げる。**
  36 件の違反は「散文では効かない」ことの証拠である。
  `aidev taskcheck report` に **`--mutations <n>`（守ると主張する防御を何通り壊して確かめたか）**を
  足し、0 のまま `approve coding` に進めない、という形が考えられる。
  本 work では手で 42 通りの変異を試したが、**その記録は `review.md` の散文にしかない**。
- **提案 3: `doccheck report` を「修正前」に強制する手段が無い。**
  規約（`protocol-check.md`）はあるが、破っても何も起きない（本 work で 1 回破った）。
  `report` が対象 md の mtime / ハッシュを `start` 時と比べて、変わっていたら WARN を出せる。
- **提案 4（重要）: ハーネスがリポジトリ外にあると効果検証の母集団に入れない。**
  `harnessRev: unknown` / `harnessRevDelivered: unknown`。
  この PJ のハーネスは `~/.claude/skills/` にあり、リポジトリ内の `.claude/skills/aidev-*` から
  tree hash を取る現行の実装では版が刻めない。
  **結果として、条項の効果検証にとって最も濃い母集団になるはずのこの work が、
  `aidev-util-insights` の集計から静かに漏れる。**
  版の取得元を設定可能にするか、`unknown` を「母集団外」として**明示的に警告**すべき。
- **提案 5: PR を作れない環境では人間由来の判定材料が 1 件も残らない。**
  remote が無いため `review.md` に「PR レビュー（人間）」節が生まれない。
  `protocol-autonomous.md` は「insights はその旨をレポートに明記する」と定めるが、
  **その事実を機械的に拾う印が state に無い**（報告の散文に頼っている）。
  deliver が「PR を作れなかった」を `state.yml` か `metrics.yml` に刻めば、insights が確実に拾える。
- **提案 6: retro の前提チェックが正しく効いた（良かった点として記録）。**
  deliver 未承認の状態で `/aidev-95-retro` を起動したところ `aidev guard retro` が exit 2 で止めた。
  そこで工程を回し切ってから retro に入れたので、**test / review / deliver の学び
  （最大の課題である「修正が作った退行」を含む）が振り返りに入った**。
  guard が無ければ、この retro は上流 4 工程だけの浅いものになっていた。
