## 課題 / 手戻り

### 1. 境界の向こう側を一度も動かしていなかった（must 20 件中 5 件）

この work で最も高くついた欠陥は、すべて**別プロセス / 別 OS / 外部パーサの側**にあった。

| 欠陥 | 何を仮定していたか | どう見つかったか |
|---|---|---|
| トーストが一度も出ない | `Host.exec` に `powershell.exe` を渡せば素直に届く | 点検が実 Windows で `Missing ')' in method call.` を実測 |
| 本文・タイトルが空 | `ExecOptions.env` が子プロセスに届く | 点検が `TITLE=[]` を実測 |
| `too-large` が返らない | `req.destroy()` の後でも resolve できる | 点検が実サーバで 5 サイズ分を実測 |
| 承認が 2 件になる | hook とポーリングの payload が同じ形 | 実データで `approvals=2`（片方は `toolName: ''`） |
| `smokeCommands` の 2 行目が消える | ブロック内のコメントは無視される | 同じ awk で再現すると 1 行しか出ない |

**前段で防げたか**: 防げた。5 件とも「**実物を 1 回通せば即座に分かる**」もので、
`design.md` の該当節も、単体テストも、私の頭の中のモデルの上で閉じていた。
既存条項では覆えない——`test-doubles-no-looser-than-real` は
「ダブルを実物の契約より緩くするな」だが、ここは**契約そのものを観測せずに書いていた**。
→ **条項 `cross-boundary-needs-a-real-run` を起票**（下記）。

### 2. 修正が次の欠陥を作る型が、3 つの層で同時に起きた

| 層 | 1 巡目の修正 | 2 巡目に出たもの |
|---|---|---|
| cross | 7 件を直した | **7 件すべてが 1 巡目の修正由来** |
| taskcheck（T17） | review ラウンド 1 の 7 件を直した | 6 件中 **5 件**が 1 巡目の修正由来 |
| review | ラウンド 1 の 7 件を直した | should 4 件（**うち 1 件は私が入れた退行**） |

**前 work との違いは「捕まえられたこと」**——H3 が「前ラウンドの修正由来か」を問う段を置いたので、
判定ごと `review.md` に残り、deliver には 1 件も抜けていない（review の must 0）。
**型そのものは消えていない。**

**原因**（前 work の「散らばった暗黙の連言」とは別の形が 2 件）:

- **規則を書き直すと、書き直した規則が新しい未検査領域になる。**
  畳み込みは **work 単位 → 家族単位 → 家族単位＋親のあるツリー優先**と 2 度書き直した。
  2 度目の根拠に書いた「家族は必ず 1 つのツリーにしか存在しない」が誤りで
  （`scanWorks` は親の `state.yml` が読めなくても子を返す）、**家族が一覧から丸ごと消える**退行を作った。
  **物理的な配置の話を、走査結果にそのまま当てはめていた。**
- **可変値から安全側の余裕を導出すると、下限を足しても要求を満たさない。**
  「`pollIntervalMs` に下限が無い」を `MIN_POLL_INTERVAL_MS = 250` で塞いだが、
  そこから導く hook の猶予（間隔の 2 周＝500 ms）が**実測 1 周（730〜788 ms）より短く**、
  指摘の (b) は下限値では閉じていなかった。猶予に**独立した床**を置いて初めて閉じた。

**前段で防げたか**: 一部は防げた。前 work の H4「修正は**全面改稿ではなく最小の差分**で当てる」は
採用されたが、入ったのは `protocol-check.md`「(a)」＝**上流の doccheck の側だけ**で、
coding の修正（(b)）と review の差し戻しには掛かっていない。今回 2 度書き直した畳み込みは
まさに「最小の差分ではない修正」だった。→ ハーネス提案 H5。

### 3. 実データに事例が無い規則を 2 度書き直した

AC3（worktree 重複の畳み込み）は、`/workspaces` に worktree が 1 つも無いため
**実データを 1 度も通っていない**（`duplicates=0`）。それでも規則を 2 度変えており、
確かめたのは合成 fixture だけ。`test-result.md` の「未検証の穴」1・5 に残した。

**前段で防げたか**: 防げない。research F15 が着手前に「実データに事例が無い」と記録しており、
design もそれを前提にしている。**規則を変える判断自体は点検が出した実在の欠陥に基づく**ので、
やらない選択は無かった。残るのは「**実物での初回は人が見る**」という引き継ぎだけ。

### 4. `[conv:agents]` という存在しない id を 3 件書いた（記録の欠落）

`aidev convention status` の一覧は 6 件で、`agents` は無い（`AGENTS.md` を指したつもりの造語）。
skill は「**語彙を発明しない**」と明記しているが、**機械検査が無い**ので静かに通った。
`aidev-util-insights` の集計ではこの 3 件がどの条項にも入らない。

**遡って付け直さない**——3 件とも「`AGENTS.md` の規定に反する」であって
`.aidev/conventions/` の条項違反ではないので、正しくは `[conv:-]` だった。
混在した母集団を作るより、事実として残してハーネス提案に繋げる。

### 5. 工程の所要時間が「中断」と区別できない

`work_sec` は 52,913 秒（14.7 時間）だが、coding の中に **8 時間 40 分の空白**がある
（`2026-09-07T05:39:33Z` の taskcheck report と `14:19:29Z` の次の start の間。イベント 0 件）。
実作業はおよそ 6 時間で、**この work が「最長」なのは主にこの空白のせい**。
`aidev metrics` はこれを区別できないので、**work 間の lead / work 比較はそのままでは成り立たない**
（前 work の retro が 5 work の lead を並べた比較も、同じ理由で怪しい）。

上流 4 工程は合計 **1.04 時間**（requirements 0.26 / research 0.27 / design 0.33 / tasks 0.18）。
review 以降は差し戻しで工程が交錯するため、start→approved の対では分離できない。

### ハーネス自体（→ aidev-* への提案・適用は人間）

- **H2（前 work から継続）: 数え上げ・列挙の陳腐化を機械で拾う。**
  前 work の H2 は未着手で、この work で **6 件再発**した——
  `lock.ts`「3 項の不変条件」（項 2 が load-bearing でなかった・must）／
  `daemon.ts` 冒頭「ここが持つのは 3 つだけ」（実際は 4 つ）／
  `sse.ts` `send` の doc「見るのは `destroyed` だけ」（実装は 2 項）／
  `index.ts`「明示している非公開は `fsread.ts` だけ」（実際は 3 つ）／

  **2 work で計 11 件。** 提案は前回と同じ（一覧を持つ定数の件数を散文に書いたら落ちる検査の定型）。
- **H3: retro の「製品 / コード」提案が次の work に届かない。**
  前 work の retro が挙げた `costFromUsage` の穴は backlog に入らず、**予告どおり再発した**（上記）。
  `aidev backlog` の口は `new|archive|compact` の 3 つで、**既存ファイルに 1 行足す口が無い**。
  提案: `aidev backlog add <file> "<item>" [--source <retro.md>]` を足すか、
  `aidev-95-retro` の手順に「**製品 / コードの提案は backlog に落として同じコミットに含める**」を
  明記する（条項が `aidev convention new` で機械的に起票されるのと同じ扱いにする）。
- **H4: `metrics` に「イベントが 1 件も無い区間」を出す。**
  この work は coding の中に 8 時間 40 分の空白があり、`work_sec` が実作業の 2 倍以上になった（課題 5）。
  提案: `aidev metrics` が**イベント間隔が閾値（例 30 分）を超えた区間の合計**を 1 列足す。
  空白を引いた値を「実作業時間」と名乗らせない——**観測できるのは「イベントが無かった」だけ**で、
  そこで作業していたかは分からない。列を足すだけなら捏造にならない。
- **H5: 前 work の H4（最小の差分）を coding 側と review の差し戻しにも掛ける。**
  採用された一文は `protocol-check.md`「(a)」＝**上流の doccheck にしか無い**。
  この work では**規則の書き直し**が 2 度あり、2 度とも新しい欠陥を作った（課題 2）。
  提案: `protocol-check.md`「(b)」に「**規則そのものを書き直したら、
  書き直した規則を新規実装として点検し直す**（直した箇所の変異では足りない）」を足す。
  根拠は「畳み込みを work 単位から家族単位へ書き直した結果、
  **書き直しの根拠に書いた前提が誤っていた**」という 1 件（review ラウンド 2 の 1 件目）。
- **H6: `aidev smoke` が実行した本数を毎回出す。**
  `smokeCommands` の 2 行目が黙って捨てられていた（課題 1）。CLI は `doctor` では `commands=2` を出すが、
  **`smoke` 自身の出力は本数を言わない**ので、2 本設定して 1 本しか走っていない状態が無徴候だった
  （今回は点検が同じ awk で再現して気づいた）。
  提案: `smoke` の出力に `(exit 0, N 本)` の N を**設定値と実行値の両方**で出すか、
  食い違ったら WARN を出す。
