# 振り返り: core パッケージと npm workspaces のモノレポ土台

## サマリ

`packages/core`（I/O を持たない純関数・公開 API 14 関数＋13 型）とモノレポ土台が着地した。
コミット `188e50e`、実装 27 ファイル / +4,548 / −6、テスト 103 件 green。

| 指標 | 値 |
|---|---|
| リードタイム | 19,787 秒（5 時間 30 分） |
| 手戻り（reworks） | 9 |
| 差し戻し | 3（test→coding、review→coding、**deliver→coding**） |
| review 指摘 | must 1 / should 1 / nit 9（3 ラウンド通算） |
| タスク点検（別枠） | 7 タスク・**40 件** |
| `ac_drift` | **0** |
| 条項タグ | `[conv:-]` 52 件 / `[conv:constraints-to-agents-md!]` 1 件 |

**この work の性格を一言でいうと「検査を足すたびに、その検査自体に穴が見つかった」。**
40 件の点検指摘のうち複数が「直したつもりの修正が開けた新しい穴」だった。

## うまくいった点

- **部分自律（`humanGates: [spec, review]`）の切り方が正しかった。** ユーザーの判断を要したのは
  実際に 2 箇所だけ（spec の範囲、review の受け入れ）で、それ以外は自動で進んだ。
  正規化表の 1 行を `unknown` に倒す判断も、負債を残す判断も、spec / review のゲートで人間に届いた。
- **独立点検（delegated）が繰り返し実質的な欠陥を返した。** 40 件のうち、
  自分では見つけられなかったものが多数あった。とくに:
  - 停滞判定から `start` イベントを持たない work が構造的に漏れていた
    （点検者が**実データ 345 works を走査**し、48 件が該当・うち 12 件が長期放置と確認）
  - **テストが一度も型検査されていなかった**（`tsconfig.json` の `include` が `src` だけ）
  - 祖先集合への変更が **DAG の指数展開＝ヒープ枯渇**を開けていた（深さ 24 で OOM）
- **「壊したら落ちるか」を毎回実測した。** 正規化表の 1 行変更で 4 テストが落ちること、
  `MAX_DEPTH` を下げるとテストが落ちること、`MAX_NODES` を外すと DAG テストが終わらないこと、
  `exports.default` を壊すと build が落ちること——**緑であることを合格の根拠にしなかった**。
  この確認をしていなければ、`MAX_DEPTH` は「64 と書いてあるだけで誰も守っていない定数」のままだった。
- **`ac_drift = 0`。** plan 承認時と実装後で被覆が変わっていない。spec と実装が離れなかった。
- **実データで検証できた。** 16 PJ・346 works が手元にあるので、停滞判定の修正を
  仮説ではなく実測（停滞 15 件中 12 件が `start` 無し）で確かめられた。

## 課題 / 手戻り

### 1. AC3 の失敗は plan で作り込まれていた（前段で防げた）

`requirement.md` の AC3 は「7 つの型が `packages/core` から export され、**外部から import できる**」。
ところが `plan.md:68` は検証方法を
「`index.ts` から 7 型が import できること（**型テストは `tsc -b` の成功をもって代える**）」と書いた。

**`tsc -b` はパッケージの内側からの検査で、「外部から」を一切見ていない。**
AC が検証の観点まで指定しているのに、plan がそれを内側の手段へ代替した。
結果、ワークスペースが一度も配線されていない状態で `npm run build` / `npm test` / `npm run lint` が
3 つとも exit 0 を返し、test ラウンド1 まで誰も気づかなかった。

**これは「実装のバグ」ではなく「検証設計の劣化」**で、
protocol-check.md「(a) 文書の内部一貫性」の観点（**`AC` の入力の出所が文書内で辿れるか**）に
ちょうど当たる。つまり **plan の独立点検が拾うべきだった**——課題 6 に繋がる。

### 2. 検査を足す修正が、繰り返し新しい穴を開けた

| 足した検査 | 開いていた穴 | 見つけた者 |
|---|---|---|
| `check:exports`（型で公開 API を検査） | `tsc -p` は `exports` の `types` 条件しか解決せず、実行時の `default` が壊れても通る | T13 の点検 |
| `smoke` の孤児検査 | 非再帰・`packages/core` 決め打ち・`.js` 限定で、src にサブディレクトリを切った時点で対象が縮む | T13 の点検 |
| `stableKeyOf` の祖先集合化 | 循環でない共有参照（DAG）が指数展開し、**深さ 24 でプロセスごと落ちる** | T15 の点検 |
| `node:*` の一括禁止 | 接頭辞つきだけを塞ぎ、**素の `path` は素通り** | T15 の点検 |
| 生 NUL の検査 | `.mts` / `.cts` を**黙って見逃す**（`walk` の返り値に `.ts` を決め打ちで付け直していた） | T19 の点検 |
| 鍵の衝突テスト | 「区切りが空白でない」しか固定せず、`/` に変えても全件緑 | T19 の点検 |

**共通の失敗の形**: 検査を足したとき、**「代表 1 件で発火すること」は確かめたが、
「その検査が守ると主張する対象集合の全クラスで発火すること」を確かめていない。**
`.ts` で発火したから `.mts` も大丈夫だろう、`node:os` で落ちたから `os` も落ちるだろう、と暗黙に広げていた。

### 3. 生 NUL バイトは 4 工程を素通りした

`packages/core/src/fleet.ts` の鍵の区切り文字が生の NUL バイトで、
**型検査・テスト・lint がすべて通り、読んでも空白にしか見えなかった。**
気づけたのは deliver 直前の `git diff --cached --stat` が `Bin 0 -> 5947 bytes` と出したときだけ。

**この欠陥を検出できる場所が「git のファイル判定」しか無かった**というのが本質で、
自動検査の網に「git から見てどう見えるか」という観点が 1 つも無かった。
（対策として `aidev smoke` に検査 4 を足した。）

### 4. 文書が実態から遅れることが繰り返し起きた

README（must 1 件・nit 2 件）、AGENTS.md（nit 1 件）、`smoke.mjs` のコメント（nit 1 件）、
`probe.ts` のコメント（nit 1 件）、decisions の相互参照欠落（nit 1 件）。
**振る舞いを変えた差分が、その振る舞いを説明している文を置き去りにする**形で一貫している。
とくに README の must は「実装を入れる work が README の『実装未着手』を直さなかった」もので、
**この work 自身が作った矛盾**だった。

### 5. 自分のレビュー指摘に事実誤認があった

`sumCosts` の指摘で「混在時の振る舞いは `decisions.md` にも無い」と書いたが、**D7 が決めていた**。
`decisions.md` を該当語で検索せずに「無い」と断定した。
指摘の中身（`transcript` を名乗るのは事実と違う）は妥当だったが、
正しい枠組みは「決定が無い」ではなく「**D7 を覆す**」で、退けられた理由に反論する責任があった。
（訂正を `review.md` に残し、D11 に「D7 を差し替える」と明記した。）

### 6. `autonomous` で必須の上流点検（doccheck）を 1 度も実施しなかった

`aidev doccheck status` は **rounds=0**。requirement / spec / plan のいずれにも独立点検を掛けていない。

protocol-check.md「(a)」は **`mode: autonomous` では必須**と明記している——
「人間の目が入らないので、要否を書いた本人の裁量に委ねない。
coding が全タスク必須なのに上流が任意だと、**『上流で最も効く』と書いた優先順位と逆になる**」。
まさにその逆をやった。coding のタスク点検は 7 タスク全部に掛けて 40 件を得たのに、
**手戻りの源として最も効くはずの上流には 1 度も掛けなかった。**

そして**課題 1（AC3 の検証設計の劣化）は、その点検が拾う類型そのもの**だった。
掛けていれば test ラウンド1 の差し戻し 1 回・修正 2 タスクは避けられた可能性が高い。

**なぜ気づかなかったか**: この work の `state.yml` は `schema: 10` で、
`doccheck` の記録欠落を `verify` が咎めるのは **schema 11 から**（`bin/README.md:49`）。
つまり**規約はあるが、この schema では機械的な強制が無い**。
散文の規約だけが根拠で、私はそれを読み落とした。
protocol.md「2.10」の三層でいえば**第一層（散文）しか無く、第二層（CLI）が効いていない**区間だった。

## 改善提案

### 製品 / コード（→ backlog / issue 候補）

- **正規化の生スキーマ読み取りが `core` にある**（D8）。design D4 と AGENTS.md「4.」に反する。

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項。AGENTS.md 本体には書かない）

材料は `[conv:-]` が **52 件**（既存条項に当たったのは 1 件のみ＝規約の穴が大きい）。
**3 案あるが、母集団を薄めないため起票は 1 本に絞ることを推奨する。**

- **【推奨】条項案 `guard-must-fire-on-every-class`**:
  「検査（lint ルール・テスト・smoke の検査項目）を追加・変更したら、
  **それが守ると主張する対象集合の各クラスで実際に発火することを確かめる**。
  代表 1 件の確認で全体に一般化しない。」
  - **根拠**: 課題 2 の表。この work で追加・変更した**防御 6 つ（検査 5・実装修正 1）すべてに穴**があり、
    いずれも「1 クラスで確認して他へ一般化した」形。すべて `[conv:-]`。
    実装修正（`stableKeyOf` の祖先集合化）だけは毛色が違うが、
    **「偽陽性 1 件を消す修正が、無限の資源消費と引き換えだった」**という点で
    やはり「守る対象を 1 面でしか見ていない」同じ形。
  - **仮説**: この確認を課すと、検査の穴に起因する点検指摘が減る。
  - **baseline**: 検査の穴に起因する点検指摘 = 6 件 / 40 件（15%）。
- **条項案（保留）`ac-verification-verbatim`**:
  「AC が検証の観点（『外部から』『利用者と同じ経路で』等）を明示しているとき、
  plan でそれを内側の手段に代替しない。」
  - **根拠**: 課題 1。ただし**この work での発生は 1 件**なので、母集団が足りない。
    次に同型が出たら起票する。
- **条項案（保留）`docs-follow-behaviour`**:
  「振る舞いを変えた差分は、その振る舞いを説明している文（コメント / README / AGENTS.md / decisions）を

    現に生 NUL は smoke の検査で層を下げられた。**次の work で見極める。**

残る 2 案は上記のとおり保留——母集団が足りない（`ac-verification-verbatim`）か、

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

1. **`task_checks` が「独立したコンテキストの数」ではなく「report したタスクの数」を数えている。**
   この work は `task_checks: 7` だが、実際に走った点検エージェントは **6 体**——
   T6 と T7 は 1 体が 8 件（`[T6]`×6・`[T7]`×2）をまとめて返したものを 2 タスクに割って report した
   （サブエージェントの生の返答で確認）。`mode: delegated|same_session` を刻む目的は
   protocol-check.md が言うとおり「コンテキスト分離の効果を測る」ことなので、
   **分離の回数を水増しする向きにずれる**。`aidev-util-insights` の横断集計に効く。
2. **`taskcheck report --findings <n>` を検証する口が無い。**
   `review.md`「タスク点検ログ」の行数と突き合わせる検査が `verify` にも `doctor` にも無い。
   この work では **ログ 41 行に対し合計 40 件**の 1 件ずれが承認まで素通りした
   （原因は T5 の 1 指摘を対応別に 2 行へ割ったこと＝記録側の判断で、ハーネスの不具合ではない）。
   README は「崩れた返答から数字を拾わせない」ために `--findings` を必須にしたと書いているが、
   **打った数が正しいかは誰も見ていない**。
3. **`smokeStaleAfter` の基準日判定が `smokeCommands` の成長を捉えない。**
   判定は `git log -S smokeCommand` の pickaxe で、文字列の**出現回数の変化**で拾う。
   `smokeCommands:` の下に行を足しても `smokeCommand` の出現数は 1 のままなので基準日が更新されず、
   古い WARN が出続けうる。**「起動確認は成果物と一緒に育てる」という設計意図と検査が噛み合っていない。**
4. **`aidev metrics` の `harnessRev` が `unknown`。** `state.yml` には `e69de29bb2d1` が入っているのに
   metrics 側が読めていない。前 work の retro で報告した「`~/.claude/skills` が git リポジトリでない」
   （H1）と同根の可能性があるが、**state に値がある以上、表示側の問題**として別に見る価値がある。
5. **`doccheck` の必須化が schema 10 では機械的に効かない**（課題 6）。
   `autonomous` で上流 4 工程の独立点検は protocol-check.md「(a)」が**必須**と定めているのに、
   この work は **rounds=0 のまま requirement / spec / plan / coding / test / review / deliver
   すべてを承認できた**。`verify` も PASS。咎めるのは schema 11 からで、
   **規約と強制の間に schema 1 つ分の空白がある**。
   `taskcheck` は「1 ラウンド = 1 コマンド」の形を持つので数えられるが、
   `doccheck` も同じ形を持ちながら**旧 schema の work では検査が走らない**。
   - 提案 A: schema 10 の work でも `verify` が **WARN** は出す（致命にはしない）。
     「規約はあるが観測点が無い」状態を、schema の移行を待たずに可視化できる。
   - 提案 B: 各工程 skill の手順に `doccheck` を**明示のステップとして書く**
     （現状 protocol-check.md を読まないと存在に気づけない。付録は「該当する状況のときだけ読む」建付けなので、
     **`autonomous` という該当条件を工程 skill 側が知らせない限り読まれない**）。
6. **`lead_sec` が実時間なので、work 横断の比較に中断の影響がそのまま乗る。**
   この work の `lead_sec` は 19,787 秒（5 時間 30 分）だが、`metrics.yml` の
   連続イベント間隔を数えると**内訳の過半が「次のコマンド待ち」**だった。

   | 区分 | 時間 | `lead_sec` 比 |
   |---|---|---|
   | **工程間の空白（5 分以上の間隔）** | **200.1 分** | **60.7%** |
   | 独立点検（サブエージェントの実行） | 73.1 分 | 22.2% |
   | 工程内の作業（残り） | 56.5 分 | 17.1% |

   工程間の空白 200.1 分のうち **191.4 分が下の 2 箇所**に集中している。

   ```
   100.6分  10:32→12:12  [coding/approved] → [test/start]
    90.8分  12:34→14:05  [test/approved]  → [review/start]
   ```

   **どちらも承認ゲートでの検討時間ではなく、次の skill が起動されるまでの空白**である
   （実際の承認応答は数分——requirement 承認後の 8.7 分が最長）。
   つまり `lead_sec` は**労力ではなくセッションの張り付き方**を測っている。
   同じ内容でも、途中で離席すれば伸びる。

   - **提案**: `aidev metrics` に**工程の `elapsed_sec` 合計**（この work では 7,463 秒＝2 時間 4 分）を
     per-work 列として出す。`lead_sec` と並べれば「実作業に近い時間」と「暦の上の時間」を
     読み分けられる。両方を出す価値があるのは、**外部の締切に対しては `lead_sec` が正しく、
     工程の重さの比較には `elapsed_sec` 合計が正しい**ため。
   - **補足**: それでも `elapsed_sec` は独立点検の待ち（この work で 73 分）を含むので、
     「人手の労力」ではない。DESIGN が insights の分母に `files_changed` を採ったのと同じ理由で、
     **規模あたりの手戻り**（この work は `reworks 9 / files_changed 27` ≒ 0.33）のほうが
     中断に対して頑健。時間系の指標を KPI にしないこと自体は既存の方針と整合している。
7. **`aidev-00-start` が `mode: autonomous` を選ばせた時点で、必須になる点検を提示していない。**
   モード選択は `humanGates` の設定とセットで行われるが、
   そこで「autonomous を選ぶと上流 4 工程の doccheck が必須になる」ことが示されない。
   選択の帰結が選択の場に無いので、**選んだ本人が後で規約を読み直さないと守れない**。
