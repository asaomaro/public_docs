# `aidev-docs/retro/` — ハーネス改修の材料として受け取った振り返り

**このフォルダは効果検証の母集団ではない**。`aidev-util-insights` が集計するのは
`.aidev/works/**/retro.md`（その PJ の work に紐づく記録）で、ここはその**公開写し**と、
work に紐づかない**外部レビュー**の置き場である。ハーネスを改修するときの入力として読む。

## 置けるもの

| 種別 | 冒頭に付ける印 | 例 |
|---|---|---|
| **work の retro の公開写し** | `出典: <PJ> / .aidev/works/<slug>/retro.md` ＋ コミット | `20260905-core.md` |
| **外部レビュー**（work に紐づかない読み合わせ・監査） | `出典: work の retro ではなく、外部レビュー` ＋ 対象コミット | `20260906-planmode.md` |

どちらも本文は原文のまま置き、**印の 2〜3 行だけを公開時に付与する**。
書き換えると「指摘がどう届いたか」が復元できなくなる。

## なぜ印が要るか

**2 種類が混ざると、扱いを間違える**。work の retro は「その作業で実際に起きたこと」で、
提案の重みが実測に裏打ちされている。外部レビューは読み合わせなので、
**動作を確認していない指摘が混ざりうる**（`20260906-planmode.md` の末尾が自分でそう断っている）。

受け取った側の義務は同じ——**実物に当てて確かめてから採否を決める**（`DESIGN.md`「3.5」）。
違うのは、外部レビューのほうが**再現手順を持たないことが多い**という点で、
その場合は検証にこちらの手間がかかる。印があれば最初からそう構えられる。

## 受け取ったあと

1. **1 件ずつ実物に当てる**。行番号・ファイル名の引用は、引用元を開いて確かめる。
2. 採る／採らない／既対応を判定し、**採らない理由も記録する**（`DESIGN.md`「2.」または「3.5」）。
   理由の無い不採用は、次の retro で同じ提案として戻ってくる。
3. 改修したら 3 ゲート（`DESIGN.md`「3.6」）を通す——文書・README・実走。
