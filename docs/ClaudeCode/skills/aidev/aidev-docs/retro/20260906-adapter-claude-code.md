`AgentAdapter` を実装し、Claude Code の列挙・起動・停止・削除・コスト・更新発行を
1 パッケージに閉じた。**backlog の 3 項目（`server` / `cli` / 技術的負債の解消）が待っていた
依存グラフ上のボトルネック**を解消した。

| 指標 | 値 | 5 work 中の位置 |
|---|---|---|
| lead / work | 19,070 s / 19,237 s（約 5.3 時間） | 最短ではないが短い部類 |
| **手戻り（reworks）** | **10** | **最多**（core 9 / sources 9 / host 6 / mvp-design 5） |
| **差し戻し（sent_backs）** | **4** | **最多**（core 3 / sources 3 / host 2 / mvp-design 2） |

| 成果物 | src 1,938 行 / test 3,931 行（比 **2.03**）/ 工程文書 2,975 行 | — |
| 着地 | 34 ファイル / +6,272 / −10、テスト 881 件 green / skip 0 | — |

**独立点検の内訳**（母集団が違うので混ぜない）:

## うまくいった点

- **点検が工程に到達する前に 114 件を潰した。** review の must は 4 件で、
  そのうち 2 件は「実装当初からの欠陥」、2 件は「前ラウンドの修正が作り込んだもの」。
  点検が無ければこの 114 件が review か deliver 後に出ていた。
- **実測が設計を 3 回訂正した。** `--bg` が `--session-id` を無視すること（D23）、
  履歴に `cost-state` が実測コストを持つこと、Windows 経由の所要が research の 1/3 だったこと。
  いずれも**文献値・前 work の記録を疑って測り直した**結果で、
  research 工程を挟んだ判断（D4）が回収できた。
- **`ac_drift` が 0。** tasks 承認時の被覆（`ac_total=20 / ac_covered=20`）が review まで変わらなかった。
  上流の doccheck が「未確認のことを確定形で AC に書く」を繰り返し指摘し、
  該当 AC に「U◯ の結論に従う」と明記させた（D7）ことが効いた——
  実測で前提が崩れた AC7 も、**AC を書き換えずに済んだ**。
- **差し戻し上限でデバッグへ切り替えたことが実際に効いた。** 同じコンテキストで 4 巡目を回していたら、
  また 1 項だけ直していた可能性が高い。まっさらなコンテキストは
  「4 つの項の暗黙の連言」という**構造**を名指しし、**まだ生きていた穴**（ポーリングの母集団を
  変えても 298 件全緑）まで見つけた。

## 課題 / 手戻り

### 1. 修正が次の欠陥を作る（2 ラウンド連続）— 最大の問題

review の must 4 件のうち **2 件が前ラウンドの修正由来**。

| ラウンド | 直したもの | 次に出た must |
|---|---|---|
| 1 | 見つからないとき `--all` も見る | **基準が活動中のみのままで、過去のセッションが全部「増えた」に見えた** |
| 2 | 基準も `--all` に揃え、`name` を優先すると書いた | **`name` を見る前に早期 return していた**（コメントと実装の順序が逆） |

**前段で防げたか**: 防げた。原因は「`start` の同一性判定が **4 つの項の暗黙の連言**として散らばり、
不変条件が散文コメントにしか無かった」こと。**同じ work の `readCost` は不変条件を
`transcriptBelongsTo` という名前つき述語 1 個に閉じ、3 ラウンド無指摘だった**——
差は「散らばっているか、1 箇所に閉じているか」だけ。

**どのラウンドでも「直した行」の変異は実測していた。** 落ちなかったのは**隣の項**で、
そこは一度も変異させていない。条項 `fix-the-class-not-the-instance` は
「その修正が別の枝を壊していないか、壊してみて確かめる」と既に書いていたが、
**「どこを壊してみるか」が書かれていなかった**ため、直した行だけを変異させて満足していた。
→ 条項に「**同じ不変条件を支える項をすべて列挙して変異させる**」を追記済み（この work で対応）。

### 2. テストが「壊しても緑」だった箇所が多すぎる

`guard-must-fire-on-every-class` タグが **38 件**（must 7）。点検エージェントが
**実装を変異させて「壊しても全緑」を実測**してきた回数がそれだけあった。代表例:

- `cli.ts` の `failure` 枝を丸ごと削除しても **19 件全緑**（断言が両枝で成り立つ形だった）
- `defaultScheduler` を空にしても **17 件全緑**（既定の経路を 1 度も通っていなかった）
- `isControllable` の 2 条件のどちらを外しても **smoke 緑**（固定値の軸が縮退していた）
- `AGENT_ID` を変えても **19 件全緑**（実装と同じ定数との自己参照だった）
- ポーリングの母集団を変えても **298 件全緑**（フェイクが引数を見ないので原理的に観測不能）

**前段で防げたか**: 一部は防げた。最後の 1 つは**テスト用フェイクの設計**の問題で、
`createFakeHost` が「呼び出し順」で応答を返すため、**どの母集団に問い合わせたかがテストから
原理的に観測できなかった**。フェイクを引数駆動（`createStatefulFakeHost`）にして初めて見えた。

### 3. 事実主張が根拠を超える（この work の最頻出）

`claims-within-evidence` タグが **47 件**（全 140 件の 34%）。パターンは 3 つ:

- **数え上げが古くなる**: `--bg` の「5 行」（実際 6 行）、AGENTS.md の「2 箇所」（実際 3 箇所）、
  `fsread` の「3 名」（実際 2 名）、hook の「3 種まで」と「3 種ちょうど」の食い違い
- **撤回した説明が残る**: D23 で撤回した「`--session-id` で id を先に決める」が
  `control.ts` / `cli.ts` の**冒頭**と design の 7 箇所に残っていた
- **保証が観測より広い**: 「別のセッションに当たることはない」「`setInterval` なら周が重なる」
  「実測した生データ」（実際は伏字を推測で埋めていた）

**前段で防げたか**: `claims-within-evidence` は**この work の直前に起票された条項**で、
索引にも載っていた。それでも 47 件出た。**条項はあるのに守られていない**型なので、
条項をもう 1 つ足しても効かない（protocol.md「12.」の判別）。

### 4. `[conv:<id>!]` の `!` を一度も使わなかった（記録漏れ）

`protocol.md`「8.」は「**条項に反している指摘は `[conv:<id>!]`**（`!` 付き）、
関係するが違反ではないものは `!` 無し」と定め、「効果検証で仮説と突き合わせるのは `!` 付きだけ」
としている。**この work の 140 件すべてが `!` 無し**（`grep -c 'conv:[a-z-]*!'` → 0）。

明らかな違反（撤回済みの説明が残る＝`sweep-references-when-reversing` 違反、
壊しても緑のテスト＝`guard-must-fire-on-every-class` 違反）も `!` 無しで書いている。
**このままだと `aidev-util-insights` の効果判定で、この work は 5 条項すべてについて違反 0 件と読まれる。**

**遡って付け直さない**——140 件の再分類は精度が落ち、混在した母集団を作るほうが悪い。
事実として記録し、ハーネス提案に繋げる。

### 5. `coverage` の書式ミスが 1 工程遅れて発覚

design.md の AC 対応行を `- **AC1**:` と太字で書き、CLI が読む書式（行頭 `- AC<id>:`）に
合っていなかった。**tasks 工程で `coverage` を打って初めて `design=0/20` で気づいた**（D12）。
design 工程の skill は「`coverage` が読む書式」を注記しているが、**その工程では `coverage` を打たない**。

## 改善提案

### 製品 / コード（→ issue 候補）

- **`costFromUsage` が空の `usage` に 0 を返す。** `packages/core/src/cost.ts` は
  `usage: {}` を渡されると `valueUsd: 0` / `estimated: true` を返す。
  「分からない」を「タダで動いた」と表示する経路で、**AGENTS.md「4.」に反する**。
  今回はアダプタ側（`parseUsageLines`）で塞いだが、**同じ穴は次の呼び出し元でも開く**。
  `core` 側で「4 欄が 1 つも無いなら `null`」にするのが筋。→ backlog 候補。
- **正規化表が `core` に残っている。** AGENTS.md「4.」の ⚠ を 3 箇所へ更新した。
  `raw.ts` という正しい行き先ができたので、backlog の「技術的負債の解消」項目は
  **移す先が確定した状態**で着手できる。
- **`start` が 5 秒かかる**（一覧 2 回＋起動 1 回）。`server` が 202 Accepted で返す前提だが、
  UI の体感に効くので `server` 実装時に再測する価値がある。
- **`name` を渡さないときの取り違えの隙**（D26）。`server` が一意な `name` を渡せば消えるが、
  **アダプタ側では閉じていない**。`server` の実装で必ず渡すことを AC にする。

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項）

- **【条項化する】`test-doubles-no-looser-than-real`**——テストダブルは実物より緩くしない。
  根拠は `[conv:-]` 45 件のうち**フェイク `Host` 関連の 5 件**（すべて should）:
  到達不能の理由を捨てる／失敗枝で部分出力を作れない／実物に無い状態の組合せを作れる／
  `stop` が `sessionId` でも当たる（実物は短い id だけ）／`toWsl` 既定のコメントが実装より広い。
  **このパッケージのテストは全部このフェイクの上に載る**ので、ここが甘いと全部が甘くなる。
  さらに「引数ではなく呼び出し順で応答を返す」設計のせいで、
  **母集団の取り違えが原理的に観測できず 298 件全緑で通った**——これは緩さの最も高くついた形。
- **【条項化しない】「分からない」を既定値に丸める型**（`usage: {}` → $0.00、
  読み取り失敗を「無い」と同じに握り潰す、`available: true` でも reject する契約違反）。
  **AGENTS.md「4.」が既に定めている**ので、条項を足しても「規約はあるのに守られていない」を
  重ねるだけ。打ち手は**層を下げること**——上の「製品 / コード」の `core` 側修正がそれ。
- **【条項化しない】`claims-within-evidence` の 47 件**。条項は既にあり索引にも載っている。
  重ねても効かない。層を下げる案は下のハーネス提案 H2（数え上げの機械検査）。

### ハーネス自体（→ aidev-* への提案・適用は人間）

- **H1: `[conv:<id>!]` の `!` が実運用で 1 度も使われなかった。**
  140 件すべて `!` 無しで、効果判定の母集団が 0 になる。書式は `protocol.md`「8.」にあるが、
  **書く側（review / taskcheck の返却形式）に `!` の選択が現れない**のが原因と見る。
  提案: `protocol-check.md` の**返却形式そのもの**に
  `- [<must|should|nit>][conv:<id>|<id>!|-] …` と両形を並べ、
  「違反なら `!`」を形式の一部にする。あるいは `aidev approve review` の時点で
  `!` 付きが 0 件なら WARN を出す（`doc_check_mode` を必須にしたのと同じ形）。
- **H2: 数え上げの陳腐化を機械で拾う。** `claims-within-evidence` 47 件のうち
  **数え上げ由来が 5 件**（「5 行」「2 箇所」「3 名」「3 種まで／ちょうど」）。
  条項本文も所々で「件数はここに書かない」と書いているが、守られない。
  提案: 一覧を持つファイル（`RAW_ONLY_KEYS` / `FS_READ_ONLY` / `HOOK_EVENTS` 等）について、
  **その件数を散文に書いたら落ちる**検査を PJ 側で持てるようにする定型を
  `guard-must-fire-on-every-class` の付録として示す。
- **H3: 差し戻し 2 回目で「前ラウンドの修正が原因か」を問う段を置く。**
  この work は 3 回目（上限）まで気づかず、デバッグ委譲で初めて構造が見えた。
  `maxSendBacks` は**回数を止めるだけで方向を変えない**と protocol 自身が書いている。
  提案: `aidev event <工程> sent_back` が **2 回目**で
  「**この指摘は前ラウンドの修正に由来するか**」を問い、Yes なら
  「直した項の**隣**を列挙したか」を促す（デバッグ委譲より軽い 1 ステップ）。
- **H4: 上流の doccheck も「2 巡目の指摘の多くが 1 巡目の修正由来」だった。**
  requirements 11→11 / design 15→10 / tasks 10→7。件数は減るが**ゼロにならない**のは、
  全面改稿が新しい不整合を作るため。review と同じ構造が上流にもある。
  提案: `protocol-check.md`「(a)」に「**修正は全面改稿ではなく最小の差分で当てる**」を
  1 行足す（改稿すると隣が壊れる、が 3 工程 6 ラウンドで一貫して観測された）。
- **H5: `design` 工程でも `aidev coverage` を打つ。**
  書式ミスが tasks まで気づかれなかった（D12）。design の skill は
  「`coverage` の `design` 列がここを読む」と注記しているのに、その工程では打たない。
  提案: `aidev-20-design` の手順に「`aidev coverage` を打って `design` 列だけ見る」を足す
  （`--strict` は tasks.md が無いので不可）。
- **H6: タスク点検は「1 タスクの差分だけ」なので、タスクをまたぐ不変条件が構造的に見えない。**
  `protocol-check.md` 自身がこの射程の限界を書いており、今回まさにそこ（`start` の 4 項が
  T8 と review 後の修正にまたがる）で 2 度失敗した。114 件を出した点検が 1 件も拾えていない。
  提案: coding の終盤に **「複数タスクにまたがる不変条件」だけを見る点検を 1 回**置く
  （全タスクではなく 1 回。`taskcheck` とは別の記録キーにする）。
