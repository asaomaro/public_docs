# 振り返り: plan モード規律の読み合わせ — 条件が 3 箇所に書かれて 1 箇所が古い

## サマリ

`d0f5ed6`（「使ってよい」から「この条件なら入れ」へ）と
`527e195`（条件を「承認者がいるか」へ）で入った plan モード規律を、
**上流工程の skill から CLI まで層をまたいで読み合わせた**。

規律そのものは 3 層（`DESIGN.md`「2.」→ `protocol-autonomous.md`「plan モードとの関係」→
`bin/aidev` の `guard` の促し）に一貫して入っており、工程の絞り込み（start / spec / design のみ）も
`allowed-tools` と一致していた。**ただし条件が 4 箇所に書かれており、うち 2 箇所が古い。**

| 層 | 条件 |
|---|---|
| `bin/aidev:929` | `profile != light` **かつ** `has_approver(phase)` |
| `protocol-autonomous.md`「plan モードとの関係」 | `light` 以外で、その工程に**承認者がいるなら**（`autonomous` でも `humanGates` に挙がっていれば承認者はいる） |
| **`aidev-20-spec/SKILL.md:35`** | **（`full` × `interactive` のみ）** |
| **`aidev-25-design/SKILL.md:50`** | **（`full` × `interactive` のみ）** |

## うまくいった点

- **条件の判定を CLI に置いた設計が効いている。** `guard spec|design` が該当条件でだけ促すので、
  散文を読み落としても促しは出る。「打つ側は工程に入る瞬間には思い出さない」という
  `bin/README.md` の見立てのとおりで、**今回のズレの実害を CLI が肩代わりして小さくしている**。
- **文面を命令形（「入れ」）にした判断が正しい。** 「方針を先に固める」のような役割だけの
  言い方だと丁寧に計画するだけでモードは切り替わらない、という整理が
  `DESIGN.md` と CLI のコメント両方に残っており、後から読んでも理由が追える。
- **除外した工程の理由が全部書いてある。** research は委譲が正、plan は `plan.md` と重複、
  coding は差し戻しが metrics に残る、と一つずつ根拠がある。
  **「使わない」側に理由があるほうが、後で足したくなったときに判断できる。**
- **`allowed-tools` と散文が一致している。** `EnterPlanMode` / `ExitPlanMode` を持つのは
  `aidev-00-start` / `aidev-20-spec` / `aidev-25-design` の 3 つだけで、
  「入らない」と書かれた工程は道具自体を持っていない。**散文だけの禁止になっていない。**

## 課題 / 手戻り

### 1. 条件の直し残し（`spec` / `design` の SKILL.md）

`527e195` が spec / design の SKILL.md に対して行ったのは `allowed-tools` への
`EnterPlanMode` / `ExitPlanMode` の追加だけで、**本文の条件は `d0f5ed6` 時点の
`（full × interactive のみ）` のまま**になっている。

`has_approver()`（`bin/aidev:180`）は `mode != autonomous`、または `humanGates` に
その工程が含まれるとき真。`profile` は `full|light` の 2 値なので前半は等価だが、
後半が食い違う。

**`mode: autonomous` + `humanGates: [spec]` の部分自律で、CLI は促すのに
SKILL.md を読んだエージェントは「`interactive` のみ」と読んで入らない。**
これは `bin/README.md` が「実走で実測した」と記録している構成そのもので、
CLI 側は直したが skill 側の文言が残った形。

実害は CLI の促しが肩代わりするぶん小さいが、**`guard` の出力を見落とした場合と、
CLI を通さず skill だけを読んで進める場合に効く**。

### 2. 条件が 2 箇所に書かれていること自体が原因

**この直し残しは「条件を skill に書いた」時点で予約されていた。**
条件が変われば 3 ファイル（CLI・散文・skill × 2）を揃って直す必要があり、
今回は 2 つが取り残された。

同じ構造の問題を、このハーネスは既に一度解いている。
`lint-docs.sh:199` に「各 SKILL の doccheck 行 +3（**正典は protocol-check。
ここは引き金と打つコマンドだけ**）」と書かれている——**doccheck では条件を skill に書かず、
引き金とコマンドだけを置いた**。plan モードだけ同じ扱いになっていない。

### 3. lint が条件のズレを見ていない

`lint-docs.sh` は行数予算と経路の存在を見るが、**同じ条件が複数箇所に書かれて
食い違っていることは検査していない**。`527e195` は lint を触っているが、
今回のズレは通過している。

## 改善提案

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

- **提案 1（本命）: spec / design の SKILL.md から条件を消し、`protocol-autonomous.md` を正典にする。**
  doccheck で採った形（`lint-docs.sh:199`）と同じにする。skill には引き金だけを残す:

  ```
  - 有力な案が複数あるなら、**`spec.md` を書く前に plan モードへ入る**
    （入る条件は `protocol-autonomous.md`「plan モードとの関係」。`aidev guard spec` が該当時に促す）。
  ```

  条件の写しを消すので**次に条件が変わっても直し残しが起きない**。
  行数も減る（`light` 以外で承認者がいるとき、という条件を skill に書くと 2 行かかる）。

- **提案 2（提案 1 を採らない場合）: 文言を現行条件に合わせる。**
  `（full × interactive のみ）` → `（light 以外で、その工程に承認者がいるときのみ。
  autonomous でも humanGates に挙がっていれば承認者はいる）`。
  **ただし条件が 3 箇所に残るので、同じ直し残しがまた起きる。**

- **提案 3: lint に「条件の写しを作らない」検査を足す。**
  `full` × `interactive` のような**条件式が実行時文書に現れたら WARN** する、
  あるいは `guard` が判定に使うキー（`profile` / `mode` / `humanGates`）が
  SKILL.md 本文に現れたら WARN する。
  **条件の正典を 1 箇所に保つのは規律ではなく検査で守るべき**——今回、
  規律（doccheck で採った形）は既にあったのに守られなかった。

- **提案 4: 外部レビューの指摘を入れる口が無い。**
  この文書は work の retro ではなく、別セッションからの読み合わせによる指摘だが、
  `retro/` は `.aidev/works/*/retro.md` の公開写しを置く場所として運用されている
  （既存 2 件はどちらも `出典:` にコミットを持つ）。
  **work に紐づかない指摘の置き場が定義されていない**ので、
  `aidev-util-insights` の集計にも入らない。置き場を決めるか、
  「母集団外」と明示する印を持たせるのが妥当。

  **ここはズレていない**。条件を写さなければズレない、という提案 1 の裏付けでもある。
- 動作は確認していない（読み合わせのみ）。`guard` を実際に部分自律の work で走らせた検証ではない。
