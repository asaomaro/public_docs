## 課題 / 手戻り

### 指摘 9 件の出どころと、どの段で防げたか

| # | 指摘 | 出どころ | 防げた段 |
|---|---|---|---|
| 1 | [must] 拡張子を足した先の**既存ファイルを黙って上書き** | 組み込みレビュー | **spec** |
| 2 | [must] `✕` がキーボードで押せない | 自分 | coding / test |
| 3 | [should] 最後の様式を消すと焦点が body に落ちる | 組み込みレビュー | coding |
| 4 | [should] 様式名の大文字小文字が食い違う | 組み込みレビュー | coding |
| 5 | [should] `recordAt` の選択優先が広すぎた | 自分 | spec → coding |

**5 件中 3 件を自分の点検では見つけられなかった。** どれも「押すと分かるが読んでも気付きにくい」形。

### 原因 1: コメントで主張したことを、テストしていなかった（#2 / #3）

2 件とも**自分で書いたコメントが嘘になっていた**。

- `✕` に「見出しの中に置くので Tab で届き、マウス専用にはならない」と書いたが、
  見出しの `keydown` が Enter を横取りして**押せなかった**。
- `pendingRecordFocus` に「見つからなければ…`＋` へ戻す」と書いたが、
  その分岐は**到達不能**だった（`pendingSelectRecord` が `undefined` になって手前で飛ぶ）。

コメントを書いた時点で「これは検証可能な主張か」を問えば、どちらも e2e 1 行で塞げた。
**要件には AC-I3（キーボードだけで完結）と AC-I4（焦点の行き先）があり、
test 工程で e2e も書いた。それでも漏れた**のは、書いたのが**幸せな経路だけ**だったから
——`＋` は試したが `✕` は試さず、「隣へ移る」は試したが「隣が無い」は試さなかった。

### 原因 2: 変換は試したが、その帰結を試していなかった（#1）

`createDdsFile` には単体 6 件を書いていた。「拡張子が無ければ足す」も試している。
試していなかったのは**足した先に既にファイルがあったら何が起きるか**。

`showSaveDialog` が衝突を見るのは利用者が打ったパスだけなので、
`CUSTMNT` と打つと `CUSTMNT.dspf` が**確認なしで 2 行の雛形に置き換わる**。
開いていないファイルなので undo も無い。**この PJ でいちばん重い種類の欠陥**を、
自分の点検も、書いたテストも通していた。

spec の段で「この操作の取り消しは何が担うか」を問うていれば出た。
実際、requirement / spec は削除について「undo が担う」と何度も書いており、
**新規作成についてだけその問いを立てていなかった**。

### 原因 3: 「戻して落ちる」で、戻すものを取り違えた

#3 の確認で、最初に `?? null` を外したがテストは通ったままだった。
実際に効いていたのは**フィールドの分離**（`pendingSelectRecord` / `pendingRecordFocus`）で、
そちらを戻して初めて落ちた。

AGENTS.md は「テストを足したら、直す前の状態に戻して落ちることを確かめる」としているが、
**「直す前の状態」が複数の変更に散っているとき、どれが効いているかは自明でない**。
今回は気付けたが、1 回で通っていたら「守られている」と誤認していた。

### 差し戻しの記録が実態とずれた

review で must/should が出たので `sent_back` → coding → test を踏み直したが、
**修正そのものは review 工程の時間帯に済んでいた**（レビューしながら直した）。
結果、記録上は coding も test も 0 秒で、review は 120 秒になっている。

**AI がレビュアーと実装者を兼ねると、この形は毎回起きる。**

### 承認ゲートを飛ばして approve を打った

review 工程で、ユーザーに提示する前に `aidev approve review` を実行した。
気付いて state と metrics を戻したが、**CLI は何も言わなかった**——
`approve` は「人が承認したか」を知らない。これは散文規約（protocol「3.」）でしか守られていない。

## 改善提案

### 製品 / コード（→ backlog に追加）

1. **PRTF の雛形にファイル・レベルの行が無く、`LPI` / `CPI` をデザイナから足せない。**
   DSPF は `DSPSIZ` があるので足せる。ファイル・レベルの行を**作る**手段がデザイナに元から無い
   （既存の行を直せるだけ）ことが本体。→ `dds.md`
2. **統合テストの緑は webview が描けている根拠にならない。**
   `npm run test:integration` は `npm run compile`（tsc のみ）しか走らせないので、
   束ねた資産（`out/dds-webview`）が無くても通る。実際に
   `Webview.loadLocalResource - Error using fileReader` が出ているのに 3 件とも緑だった。
   → `workflow.md`

### PJ プロセス / 規約（→ AGENTS.md への追補案）

**A. コメントが振る舞いを主張したら、その主張はテストの対象**（原因 1・指摘 2 件が根拠）

> 「Tab で届く」「見つからなければ `＋` へ戻す」のように**コメントが利用者から見える振る舞いを
> 主張したら、その主張が成り立つことを検査で固定する**。この PJ のコメントは判断の理由を書く
> ものが多く、そこに書いた「こうなる」は**読み手が確かめずに信じる**。
> 実際、`20260908-dds-new-and-records` では 2 件とも主張が嘘で、片方は到達不能な分岐だった。

**B. 相互作用の受け入れ基準は、幸せな経路の外まで書く**（原因 1 が根拠）

> AC-I3 / AC-I4 のような相互作用の基準を立てたら、**その基準が壊れる側**も併記する
> ——「`＋` はキーボードで押せる」なら `✕` も、「削除したら隣へ移る」なら**隣が無いとき**も。
> 基準があっても幸せな経路しか書かなければ、検証もそこで止まる。

**C. 取り消せない操作を作ったら、そこだけ確認を出す**（原因 2 が根拠）

> この PJ は「即座に実行して undo で戻す」で統一しており、確認ダイアログを置かない。
> ただしそれは*取り消せる操作*の話。**ファイルの上書き・外部への送信のように
> 取り消しの受け皿が無い操作**を足したときは、そこだけ確認を出す。
> 新しい操作を作ったら「この取り消しは何が担うか」を必ず答える。

**D. 「戻して落ちる」は、直した行ではなく効いている判断を戻す**（原因 3 が根拠）

> 修正が複数の変更に散っているとき、**どれが効いているかは自明ではない**。
> 戻して通ってしまったら「テストが弱い」ではなく「戻す先を間違えた」を先に疑う。

> **いずれも `[conv:-]`（該当条項なし）由来**——「規約はあるが守られていない」型ではないので、
> 条項として起こす価値がある。ただし**適用は人が決める**（この工程は提案まで）。

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

**1. レビュアーと実装者が同一のとき、差し戻しの記録が実態を表せない**

いまの手順は「`sent_back` を打つ → coding をやり直す」順を前提にしているが、
AI は**レビューしながら直す**ので、記録は後追いになり `coding` / `test` が 0 秒になる。

- 案 (a): `sent_back` に「修正はこの工程の中で行われた」印を持たせ、
  `metrics` が elapsed を review 側に寄せる。
- 案 (b): 0 秒の工程ブロックを `verify` が WARN で知らせ、retro が読めるようにする
  （直さずに「読めない」と分かるだけでも足りる）。

**2. 承認ゲートは CLI が守れない**

`approve` は「人が承認したか」を知らないので、飛ばしても通る（実際に一度飛ばした）。
完全には塞げないが、**`interactive` の work で `approve` を打つとき、
直前に `AskUserQuestion` 相当が無ければ注意を出す**程度は考えられる。
少なくとも**そういう限界がある**ことを protocol に明示したい。
