# 振り返り: plan モードの判断基準 — 前提が 1 つ書かれていない

## サマリ

`plan` 工程に plan モードが適用されていない件を、**適用すべきかどうか**として調べた。
結論は **除外は正しい**。`protocol-autonomous.md`「plan モードとの関係」の判断基準
（二重ゲートに見合うか）と、`plan` の除外理由（方針と成果物が分離できない）は妥当である。

**ただし基準には前提が 1 つあり、それが書かれていない。**
「既存のゲートが**機械で強制されている**」——aidev では `guard` の exit code と
metrics の承認記録がそれを担うので成立しているが、**基準の文面からは導出できない**。

## うまくいった点

- **列挙から基準へ移した判断が効いている。** 「実装計画かどうか」を基準にしていた頃の
  誤り（plan モードで禁じられるのは Write / Edit だけで対話は動く）を自分で見つけ、
  「plan モードで承認するものが、ゲートが承認するものと違うか」へ置き換えている。
  **列挙は網羅を検査できないが、基準は導出できる**という整理は、今回の指摘もその上に乗っている。
- **上流のゲートまで含める、という但し書きが要点になっている。** これが無いと
  coding が「入る」に化ける、と明記されている。実際、この但し書きを外して読むと
  `tasks.md` が承認済みであることを見落とす。
- **`research` を「基準の外の規則で外す」と分けて書いてある。** 基準で落ちるものと、
  別の規則で落ちるものが混ざっていない。**基準の適用範囲が自分で分かる形**になっている。

## 課題 / 手戻り

### 1. 基準が「既存ゲートは強制されている」を前提にしているが、書かれていない

基準は「同じものを承認するなら二重だから**入らない**」と結論する。
だがこの結論は、**既存のゲートがちゃんと止まることを前提にしている**。
止まらないゲートなら、同じものを承認することは二重化ではなく——

**plan モードが**ゲート**そのものになる**（Write / Edit が塞がるので、
承認前に次工程の成果物を書けない）。

aidev ではこの前提が成立している:

| ゲートを止めているもの | 実体 |
|---|---|
| `aidev guard <phase>` | 前提未充足なら非ゼロ終了 |
| `metrics.yml` の承認記録 | `verify --strict` が欠落を検出 |
| `AskUserQuestion` の 4 択 | 承認と遷移を人間が選ぶ |

**だから aidev では「除外」が正しい。** 問題は、**基準の文面からその理由が出てこない**ことである。
文面は「承認するものが同じか」しか見ておらず、**「既存ゲートが実際に止まるか」を見ていない**。

### 2. 前提が崩れる場面が実在する（外部で実測）

同じ基準を、**ゲートが散文だけのハーネス**に当てたところ、同じ「除外」を出した。
（別リポジトリの教材用 SDD キット。6 つの skill だけで CLI を持たず、
「次に進まずユーザーの指示を待つ」と書いてあるだけで、守らなくても何も起きない。）

そこでは**逆の結論が正しい**。plan モードは二重化ではなく、
**存在しないゲートを実体化する**からである。**基準は同じ答えを出したが、答えるべき答えは違った。**

これは移植先の話に見えるが、**aidev 自身にも効く**:

- 将来、**承認ゲートを持たない工程**が増えたとき（`aidev-util-*` 系や、`profile` の
  新しい値で承認を省く工程）、基準は「除外」を出すが、それが正しいとは限らない。
- **ハーネスを他エージェントへ移すとき**（`aidev-docs/README.md` はサーフェス表を持っており、
  移植は想定内）、`guard` が動かない環境では前提が崩れる。

### 3. これは「結論は同じだが理由が違う」型の再来

`DESIGN.md`「2.」に、この型の教訓が既に書かれている——
**「結論は変わらないが、理由が変わると次に工程が増えたときの判断が変わる」**。
今回はその 1 段外側で、**前提が書かれていないと、前提が崩れたときに基準が黙って誤答する**。

## 改善提案

### ハーネス自体（→ `aidev-*` への提案・適用は人間）

- **提案 1: 基準に前提を 1 行足す。** `protocol-autonomous.md`「plan モードとの関係」の
  「判断基準は『二重ゲートに見合うか』」の直後に、次を加える:

  ```
  この基準は**既存のゲートが機械で止まること**（`guard` の exit code と metrics の承認記録）
  を前提にする。**止まらないゲートしか無い工程では、plan モードは二重化ではなく
  ゲートの実体化になる**ので、同じ基準から逆の結論が出る。
  ```

  2 行で、`plan` / `coding` の除外は変わらない。**変わるのは、前提が崩れたときに
  基準が黙って誤答しなくなること。**

- **提案 2（提案 1 を採るなら不要）: 除外の一覧に前提を書く。**
  「入らない」の各項目に「（ゲートが `guard` で止まるため）」を添える形。
  ただし**列挙に戻すことになる**ので、基準側に置く提案 1 のほうが筋が良い。

- **提案 3: lint で検査できるものではない。** 前提の欠落は文面の整合では捕まらない。
  L9 のような機械検査は作れないので、**基準を読み直す機会**（工程が増えたとき・
  移植のとき）に当てる規約として置くしかない。**検査できないことを明示して置く**のが
  この提案の扱いだと考える。

## 補足

- **`plan` 工程への plan モード適用は提案していない。** 「方針と成果物が分離できない」は
  正しく、`plan.md` を書く前に方針を承認すると計画を二度書くことになる。
  調べた結果として、**現行の除外は妥当**と結論した。
- **動作は確認していない**（読み合わせのみ）。基準を別ハーネスに当てて逆の結論が出ることは
  確かめたが、aidev 側で前提が崩れる工程を実際に作って試した検証ではない。
- 指摘の出どころは、`plan` モードを「ゲートに**足す**」のか「ゲート**そのものにする**」のかを
  区別する問いだった。**基準はこの区別を持っていない。**
