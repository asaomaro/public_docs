# GitHub Copilot フィーチャー分類（講習設計用 参照資料）

> **この資料の使い方**
> カリキュラムで「何を扱い、何を外すか」を判断するための一覧です。網羅性を重視し、忘れがちな要素も拾っています。
>
> 資料は4つの軸で構成されています：**①フィーチャー（機能）** を初級・中級・上級に分類、**②補助トピック**（ライセンス等の前提）、**③AIの特性**（LLMの挙動原理＝操作の「なぜ」を支える土台）、**④概念・用語・方法論**（考え方）。各項目に **概要** と **講習での扱い所感**（この講習＝未経験〜中堅混在・ゴールは「AI開発の全体像を掴む」を前提）を添えています。
>
> 分類の軸は「**個人がCopilotを使えるようになる**ための習熟度」。初級＝AIに使われる側として触れる入口、中級＝意図的にAIを御する技術、上級＝AIの基盤・ワークフローを設計する側。上級に行くほど「道具の使い方」から「基盤の作り込み」へ移り、未経験者の射程からは外れます。
>
> ⚠️ **更新の速い領域です。** 機能名・UI・ファイル仕様（特にエージェント／カスタマイズ周辺）はIDEとバージョンで差があり、頻繁に変わります。実際に扱う前に最新の挙動を確認してください。

---

## 凡例（講習での扱い所感のラベル）

- **◎ 核**：未経験者含め全員に体験させたい中核
- **○ 推奨**：本編に織り込む価値あり（多くは独立回不要、既存回に一コマ）
- **△ デモ/一言**：手を動かさせず「見せる」「名前を出す」程度
- **▲ 外縁/任意**：本筋から外し、地図の外縁で名前を挙げるか、中堅の自習・発展に委ねる
- **× 対象外**：この講習の射程外（enterprise専用・基盤運用寄りなど）

## 初級 — AIに「使われる側」として触れる入口

最も自律度が低く、人間が一手ずつ確認できる。未経験者がAIに慣れ、「日本語で指示すれば動く」を体感する層。

### インライン補完（コード補完 / Ghost text）
- **概要**：入力中にAIが続きを予測し、Tabで受け入れる。複数候補の切り替え可。最も軽量で人間主導。
- **扱い所感**：**◎ 核**。AIとの最初の接点。良いコメント・命名が精度を上げる仕組みまで見せる。

### Next Edit Suggestions（次の編集の予測）
- **概要**：今の編集の次に直しそうな箇所を予測し、補完を提案する。補完の発展形。
- **扱い所感**：**○ 推奨**。補完回のデモの一コマで「次の一手まで読む」と見せる程度。独立項目は不要。

### Copilot Chat（チャット）
- **概要**：コーディングの質問、コード説明、リファクタ依頼、エラー相談ができる対話パネル。IDE・GitHub.com・モバイル等で利用可。
- **扱い所感**：**◎ 核**。補完との使い分けが要。「読めば分かる提案／鵜呑みにできない提案」の区別を育てる。

### Inline Chat（インラインチャット）
- **概要**：パネルではなくコード上でその場でチャットを呼び出す。流れを切らずに依頼できる。
- **扱い所感**：**○ 推奨**。チャット回で「呼び出し方が二つある」と見せるだけで十分。

### 組み込みスラッシュコマンド（/tests, /fix, /explain, /doc 等）
- **概要**：定型タスクのショートカット。GitHubが用意した定型プロンプトに展開される。出力が安定する一方、PJ固有規約は知らない。
- **扱い所感**：**◎ 核**。「コマンドあり/なし」「コマンド/自然言語」の使い分けを教える格好の素材。

### コンテキスト変数（#-mention：#file, #selection, テスト失敗 等）
- **概要**：チャットにファイル・シンボル・選択範囲・コミット・テスト失敗などを明示的に文脈として渡す。
- **扱い所感**：**○ 推奨**。「AIに何を見せるか」の実践そのもの。チャット／コマンド回で扱う。

### 言葉以外の指示（画像・スクショ・お手本・入出力例）
- **概要**：画面デザイン画像から実装、エラー画面のスクショから修正、既存コードをお手本に、期待する入出力例を提示、手書きスケッチ、図(mermaid)など。マルチモーダル＆コンテキスト設計の入口。
- **扱い所感**：**◎ 核**。「指示とは言葉だけでなくAIに何を見せるかの設計」という学び。各回に散らす。画面デザイン実装は幅と実習を兼ねる目玉。

### スマートアクション（Code Actions 等の提案）
- **概要**：エディタ上にAIが修正提案を電球アイコン等で出す。問題箇所のワンクリック修正。
- **扱い所感**：**△ デモ/一言**。補完・チャット回のついでに「こういう提案も出る」と見せる程度。

## 中級 — AIを「意図的に御する」技術

人間が主導権を保ちつつ、自律度の高い道具を使い、検証を上流に動かしていく層。中堅が手を動かして価値を出す中心帯。

### エージェント（Agent mode）
- **概要**：高レベルの指示を出すと、AIが対象ファイルを判断し、実装・テスト・エラー解消・ターミナル実行までを自律的に反復。単一応答で止まらず、目標達成まで回す。差分は承認制。
- **扱い所感**：**◎ 核**（後半の主役）。まず万能感を体感→内部を分解して見せる→出力を疑う、の流れ。工程が不可分になるため学び方が「視点軸」に切り替わる起点。

### マルチファイル編集と差分レビュー
- **概要**：複数ファイルにまたがる変更を一括で行い、差分をまとめて確認・採否できる。チェックポイントからの巻き戻しも。
- **扱い所感**：**○ 推奨**。エージェント回で「目視できない規模をどう検証するか」を体験させる。

### Plan モード
- **概要**：実装前に計画（手順の要約・ステップ分解・確認質問）を提示し、人間が承認してから実行に移す。検証タイミングを「事後」から「実行前」へずらす。
- **扱い所感**：**◎ 核**。「素直な指示の事後検証は重い」を体験した後に導入すると因果が腑に落ちる。

### サブエージェント（subagent への委譲）
- **概要**：チャットセッション内で、独立したコンテキストを持つサブエージェントにタスクを委譲。ユーザー介入なしに自律実行し結果を返す。調査・分析などの委譲向き。
- **扱い所感**：**△ デモ/一言**。operateは重い。エージェント回の発展デモで「AIが分担して進める」様子を"見せる"のはあり。

### instructions.md（copilot-instructions.md / *.instructions.md）
- **概要**：リポジトリ全体や特定言語・フォルダに「常に効く規約」をMarkdownで宣言。Copilotが文脈に応じ自動で参照する。`/init`でAI生成も可。
- **扱い所感**：**○ 推奨**。「規約を仕組みに落とす」最も素朴な実装。Spec Kitのconstitutionと同じ思想。規約のファイル化の回で最小限体験。

### AGENTS.md
- **概要**：エージェントに常時効く指示を置く標準的ファイル（CLAUDE.md等と同系統）。instructionsと役割が重なる。
- **扱い所感**：**○ 推奨**。instructions.mdと併せて「規約のファイル化」として一度触れれば思想は伝わる。両者の細かい使い分けに深入りは不要。

### プロンプトファイル（.prompt.md）/ カスタムスラッシュコマンド
- **概要**：頻用プロンプトを`.prompt.md`として保存し、`/名前`で呼び出す再利用可能な定型指示。チームで共有可。instructionsが「常に効く規約」なのに対しこちらは「呼び出して使う手順」。
- **扱い所感**：**○ 推奨**。instructionsと対で「規約の固定」と「手順の再利用」の区別を見せる。

### カスタムチャットモード（.chatmode.md）
- **概要**：Copilot Chatに特定のペルソナ・役割（テスト用、セキュリティレビュー用など）を持たせ、応答や使えるツールを限定・調整する。
- **扱い所感**：**△ デモ/一言**。「AIに役割を与える」発想はinstructions/プロンプトファイルで伝わる。中堅向け発展デモ止まり。

### カスタマイズ生成コマンド（/init, /create-instruction, /create-prompt 等）
- **概要**：カスタマイズ自体をAIに作らせる。`/init`でinstructions雛形、`/create-*`で各種カスタマイズの雛形をAI補助生成。
- **扱い所感**：**○ 推奨（一言）**。「規約ファイルも手書きせずAIに書かせられる」の一言で未経験者の心理的ハードルを下げる。

### SDD（Spec-Driven Development / Spec Kit）
- **概要**：仕様を先に固め、それを起点に実装を生成する手法。Spec Kitは Specify→Plan→Tasks→Implement の4フェーズをスラッシュコマンドで提供。constitution（不変の原則）でPJ規約を固定。
- **扱い所感**：**◎ 核**（後半の到達点）。検証点の最上流＝仕様段階。概念紹介に最適。CLI導入が未経験者の障壁なので、環境配布かデモ主体が安全。

### Copilot memories
- **概要**：チャット中に好みを自動検知し、指示ファイルに追記して手書きの手間を省く。
- **扱い所感**：**△ デモ/一言**。便利だが副次的。触れるなら一言。

## 上級 — AIの「基盤・ワークフローを設計する」側

エージェントをoperateできる前提の上に乗る、基盤設計レイヤー。日常的に作るのは一部の人で、未経験〜中堅の「全体像」の射程外。多くは名前を見せる程度でよい。

### Agent Skills（SKILL.md）
- **概要**：複数ステップの手順・スクリプト・テンプレートを「スキル」としてパッケージ化し、タスクが一致したときAIが必要に応じて読み込む（progressive disclosure）。
- **扱い所感**：**▲ 外縁/任意**。再利用可能な手順の自作は基盤設計寄り。最終盤で名前を挙げる程度。中堅の発展に委ねる。

### カスタムエージェント（*.agent.md / custom agents）
- **概要**：特定のツール・指示・MCPサーバーにアクセスする専用エージェント（コードレビュアー、プランナー等の役割）を定義。
- **扱い所感**：**▲ 外縁/任意**。複数AIの役割設計。中堅の興味次第。本筋には入れない。

### MCP（Model Context Protocol）サーバー
- **概要**：外部ツールやデータソースにCopilotを接続する仕組み。多くのCopilot機能でMCPサーバーを構成できる。
- **扱い所感**：**▲ 外縁/任意**。基盤設計レイヤーだが**開発でも実用的**（例：Atlassian MCPでチケットを読み取りSDDのrequirement工程に渡して起点を自動化／Playwright MCPでブラウザ操作によるE2Eテスト）。ただし使いこなしにはMCPサーバー構成・認証・ワークフロー接続の前提が積み上がり、未経験〜中堅が日常的に構成する層ではない。**最終盤の地図の外縁で名前を挙げ、上記の具体例を一言添える**のが適量——抽象的なMCPの説明が「開発に効く具体像」に変わり、道標になる。「AIを社内システムやツールにつなぐ仕組みもある」程度から、具体例で深さを足す。

### Hooks
- **概要**：MCPと併せ、外部サービスやカスタムアクションでAIを拡張する仕組み。特定タイミングで処理を差し込む。
- **扱い所感**：**× 対象外**。基盤設計レイヤー。本筋から外す。

### Cloud Agent / Coding Agent（クラウドの自律エージェント）
- **概要**：リポジトリを調査し実装計画を立て、ブランチ上で変更する自律エージェント。GitHub issueを割り当てたり、PRを直接作らせたりできる。ローカルのagent modeより一段自律的。
- **扱い所感**：**▲ 外縁/任意**。基盤・運用寄り。最終盤の地図の外縁で名前を出す程度。

### 第三者コーディングエージェント
- **概要**：Cloud agentと並んで使えるサードパーティ製エージェント。同等のセキュリティ保護・制約下で動く。
- **扱い所感**：**× 対象外**。本講習の射程外。

### Copilot CLI
- **概要**：ターミナルでCopilotを使うCLI。機能追加やバグ修正をしてPRを作成。GitHub.comやモバイルへセッションを継続可。
- **扱い所感**：**▲ 外縁/任意**。VSCode中心の本講習では外す。中堅の自習で十分。

### Copilot Spaces
- **概要**：コード・ドキュメント・仕様などを Spaces に集約し、特定タスク向けにCopilotの応答を文脈づける。主にenterprise向け。
- **扱い所感**：**× 対象外**。enterprise寄りで全体像には不要。

### Copilot Spark
- **概要**：自然言語プロンプトでフルスタックアプリを構築・デプロイし、GitHubプラットフォームと統合する。
- **扱い所感**：**× 対象外**。本講習の範囲を超える。

### カスタマイズ評価（Chat Customizations Evaluations / Waza）
- **概要**：instructions・プロンプト・スキル・エージェントの各カスタマイズファイルの品質を分析し、曖昧さ・矛盾・過剰な複雑さを検出。スキルはテストケースに対する性能を計測。
- **扱い所感**：**× 対象外**。カスタマイズを作り込むチーム向けのメタな道具。本筋から外す。

### PRレビュー支援 / PR要約（GitHub.com側）
- **概要**：PRの変更要約、影響ファイルの抽出、レビュー観点の提示、AIによるコードレビュー提案。
- **扱い所感**：**▲ 外縁/任意**。GitHub.com側の機能。開発フロー全体の話として最終盤に一言、または中堅の発展に。

## 補助トピック（フィーチャーではないが講習設計に関わる前提）

### モデル選択
- **概要**：Copilotは複数のAIモデルから選べる。タスクやツール呼び出し対応で使い分け。
- **扱い所感**：**△ デモ/一言**。「裏のモデルを選べる」程度に触れる。深入り不要。

### ライセンス / プラン（Free / Pro / Business / Enterprise）
- **概要**：プランで使える機能・割り当てが異なる。
- **扱い所感**：**【要事前確認】**。2026年4月20日以降、Pro・Pro+・Max・Studentの新規サインアップが一時停止、Proトライアルも停止中（時期情報は要再確認）。受講者のライセンス手配（Freeで足りるか、Business等が要るか）を講習前に必ず確認。

### 土台スキル（Git / Markdown / VSCode）
- **概要**：Copilot以前の現代開発の共通基盤。本講習では未経験者向けに土台編として扱う（GitはVSCode内蔵GUIで最小セット、Markdownは記法＋mermaidは顔見せのみ）。
- **扱い所感**：**◎ 核**（未経験者の生命線）。削ると未経験者が脱落する。土台編のGitは**コミット・履歴・同期の最小セットのみ**。ブランチ以降は後回し（下記PR運用の項参照）。

### PR運用 / ブランチ（GitHub Flow）
- **概要**：AIとは直接関係しないが、現代のチーム開発の常識。作業ブランチを切り、変更をPR（プルリクエスト）にまとめ、レビューを経てmainにマージする。mainへの直接コミットは避ける。Copilotのagent mode/SDD/自作ハーネスの **deliver（着地）工程は、いずれもPR作成で終わる**。
- **扱い所感**：**◎ 核（ただし後半で導入）**。土台として必須だが、土台編のGit（コミットのみ）と整合させるため、**ブランチ＋PRは講習後半の「AIの成果物を着地させる文脈（deliver）」で初めて導入する**のが自然。これによりPRが「**AIの成果物を人間が検証して受け入れる関所**」として位置づき、本講習の地の思想（成果物を引き受ける判断・要所に人間を置く）の制度的な体現になる。
  - **最小セット**（未経験者向け）：「作業はブランチで」「変更はPRにまとめる」「レビューを経てmainへ」「mainに直接コミットしない」。
  - **深入りしない**：マージ戦略（squash/rebase/merge commit）、ブランチ保護ルール、レビューコメントの細かい作法、CI連携は中堅の発展か対象外。
  - **Copilot連携**：コミットメッセージ・PR本文・PR要約はCopilotに生成させられる（土台学習が同時にCopilot体験になる）。

## AIの特性（LLMの挙動原理 — 操作の「なぜ」を支える土台）

機能でも方法論でもない第三の軸。Copilotの裏で動くLLMの挙動特性。**これを知らないと「なぜ指示を工夫するのか」「なぜ出力を疑うのか」が腑に落ちない**。本編の各回の操作（指示の工夫・出力の検証）と一対一で対応するので、土台編〜前半のどこかで一度まとめて、あるいは各回で関連する特性に都度触れると効果的。深い理論は不要で、「そういう癖がある」と知るだけで指示と検証の質が変わる。

### トークン（入力・出力）
- **概要**：LLMはテキストを「トークン」（おおよそ単語の0.5〜1個分の断片）の列として扱う。入力も出力もトークンで数える。処理量・コスト・速度の基本単位。
- **講習での意義**：「AIは文字でなくトークンで読む」「入力にも出力にも上限がある」を知ると、長すぎる入力や一度に大量生成させることの限界が理解できる。**◎ 基礎**。

### コンテキストウィンドウ（文脈長）
- **概要**：一度に処理できるトークンの最大量。これを超えると古い情報が押し出され、性能が劣化する。近年は数十万〜数百万トークンへ拡大したが、「入る」ことと「全部に注意が向く」ことは別。
- **講習での意義**：「AIは無限に覚えていられない」「長い会話やコードを際限なく詰めると抜ける」を理解。長いセッションで指示を見失う現象の説明になる。**◎ 基礎**。

### Lost in the Middle（中盤の見落とし）
- **概要**：長い文脈では、冒頭と末尾の情報はよく使われるが、中盤に埋もれた情報は見落とされやすい（U字型の精度カーブ）。文脈窓が大きくなっても構造的に残る、Transformerの注意の偏り。2026年時点でも完全には解消されていない。
- **講習での意義**：実践に直結。**重要な指示・参照情報はプロンプトの末尾（または冒頭）に置く**、長文を際限なく詰めない、という工夫の根拠になる。「全部入れたのに無視された」現象の正体。**○ 実践的**。

### Chain of Thought（思考の連鎖 / 段階的推論）
- **概要**：「順を追って考えて」と促すと、途中の推論ステップを言語化し、複雑な問題の正答率が上がる。一足飛びに答えさせるより、過程を踏ませる方が精度が出る。
- **講習での意義**：「段階的に考えさせる」「いきなり結論でなく筋道を出させる」という指示の工夫の根拠。plan モードやSDDが「いきなり実装せず段階を踏む」のも、この特性と地続き。**○ 実践的**。

### ロール指定（役割・ペルソナ付与）
- **概要**：「あなたは経験豊富なテストエンジニアです」のように役割を与えると、その立場に沿った観点・語彙・厳密さで応答する傾向。出力の方向づけに使える。
- **講習での意義**：指示の工夫の一つ。カスタムチャットモードやinstructionsで「役割を固定する」発想の入口。ただし万能ではなく過信は禁物、と添える。**○ 実践的**。

### ハルシネーション（もっともらしい誤り）
- **概要**：事実でない内容を、自信ありげに生成する現象。**設計上の副産物**——学習・評価が「分かりません」より自信ある推測を報酬づけるため、モデルは推測するよう学ぶ。文脈に正しい情報がなければ起きやすい。単一の対策で消せず、検証が必須。
- **講習での意義**：本講習の地の思想（出力を疑う）の科学的根拠。「動くが間違っている」「もっともらしい嘘」を見抜く必修リテラシー。**◎ 核**。

### 確率的・非決定的な出力
- **概要**：LLMは確率的に次のトークンを選ぶため、同じ入力でも毎回同じ出力とは限らない。temperature 等の設定で「確実性 vs 多様性」が変わる（低いと安定、高いとばらつく）。
- **講習での意義**：「同じ指示でも結果が変わる」「コマンドの方が自然言語より安定する」現象の説明。再現性を求める場面と発想を広げたい場面の使い分けに繋がる。**○ 実践的**。

### 知識のカットオフと最新情報の弱さ
- **概要**：モデルは学習時点までの知識しか持たず、それ以降の出来事・最新ライブラリ・バージョンは知らない（検索やツール連携で補わない限り）。
- **講習での意義**：「AIは最新を知らない」「新しいライブラリの使い方を堂々と間違える」ことの理解。ドキュメントを読ませる・検索させる工夫の動機。**○ 実践的**。

### 計算・厳密処理の苦手さ
- **概要**：正確な算術、桁の多い計算、厳密なカウントなどは、言語モデル単体では誤りやすい（ツールやコード実行で補える）。
- **講習での意義**：「AIは計算機ではない」を知り、数値の絡む出力は検証する・コードに計算させる、という構えを持つ。**△ 一言**。

### 指示への過剰追従（迎合性 / sycophancy）
- **概要**：ユーザーの言うことに同調しやすく、間違った前提や誘導にも迎合して、誤りを正さず話を合わせることがある。
- **講習での意義**：「AIは肯定してくれるが、それが正しさの保証ではない」。壁打ち相手として使う際の注意。批判的な検証の動機づけ。**△ 一言**。

### 注意の偏り（冒頭・末尾への集中）
- **概要**：Lost in the Middle の背景にある、より一般的な性質。システム指示や冒頭の文脈、プロンプト末尾の依頼に注意が集中しやすい。
- **講習での意義**：Lost in the Middle と併せて「どこに何を置くか」の設計感覚に繋がる。**△ 一言**（Lost in the Middle に含めて触れてよい）。



機能ではなく、AI開発を語るための概念・用語・方法論。これらは「実装させる道具」ではなく「道具の使い方を律する思想」で、上位ほど扱う主体が「個人開発者」から「ワークフロー・組織を設計する人」へ移る。**この講習のゴール（全体像を掴む）に対しては、大半が「段階として組み込む」のは過剰で、最終盤に名前を示す程度が適量**。ただし各概念の"実質"は、用語を出さずとも本編の体験に含まれていることが多い（下記の所感参照）。

### 関心の移動：プロンプト → コンテキスト → ハーネス → ループ
AIに「何をどう伝えるか」という関心が、扱う対象を外側・上位へ広げてきた流れ。個人が順に登る習熟段階というより、**使う主体の関心が「指示文」から「基盤設計」へ移る**動き。後ろ2つ（ハーネス／ループ）は基盤設計レイヤーで、未経験〜中堅の射程外。

#### プロンプトエンジニアリング
- **概要**：単発の指示文（プロンプト）をどう書くと良い出力が得られるか、という技術。最も古く定着した概念。
- **扱い所感**：**○ 用語は出さず実質を体験**。「明確に・具体例を・段階的に」等の工夫は本編の各回で体感する。用語を前面に出す必要はない。

#### コンテキストエンジニアリング
- **概要**：単発の指示文を超え、AIに与える情報環境全体（参照ファイル・既存コード・規約・履歴）をどう設計するか。「AIに何を見せるか」が出力を決める、という発想。近年かなり定着。
- **扱い所感**：**○ 用語は出さず実質を体験**。`#file`でのコンテキスト付与、画像・お手本・入出力例による指示、instructions/SDDでの前提注入——本編で繰り返し体験する。中堅には用語を示す価値あり。

#### ハーネスエンジニアリング
- **概要**：AIエージェントが働く「足場（harness）」——規約・ツール・実行環境・ガードレール——を設計する技術。AGENTS.md、カスタムエージェント、スキル、検証ゲート等で、AIが安定して働く土台を組む。
- **扱い所感**：**▲ 外縁/任意**。基盤設計レイヤー。用語はまだ流動的。実質はinstructions/AGENTS.md/規約のファイル化で触れるので、最終盤に「これをハーネスエンジニアリングと呼ぶ」と名前を出す程度。中堅の発展学習の道標。

#### ループエンジニアリング
- **概要**：AIを反復的に回し、検証を挟みながら収束させる仕組み（実装→テスト→修正→レビューの自律ループ等）の設計。最も新しく、業界で意味が固まりきっていない用語。
- **扱い所感**：**▲ 外縁/任意**。最も射程外。用語が未確立なので構造の骨格に据えるのは危うい。実質はplanモードやエージェントの実装→テスト→修正の体験に芽がある。最終盤で名前を挙げるに留める。

### SDD（Spec-Driven Development）※方法論としての側面
- **概要**：「仕様を先に固め、それを起点に実装を生成する」開発手法。フィーチャー欄のSpec Kitはその実装の一つ。手法そのものは特定ツールに依らない（CLAUDE.mdベース、OpenSpec、cc-sdd等、複数の流派がある）。
- **扱い所感**：**◎ 核（概念として）**。本講習で扱う唯一の「方法論」。検証点を仕様段階まで上流化する思想を、Spec Kitを通じて体験。承認ゲートの厳しさで流派が分かれる（緩いOpenSpec／ゲート重視のKiro系）点は中堅向けの補足。

### AI-DLC（AI-Driven Development Life Cycle）
- **概要**：AWSが提唱した、開発ライフサイクル全体とチーム構造をAI中心に再定義する方法論。Inception→Construction→Operationsの3フェーズ。「AI支援(補完止まり)とAI丸投げ(自律実行)の両極端を避け、要所に人間の承認を置く」のが核。SDDはその一部品に相当。
- **扱い所感**：**× 対象外（思想のみ残す）**。方法論レイヤーで、組織の働き方の話。Copilotの道具の範疇を超えるため固有名詞・方法論としては扱わない。**ただし背後の問題意識**（両極端を避け人間の判断を要所に置く）**は本講習の地の思想として残す**。

### grilling / 要件の深掘り（grill-me 等）
- **概要**：AIが人間を逆に問い詰めて、曖昧な意図を明示的な要件へ引き出す手法。要件確定で停止し、その先（仕様化）には踏み込まない設計が多い。
- **扱い所感**：**× 対象外（統合）**。plan/SDDのrequirements工程と「要件を詰める深さ」の違いに過ぎないため、SDDに統合し独立では扱わない。

### Vibe coding（バイブコーディング）
- **概要**：仕様を固めず、対話的に「こんな感じで」と指示して作る直感的な開発スタイル。プロトタイプや探索に有効だが、本番コードでは手戻り・技術的負債を生みやすい。SDDはこの対極として語られることが多い。
- **扱い所感**：**△ 対比で一言**。SDDの意義を説明する際の対比概念として有用。「素早い試作はvibe、作り込みはSDD」という使い分けを一言で。

### 自律度と検証責任のトレードオフ
- **概要**：AIの自律度が上がる（補完→チャット→エージェント）ほど、人間が一手ずつ確認できなくなり、検証の責任とコストが増す。本講習の後半を貫く軸。
- **扱い所感**：**◎ 核（地の思想）**。用語ではなく体験で伝える。前半→後半の道具の移行そのものがこれを体現する。

### 検証点の上流化（事後 → 実行前 → 仕様段階）
- **概要**：エージェントの素直な指示（事後検証）→ planモード（実行前検証）→ SDD（仕様段階での検証）と、検証のタイミングが上流へ動く。「手戻りは上流で防ぐほど安い」という古典的原則のAI版。
- **扱い所感**：**◎ 核（後半の背骨）**。後半の階段の設計原理そのもの。受講者には用語でなく階段の体験として渡す。

### ハルシネーション / 過信のリスク
- **概要**：AIがもっともらしい誤りを生成する現象と、それを鵜呑みにする危険。
- **扱い所感**：**◎ 核（リテラシー）**。「動くが間違っている」を見抜く回や、アペンディックスGで扱う必修リテラシー。
