# 軽量 SDD フレームワーク（sdd-mini）方針

> 講習で SDD を説明し、受講者が手を動かすための自作フレームワークの設計方針です。
> 実物は [`sdd-mini-kit/`](sdd-mini-kit/)。**特定のエージェントに依存しない**設計（「9.」）。

---

## 大原則

**主役は SDD の理解であって、フレームワークの習得ではない。**

覚えることを**6つの段だけ**に絞る。フレームワーク自体の使い方に説明が要るなら、
それは教材として失敗している。

一方で、**機能を削ったせいで基本的なことがうまく回らない、という作りにはしない。**
少ないのは段の数と仕組みであって、各段の中身ではない。

---

## なぜ既存の SDD ツールをそのまま使わないか

SDD ツール（Spec Kit など）は CLI の導入が要る。これが講習で2つの問題を起こす。

| | CLI を持つツール | sdd-mini |
|---|---|---|
| 導入 | CLI インストール（Python 環境等） | **`.claude/skills/` にフォルダを6つ置く** |
| 講義中の実習 | 環境差で詰まる → デモ主体になりがち | 全員が手を動かせる |
| **持ち帰って宿題** | **各自の環境構築が壁** | **○** |
| 講習後に実務で使う | 別途導入が要る | そのまま自分の PJ に置ける |

**3行目が効く。** 「仕様駆動で小機能を1つ作ってくる」を宿題にしたとき、
受講者が自席で CLI を入れ直すところで脱落する。宿題が回らなければ SDD は「見た」で終わる。

また、プロンプトファイル（`.prompt.md`）は「**定型プロンプトを自分で書く**」仕組みなので、
組み込みスラッシュコマンドを習った後の自然な続きになる。
**「また新しいツールが出てきた」ではなく「習った仕組みで SDD が組める」**に着地する。

> SDD は**手法であってツールではない**——これを受講者が自分の手で実証する形にしたのが sdd-mini。

### 既存ツールを否定するものではない

フェーズの語彙は一般的な SDD ツールに揃えてある（Specify → Plan → Tasks → Implement）。
講習後に本家を触っても**そのまま転移する**。「軽い方で概念を掴み、必要なら本家へ」の順にする。

## 設計判断

### 1. 段は6つ

| 段 | 何をするか | 出力 |
|---|---|---|
| `sdd-specify` | 何を作るか | `.sdd/<機能名>/spec.md` |
| `sdd-plan` | どう作るか | `.sdd/<機能名>/plan.md` |
| `sdd-tasks` | 手順に割る | `.sdd/<機能名>/tasks.md` |
| `sdd-implement` | 作る | コード |
| `sdd-verify` | 仕様どおりか | `.sdd/<機能名>/test-result.md` |
| `sdd-review` | コードは妥当か | `.sdd/<機能名>/review-result.md` |

一般的な SDD ツールの4フェーズに **`verify` と `review` を足した**。理由は次項。

### 2. 作る／確かめる／見るを分ける（最重要）

4フェーズだと、**実装した本人がその場で「できました」と宣言する形**になる。
書いた文脈がそのまま合否を出すので、確かめたことにならない。

そこで判定を実装から切り離し、`sdd-implement` には
**結果ファイルもチェックボックスも触らせない**。書くのは verify と review だけ。

**さらに verify と review も分けている。合否を決めるものが違うから。**

| | 見るもの | 合否を決めるもの | 記録 |
|---|---|---|---|
| `sdd-verify` | 仕様どおりに動くか | `spec.md` の受け入れ条件 | `test-result.md` |
| `sdd-review` | コードとして妥当か | 規約と、保守する人の目 | `review-result.md` |

混ぜると **「仕様に無いことを理由に不合格」**になり、何が基準か分からなくなる。
逆に review 側では「この仕様はおかしい」を言わせない（それは `sdd-specify` の担当）。

どちらも**根拠を要求する**のが共通の骨。verify は「実装したのだから満たしているはず」を、
review は「読みにくい」だけの指摘を、それぞれ受け付けない。

段は2つ増えるが、**これが無いと「確かめた」も「見た」も成立しない**ので入れた。
**「少なくする」は「基本が回らなくてよい」ではない。**

### 2.5 レビューは must / should / nit で出す

| 重大度 | 意味 |
|---|---|
| **must** | 直さないと着地させられない（不具合・規約違反・「やらないこと」を作っている） |
| **should** | 直すべきだが、判断次第で見送れる（重複・責務混在・命名） |
| **nit** | 好みの範囲。直さなくてよい |

**must か should が1件でもあれば差し戻し**、nit のみなら通過。
「迷ったら下げる」を明記してある——must を安売りすると、本当に止めるべき指摘が埋もれる。

**この段で初めて `instructions` が使われる。** 規約に書いたレビュー観点が、ここで指摘に変わる。
「規約をファイルに固定する」ことの報酬が実感できる唯一の場所なので、
規約を読む手順を review に必ず含めてある。

> 逆に言うと、**レビュー工程が無い状態で `instructions` に「レビュー観点」を書かせるのは嘘**だった。
> 書いても誰も読まない。この対応関係が取れて初めて、規約のファイル化に意味が出る。

### 3. テスト結果とレビュー結果は Markdown に残す（書式は差し替え可能）

`sdd-verify` は `test-result.md`、`sdd-review` は `review-result.md` を書く。書式は
**各 skill フォルダの中に外出し**してあり（`sdd-verify/test-result-template.md` /
`sdd-review/review-result-template.md`）、書き換えれば出力が変わる。

- **なぜ外出しか**：報告の形は組織ごとに違い、**プロンプトの手順とは別の速度で変わる**。
  中に埋めると、書式を直すたびに手順の記述を触ることになる。
- **なぜチェックボックスだけで済ませないか**：チェックボックスは合否しか持てない。
  **根拠**（何をどう確かめたか）と**再検証の履歴**（何が直って何が残ったか）は入らない。
  「実装したのだから満たしているはず」を排除するには、根拠を書く場所が要る。
  レビューはそもそもチェックボックスに収まらない（重大度・箇所・なぜ・提案が要る）。

> 上流3つ（spec / plan / tasks）のテンプレートはプロンプト内にインラインのままにした。
> あちらは**書きながら1度読む足場**で、こちらは**組織が形を決める報告書**。
> 寿命と持ち主が違うので置き場所も分けている。
> （揃えたければ同じ要領で外出しできる。作りは変えなくてよい。）

### 4. 状態管理を持たない — ファイルがそのまま状態

`state.yml` も進捗ファイルも CLI も持たない。

| 見るところ | 何が分かる |
|---|---|
| `.sdd/<機能名>/` にあるファイル | どの段まで進んだか |
| `tasks.md` のチェック | 実装の進み |
| `spec.md` の受け入れ条件のチェック | 最新の合否（一目で見る用） |
| `test-result.md` | 仕様どおりか。根拠と履歴 |
| `review-result.md` | コードとして妥当か。must / should / nit と履歴 |

**`spec.md` のチェックと `test-result.md` は二重管理になりうる**ので、権威を決めてある——
**`test-result.md` が正**、`spec.md` のチェックはその写し。両方を `sdd-verify` が
**同じ実行の中で一緒に更新する**ので、通常ずれない。

状態管理の仕組みを見せると、受講者の関心が「仕組みの使い方」に逸れる。
SDD の骨格は「**段が分かれ、各段の成果物が次段の入力になる**」であって状態管理ではない。

### 5. ゲートは「AI が止まる」ことで表現する

各プロンプトの末尾に「ここで止まる」節を置き、AI が次に進まずユーザーの判断を待つ。

**ゲートを機械に検査させない。** 検査させると受講者は「通った/落ちた」を見るだけになる。
自分で読んで判断する行為そのものが体験の中身なので、そこを自動化しない。

> 講習の後半の背骨が「**検証点の上流化**」（素直な指示 → plan → SDD）なら、
> sdd-mini はその終着点で、**止まる回数の多さがそのまま検証点の上流度**になる。

### 6. 前提チェックと対象選択はプロンプトの文章で行う

各コマンドは `.sdd/` を見て対象を自分で決め（フォルダが1つならそれ、複数なら
その段の入力があって出力が無いもの）、前提が無ければ止まって前の段を案内する。

CLI のガードは持たない。順序が守られる保証は無いが、**守られなかったときに何が起きるかを
体験させる**方が教材としては価値がある。

### 7. 戻る道を各段に書く

一方通行にしない。「後ろの段で前の段の誤りに気づくのは正常」を各プロンプトに明記し、
戻り先（ほとんどは `sdd-specify`）と、戻ったときに古くなるファイルの扱いを書いてある。

**SDD の値打ちの半分は「戻れること」**なので、ここは削らない。

### 8. skill として梱包する（`/コマンド` で呼べる形）

各段を `.claude/skills/<name>/SKILL.md` に置き、`/sdd-specify` のように呼べるようにする。

- **skill 名はフラット**なので、`skills/sdd/specify/` のような入れ子で名前空間は切れない。
  6つを**横並びのフォルダ**にしてある。
- 一方で **1つの skill フォルダの中には階層を作れる**。テンプレートを
  `sdd-verify/` `sdd-review/` の中に置いているのはそのためで、
  **使う skill と書式が同じ場所にある**ので、コピーすれば必ず一緒についてくる。

#### `allowed-tools` で「この段でできること」を縛る

frontmatter で各段の道具を絞ってある。**散文の宣言を機械側でも支える**。

| 段 | 縛り | 何を防ぐか |
|---|---|---|
| `sdd-specify` / `sdd-tasks` | Bash も検索も無し | **仕様や手順を書く段でコードを触りだす**のを防ぐ |
| `sdd-review` | Bash 無し | 指摘するだけの段で**実行・修正に踏み込む**のを防ぐ |

> これは「4. ゲートを機械に検査させない」と矛盾しない。
> **ゲート（進んでよいかの判断）は人間のまま**で、ここで縛っているのは
> *その段が触れる範囲*。判断を機械化しているわけではない。

ただし **`allowed-tools` は Claude Code の機能で、他のエージェントでは無視される**。
なので各 `SKILL.md` の本文にも「この段ではコードを書きません」と書いてあり、**そちらが正**。
機械側の縛りは、効く環境でだけ効く補助と位置づける。

### 9. エージェントに依存しない

**特定のエージェントの機能を使わない。** 使っているのは次の2つだけで、どちらも
どのコーディングエージェントにもある。

1. **Markdown ファイルを読む**
2. **Markdown ファイルを書く**

CLI・スクリプト・プラグイン・ツール固有 API・実行フックは一切使っていない。

#### 依存が出る箇所と、その吸収の仕方

エージェント間で違うのは**中身ではなく置き場所**なので、そこだけ導入時に吸収する。

| 違うもの | 吸収の仕方 |
|---|---|
| skill / コマンドの置き場所と拡張子 | 中身は同じで置き場所だけ違う。**登録しなくても「ファイルを指す」で動く**逃げ道を必ず残す |
| 常時効く規約のファイル名 | `AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md` の**あるものを読む**と各段に書いてある |
| frontmatter のキー | **`description` のみ**にした。無視されても本文だけで動く |

#### 「コマンド登録」を必須にしない

`/sdd-specify` のようなスラッシュコマンドは**便利だが必須ではない**。
コマンド機構はエージェントごとに規約が違い、バージョンでも変わるので、
そこに乗ると移植性がその機構の寿命に縛られる。

そこで既定の呼び出し方を**「`sdd-mini/sdd-specify.md` の手順で進めて」**にした。
これはファイルを読ませているだけなので、**どのエージェントでも確実に動く**。
コマンド登録は「毎回パスを打つのが面倒な人向けの任意の最適化」に格下げしてある。

#### テンプレートは「使う skill と同じフォルダ」に置く

`sdd-verify` / `sdd-review` がテンプレートを指す箇所は、Markdown リンクではなく
**「この SKILL.md と同じフォルダの `*-template.md`」という文章**にしてある。理由は3つ。

- **skill フォルダごとコピーすれば、書式が必ず一緒についてくる。**
  離れた場所を指すと、コピー漏れで「書式が無い」状態が起きる。
- **Markdown リンクを辿るかどうかがエージェントによって違う。**
  場所を文章として示せば、読む主体が誰でも同じ動作になる。
- 置き場所を変えても壊れない（skill ごと動くので相対関係が保たれる）。

#### 出力先も中立

成果物は `.sdd/<機能名>/` に置く。エージェント固有のディレクトリ（`.claude/` `.github/` 等）に
出力しないので、**エージェントを乗り換えても記録がそのまま残る**。

### 10. 常時効く規約を1枚添える

「**呼び出して使う手順**（各段の手順書）」と「**常に効く規約**（`AGENTS.md` 等）」の
区別が、1つの実習の中で対比できる。`sdd-plan` `sdd-implement` `sdd-review` が
これを読む作りにしてある。

**特に `sdd-review` が読むことに意味がある。** 規約に書いたレビュー観点が、
そこで実際の指摘に変わる。規約をファイルに置く見返りが目に見えるのはこの1箇所だけ。

サンプルは**空欄ではなく実際に使える内容**で書いた。空のテンプレートを渡すと
「何を書く場所か」が伝わらず、結局書かれない。

## 分量の考え方

**行数の上限は決めない。** 削るために内容を落とすと、削った先で基本が回らなくなる。

判断基準は次の2つ。

1. **その節が無くても同じ結果になるか。** なるなら削る。
2. **受講者が読まずに使えるか。** プロンプトは AI が読むもので、受講者が
   熟読する前提にはしない。読まないと使えない作りなら、それは説明が足りていない印。

段を増やしたくなったら、**まず既存のどれかに畳めないか**を先に考える。
`verify` は畳めなかった（畳むと「作った本人が合否を出す」になる）ので足した。

## 一周した先に何が起きるか（発展・中堅向け）

sdd-mini はガードと記録を持たない。**続けて回すと必ず次が起きる**ので、
最後に「これを続けるとこうなる」と道標だけ示す（実装は見せない）。

| sdd-mini に無いもの | 続けると起きること | 実務では何で塞ぐか |
|---|---|---|
| 承認の記録 | 誰がいつ何を通したか消える。手戻りが測れない | 承認をイベントとして記録する |
| 順序の強制 | spec を飛ばして implement する日が来る | 前提を機械的に検査する |
| 規約が守られたかの検証 | instructions に書いても守られない日がある | 検査を CLI/フックに降ろす |
| 複数機能の把握 | `.sdd/` が増えると今どこか分からなくなる | 横断ステータス |
| 効果の検証 | 規約を足しても、効いたか分からない | 指標を取り、前後で比べる |

> **この表が「ハーネスエンジニアリング」の入口。**
>
> 順序が大事。**先にガードを見せると、まだ経験していない痛みへの処方箋にしか見えない。**
> 一周して足りなさを感じた直後だから、必要性として理解される。

## 講習で使うときの想定

- **題材は継続プロジェクトに小機能を1つ足す**。新しい題材を作ると文脈説明に時間を取られる。
  大きさは **画面1つ・触るファイル1〜2枚**が目安。
- 完成例（`example/`）は**別題材**にしてある。実習・宿題のネタバレを避けるため。
- **講義で全段をやる枠が無いなら、`sdd-specify` の1段だけを踏ませる。**
  仕様の段階で気づく体験が SDD の全部なので、そこだけ確実に取り、残りは宿題に回す。

### 拾うべき発言

実習中に出たら**必ず全体に共有する**。SDD の値打ちがそこに出ている。

- 「受け入れ条件を書こうとしたら、決まっていないことに気づいた」← **最重要**
- 「やらないことを書いたら、話が早く終わった」
- 「plan の触るファイルが思ったより多かった」＝仕様が大きすぎたサイン
- 「実装したら仕様の方が間違っていた」＝仕様は不変の正解ではない、という学び

---

## 保守方針

- **これは 2026-08 時点のスナップショット**として扱う。SDD の考え方は変わらないので、
  最新のツール事情に追随させる必要はない。追随させ始めると教材が肥大する。
- 直すのは「**基本が回らない**」が見つかったときだけ。機能追加の要望では直さない。

## 未確認事項

- **プロンプトファイルの frontmatter キー**（`mode` / `description`、instructions の `applyTo`）は
  ツールのバージョンで変わりうる。**配布前に実機で1度確認すること。**
  frontmatter が無視されても本文だけで動くように書いてあるので、最悪でも壊れはしない。
- `/` 候補にプロンプトファイルが出るには設定の有効化が要る場合がある（受講者環境での事前確認事項）。
