# GitHub Copilot 活用講習 カリキュラム（改訂版）

## この講習の設計思想

### 対象とゴール
- **対象**：未経験〜中堅が混在。特定のプログラミングスキルを前提にしない。
- **ゴール**：**AI開発の全体像を掴む**こと。「速くコードを書けるようになる」ではなく、「Copilotで何ができ、どこに限界があり、どう付き合うか」の地図を全員が手にする。

### 貫く一つの思想
**AI支援（補完止まり）とAI丸投げ（自律実行）の両極端を避け、要所に人間の判断を置く。**
前半でAIの万能感を体験させ、後半でその綻びを見せて「だから人間の判断が要る」へ反転させる——「最初は感動、途中で不信、最後に適切な信頼」という感情の弧を設計する。

### 全体の地図（受講者に最初と最後に見せる構造）
AI開発を、積み重なる層として捉える。各回が地図のどこを照らすかを毎回示し、受講者が現在地を見失わないようにする。

```
┌─────────────────────────────────────────────┐
│  ④ 仕様を仕組みに落とす層（SDD・規約のファイル化）  │ ← 検証点：最上流
├─────────────────────────────────────────────┤
│  ③ 成果物を検証する層（動く≠正しいを見抜く）        │
├─────────────────────────────────────────────┤
│  ② 指示してコードを得る層（補完→チャット→            │
│     コマンド→エージェント：自律度が上がる）          │
├─────────────────────────────────────────────┤
│  ① 現代開発の共通基盤（Git・Markdown・VSCode・PR）  │ ← 最下層・土台
└─────────────────────────────────────────────┘
```

### 各回の型（スキル差に強い）
**デモ（講師が見せる）→ 体験（受講者が触る）→ 議論（何が起きたか・なぜかを話す）。**
議論で未経験者の素朴な疑問が中堅の理解を深める。手を動かす量が少なくても全体像は伝わる。

### 二層課題（早く終わる人と詰まる人の差を吸収）
- **コア課題**：未経験者も到達できる本質。
- **発展課題**：中堅が手を動かす上積み。Copilotが苦戦する判断・設計寄りのタスク。
両方を各回に用意し、どちらかが退屈・脱落するのを防ぐ。

### 構成と回数
全11回（土台編3＋本編8）。当初の10前後から1回増えているが、土台編を削ると未経験者が脱落するため。減らす場合の調整案は末尾に記載。

## 第一部：土台編（第1〜3回）

現代開発の共通言語を、**Copilotに聞きながら**覚える。土台習得が同時に最初のCopilot成功体験になるよう設計する。

### 第1回：VSCodeとAIに触れる
- **地図上の位置**：最下層。
- **狙い**：VSCodeの画面構成（ファイルツリー・エディタ・ターミナル・拡張）とCopilotのセットアップ。「日本語で指示すればコードが出る」という最初の成功体験。
- **デモ**：講師がVSCodeでCopilotに簡単な指示を出して動かす。
- **コア課題**：環境セットアップ、Copilotに簡単な関数を書かせる。
- **発展課題**：拡張・キーバインドの自分好みの設定。
- **議論**：「思ったより簡単／難しかったのはどこか」。
- **宿題**：自分の環境でCopilotに何か作らせてスクショ提出。
- **備考**：ライセンス手配（Freeで足りるか等）を事前に確認しておく。

### 第2回：Markdownと「AIへの伝え方」の基礎
- **地図上の位置**：最下層。
- **狙い**：Markdown記法（見出し・リスト・コードブロック）。なぜAI開発でMarkdownが共通言語なのか（指示も仕様も規約もMarkdownで書く）。
- **デモ**：Markdownで構造化した指示とそうでない指示で、Copilotの応答がどう変わるか。**mermaidは「テキストが図になる、AIに書かせられる」という顔見せのみ**（記法習得は求めない）。
- **コア課題**：簡単な手順書をMarkdownで書く。
- **発展課題**：表・mermaid記法を自分で書いてみる。
- **議論**：「構造を与えると伝わりやすいのはなぜか」。
- **宿題**：身近な作業手順をMarkdownで一本書く。

### 第3回：Gitで「記録する・戻せる」を体感する
- **地図上の位置**：最下層。
- **狙い**：VSCode内蔵のソース管理ビューで、**コミット・履歴・同期の最小セットのみ**。操作はGUIで軽く、概念（ローカルとリモート、コミットは記録）は図で別途。**ブランチ以降は扱わない**（PR運用とともに後半で導入）。
- **デモ**：変更→コミット→履歴確認→戻す、をGUIで。コミットメッセージはCopilotに生成させる。
- **コア課題**：自分の変更をコミットし、履歴を確認、一度戻す。
- **発展課題**：`gh`連携の触り（概念のみ）。
- **議論**：「なぜ記録と巻き戻しが開発を変えるのか」。
- **宿題**：第1〜2回の成果物をGit管理し、数回コミット。

## 第二部：本編前半（第4〜7回）— 人間主導の軽量な道具

AIの自律度が低い順に道具を体験。人間が主導権を握る範囲で、工程を個別に扱える段階。「軽微ならエージェント不要」という道具選択の感覚を育てる。

> **全回共通の工夫：言葉以外の指示。** 画面デザイン画像から実装／エラー画面のスクショから修正／既存コードをお手本に／期待する入出力例を提示／手書きスケッチ／図。「指示とは言葉だけでなくAIに何を見せるかの設計」という学びを各回に散らす。**画面デザインの画像実装は、使い方の幅と実習を兼ねる目玉**。

### 第4回：インライン補完 — 最も軽い相棒
- **地図上の位置**：「指示してコードを得る」層の入口。自律度が最も低く、一行ずつ目で確認できる。
- **狙い**：Tab補完、複数候補、コメント駆動。良いコメント・命名が補完精度を上げる仕組み。Next Edit Suggestions（次の一手の予測）も一コマ見せる。
- **デモ**：補完が効くケース・効かないケースの実演。
- **コア課題**：用意した小さな仕様を補完中心で実装。
- **発展課題**：コメントの書き方を変えて補完の差を比較。
- **議論**：「AIに何が見えていると補完が良くなるか」。
- **宿題**：補完だけで小さな関数群を書いてみる。
- **関連するAI特性**：トークン、コンテキスト（AIに見えている範囲）。

### 第5回：チャット — 相談する・説明させる
- **地図上の位置**：「指示してコードを得る」層＋「検証する」層の芽。
- **狙い**：Copilot Chatで質問・コード説明・エラー相談・リファクタ依頼。補完との使い分け。`#file`等のコンテキスト変数で明示的に文脈を渡す。Inline Chat（その場呼び出し）も見せる。
- **デモ**：自作コードをChatに説明させ、改善提案を受ける。
- **コア課題**：既存コードをChatで説明させ、改善を一つ適用。
- **発展課題**：`#file`等でコンテキストを明示的に渡し、応答の差を見る。
- **議論**：「読めば分かる提案と、鵜呑みにできない提案の差」。
- **宿題**：自分のコードをChatでレビューさせ、所感を添えて提出。
- **関連するAI特性**：ロール指定、Chain of Thought（段階的に考えさせる）。

### 第6回：スラッシュコマンド — 定型作業の型
- **地図上の位置**：「指示してコードを得る」層。
- **狙い**：`/tests`や`/fix`等の組み込みコマンド。コマンドは定型プロンプトのショートカットで出力が安定する一方、PJ固有の規約は知らない。自然言語との使い分け。
- **デモ**：コマンドあり／なしで同じコードのテスト生成を比較。
- **コア課題**：自分のコードに`/tests`でテスト生成。
- **発展課題**：自然言語で観点を追加し、コマンドの出力を補正。
- **議論**：「コマンドが速いとき、自然言語が要るとき」。
- **宿題**：生成されたテストの質を評価し、過不足を所感に。
- **関連するAI特性**：確率的・非決定的な出力（コマンドが安定する理由）。

### 第7回：道具の選択 — いつ重い道具を使うか
- **地図上の位置**：前半の総括。
- **狙い**：補完・チャット・コマンドを振り返り、「タスクの重さで道具を選ぶ」を明示的に教える。軽微な修正に重い道具は大げさ、という実践知。次回からのエージェントへの橋渡し。
- **デモ**：同じ目的を、軽い道具と重い道具の両方で。
- **コア課題**：いくつかのタスクを「どの道具が最適か」で仕分け。
- **発展課題**：自分の実作業を道具選択の観点で棚卸し。
- **議論**：「万能な道具はあるか」。
- **宿題**：直近の自分の作業を、どの道具で速くなるか分析。

## 第三部：本編後半（第8〜11回）— エージェントと検証の上流化

AIの自律度が上がり、工程が不可分になる段階。学び方が「工程ごと」から「視点ごと」に切り替わる。検証点が**事後→実行前→仕様段階**へと上流に動いていく流れを体験する。

> **後半の背骨：検証点の上流化。** 素直な指示（事後検証）→ planモード（実行前検証）→ SDD（仕様段階での検証）。「手戻りは上流で防ぐほど安い」のAI版。検証点が上流に行くほど、人間の仕事は「コードを見る」から「仕様を考える」へ移る。

### 第8回：エージェントに任せる — 万能感とその綻び
- **地図上の位置**：「指示してコードを得る」層の最上位（自律実行）。
- **狙い**：エージェントに素直に指示し、実装・テスト・エラー解消まで一括で起きるのを体感。まず「すごい」を体験させ、内部で何が起きているかを分解して見せる。
- **デモ**：素直な指示で小機能を一括生成。発展デモとして、サブエージェントの分業を「見せる」のもあり（operateはさせない）。
- **コア課題**：エージェントに小さなものを作らせ、結果を眺める。
- **発展課題**：大きめ・曖昧な指示で、意図とのズレを意図的に起こす。
- **議論**：「便利さの裏で、何を見落とすか」。
- **宿題**：エージェントに作らせ、できたものを自分で検証してみる。
- **関連するAI特性**：自律度と検証責任のトレードオフ。

### 第9回：成果物を疑う — 動くと正しいは違う
- **地図上の位置**：「検証する」層。
- **狙い**：第8回で作らせたものを、視点を変えて批判的に観る。動く／正しい、通るテスト／意味のあるテスト、消えたエラー／直った原因——それぞれの違い。工程ではなく「疑い方のレパートリー」を教える。
- **デモ**：一見動くが間違っているコードを一緒に見抜く。
- **コア課題**：用意したバグ入り成果物を検証し、問題を指摘。
- **発展課題**：境界条件・セキュリティ観点での検証。
- **議論**：「テストが通れば安心してよいか」。
- **宿題**：自分の生成物を観点リストで検証し、所感に。
- **関連するAI特性**：ハルシネーション、過剰追従（迎合性）、計算の苦手さ。

### 第10回：planモード — 検証を実行前に動かす
- **地図上の位置**：「検証する」層の上流化。
- **狙い**：素直な指示の「事後検証は重い」を踏まえ、計画を実行前に確認するplanモードへ。検証タイミングを事後から実行直前にずらす技術。**planから始めるのではなく、素直な指示の不便を体験した後に導入する**（不便→解決策の因果）。
- **デモ**：planモードで計画を確認してから実行。
- **コア課題**：planモードで小機能を作り、計画段階で方針を修正。
- **発展課題**：計画への介入で手戻りがどう減るか比較。
- **議論**：「事前に確認できると、何が変わるか」。
- **宿題**：同じ課題を素直な指示とplanモードで比べ、所感に。

### 第11回：SDD（Spec Kit）と全体像の総括
- **地図上の位置**：「仕様を仕組みに落とす」層＋地図全体の総括。
- **狙い**：検証点の最上流＝仕様段階へ。Spec KitのSpecify→Plan→Tasks→Implementで「仕様を先に固める」を体験。`copilot-instructions.md`/`AGENTS.md`やSpec Kitのconstitutionで「規約をファイルに固定する」を併せて見せる。**ここでブランチ＋PR運用を「AIの成果物を着地させる関所」として導入**する。最後に地図全体を振り返り、地図の外縁（コンテキスト/ハーネス/ループエンジニアリング、MCP、Agent Skills、cloud agent等）を「あなたが体験したことは業界でこう呼ばれ、今発展中だ」と一望させる。
- **デモ**：講師がSpec Kitで仕様から実装→PR着地までを通す（環境は配布済み）。MCPの実用例（チケット読取→requirement自動化／Playwright MCPでE2E）を地図の外縁の具体例として一言。
- **コア課題**：用意したSpec Kit環境で、簡単な機能を4フェーズで作る。
- **発展課題**：constitution（規約）を書いて出力を矯正する。
- **議論**：「仕様を先に書くと、AIとの付き合い方はどう変わるか」。
- **宿題（最終）**：小機能を仕様駆動で一通り作り、「AIに任せる時代に人間がやることは何か」を一段落で。
- **関連するAI特性**：検証点の上流化（後半全体の総括）。
- **PR運用の最小セット**：「作業はブランチで」「変更はPRにまとめる」「レビューを経てmainへ」「mainに直接コミットしない」。コミットメッセージ・PR本文はCopilotに生成させる。マージ戦略・ブランチ保護等は深入りしない。

## アペンディックス：AIで何ができるか（独立メニュー）

本編（Copilotで開発する）とは**切り離した、教養・視野拡大のための独立コーナー**。順不同で、興味のあるものだけつまめる。各項目は単独30分〜1時間で完結し、前後に依存しない。提供形態は自由（希望者向け単発／資料配布で自習／本編前後の任意聴講）。

- **A. AIの地形図 — 何ができて、何が苦手か**：文章・要約・翻訳・画像・音声・コード・データ分析・調査・自動化を広く一望し、対に苦手なこと（最新情報・正確な計算・事実の保証）も示す。「そもそもAIで何ができるか」への一番素直な答え。デモ中心。
- **B. 文章・資料まわりの実用**：メール下書き・議事録要約・要点抽出・企画たたき・言い換え・翻訳。各自が実務文書を持ち込んで試すと実感が濃い。
- **C. 調べる・考えるパートナーとして**：壁打ち、アイデア出し、論点整理、賛否の両論整理、学習の伴走。RAG（手元の資料に基づいて答えさせる仕組み）もここで名前が顔を出す枠。
- **D. データと向き合う**：コードを書かずに「データに質問する」。CSV/スプレッドシートの集計・可視化・傾向説明。
- **E. 画像・音声・マルチモーダル**：画像の説明・分類、図やスライドのたたき、文字起こし。「こういう世界もある」に留める。
- **F. AIエージェントと自動化**：AIが「答える」から「動く」へ広がる流れを開発の外まで。予定調整、情報収集の定期実行、複数ステップ作業の自動化。
- **G. つまずきと注意 — AIとの付き合い方**：ハルシネーション・機密情報の扱い・著作権/ライセンス・過信のリスク。全員向け必修リテラシー。

> **重みづけ**：「そもそもAIで何ができるか知りたい」に直接効くのは **A・B・C**。**G**は全員向けリテラシー。**D・E・F**は興味に応じた拡張。全部やる必要はなくメニューとして選ぶ。

## 回数を減らす場合の調整案

11回が長ければ、本質（土台編）を守りつつ本編を圧縮する。

- **9回案**：第7回（道具の選択）を第6回に統合、第10回（planモード）を第8回（エージェント）に圧縮。
- **守るべき下限**：土台編（第1〜3回）は未経験者の生命線なので削らない。後半の「素直な指示→planモード→SDD」の上流化の流れも、検証点が動く体験が核なので順序は保つ。

## 設計の要点（再掲）

| 要素 | 決定 |
|---|---|
| 対象 | 未経験〜中堅混在、特定スキル前提なし |
| ゴール | AI開発の全体像を掴む |
| 地の思想 | 両極端（補完止まり／丸投げ）を避け、要所に人間の判断 |
| 感情の弧 | 万能感 → 綻び → 適切な信頼 |
| 型 | デモ → 体験 → 議論 |
| 課題 | 二層（コア＋発展）でスキル差を吸収 |
| 土台編 | Git（コミットのみ）・Markdown（mermaidは顔見せ）・VSCode |
| 前半 | 補完→チャット→コマンド→道具選択（人間主導・工程が見える） |
| 後半 | エージェント→planモード→SDD（検証点が上流化・視点軸） |
| ブランチ/PR | 後半で「AIの成果物を着地させる関所」として導入 |
| SDD | Spec Kitまで（概念紹介。CLI障壁のため環境配布orデモ主体） |
| 地図の外縁 | ハーネス/ループ、MCP、Agent Skills、cloud agent等は名前のみ |
| アペンディックス | 独立メニュー（AIで何ができるか）。順不同・つまみ食い可 |

---

*このカリキュラムは設計案です。各回の比重・回数・扱う道具の取捨は、受講者層や講習の制約に応じて調整してください。Copilotの機能仕様は更新が速いため、実施前に最新の挙動を確認することを推奨します。*
