# GitHub Copilot 講習 設計検討ログ

> この資料は、講習カリキュラムを設計する過程での検討経緯と結論をまとめた記録です。最終的な成果物（カリキュラム本体・フィーチャー参照資料）の背後にある「なぜその判断に至ったか」を残すことを目的としています。

---

## 1. 出発点と前提の変遷

検討は「GitHub Copilotを使ったシステム開発の講習、各1時間・全12回ほど、座学＋宿題形式」から始まった。議論を通じて前提が何度も更新され、最終的に以下に収束した。

| 項目 | 最終的な前提 |
|---|---|
| 対象 | **未経験〜中堅が混在**。特定のプログラミングスキル（Java等）を前提にしない |
| ゴール | **AI開発の全体像を掴む**（「速くコードを書ける」ではない） |
| 形式 | 座学＋宿題、各回1時間、**全11回**（土台編3＋本編8） |
| 教材方針 | 教材アプリをこちらで用意し、機能改修・バグ修正をさせる方式 |

### 前提変更の重要な転機
- 当初は「Javaの土台がある」前提で組んでいたが、途中で**「Javaを知らないメンバーもいる、特定スキルを前提にしない」**と判明 → 題材を特定言語に依存させない方針へ転換。
- ゴールも当初の高地点（カスタムエージェント自作・実PJ適用）から、**「全体像を掴む」**に確定 → 「作れるようになる」より「分かる・判断できる」へ重心を移動。
- **Git・Markdown・VSCodeの土台が未整備**（「聞いたことはあるが扱ったことはない」層）と判明 → 土台編を追加。これにより回数が当初の10前後から11に。

## 2. 講習の核となる思想（議論を通じて確立）

### テーマ：「使い方」ではなく「正しく使わせる設計」と「成果物を引き受ける判断」
議論の核心的な気づきは、**「Copilotの操作を教える講習は、Copilot自身に代替される」**という点。自然言語で指示すれば動くものは作れてしまうので、操作の習得を目的にすると講習の価値が消える。

判断基準が明確になった：**Copilotで代替できる内容なら、その講習は不要**。逆に、**Copilotが自分で解決できない領域だけが講習として残る**。具体的には、
- 「正しさ」の定義（仕様の解釈、PJ規約）は人間がする
- 全体構造の一貫性は人間が保つ
- 「動くが間違っている」の検出は人間がする
- 協働を仕組みに落とす（instructions/カスタム化）のは人間がする

### 地の思想：両極端を避け、要所に人間の判断を置く
**AI支援（補完止まり）とAI丸投げ（自律実行）の両極端を避け、要所に人間の判断を置く。** これが講習全体を貫く。

### 感情の弧
**「最初は感動、途中で不信、最後に適切な信頼」。** 前半でAIの万能感を体験させ、後半でその綻びを見せて「だから人間の判断が要る」へ反転させる。

### 「早く終わる問題」への回答
「Copilotに聞けば早く終わるのでは」という懸念に対し、**ゴールを「成果物の完成」に置かず「判断」に置く**ことで解決。各回を「Copilotで素早く動かす→その出力を疑い検証しPJ規約に合わせる」の二段構成にすると、速さと学びが両立し時間も埋まる。

## 3. 構造設計の確立

### 全体の地図（4層）
受講者に最初と最後に見せる構造。各回が地図のどこを照らすか毎回示す。
1. **現代開発の共通基盤**（Git・Markdown・VSCode・PR）＝最下層
2. **指示してコードを得る層**（補完→チャット→コマンド→エージェント、自律度が上がる）
3. **成果物を検証する層**（動く≠正しいを見抜く）
4. **仕様を仕組みに落とす層**（SDD・規約のファイル化）＝検証点は最上流

### 各回の型：デモ→体験→議論
スキル差に強い。手を動かす量が少なくても全体像は伝わり、議論で未経験者の素朴な疑問が中堅の理解を深める。

### 二層課題：コア＋発展
全回で「コア課題＝未経験者も到達できる本質」「発展課題＝中堅が手を動かす上積み」を分け、早く終わる人と詰まる人の差を吸収。これがないとどちらかが退屈・脱落する。

### 前半（道具軸）→後半（視点軸）の切り替え
- **前半**：補完・チャット・スラッシュコマンドという人間主導の軽量な道具。人間が主導権を持つので工程を個別に扱える（道具軸）。
- **後半**：エージェントが実装・テスト・エラー解消を不可分に巻き取るので、工程で分けられない。代わりに「同じエージェント実行を、回ごとに違う視点で批判的に観る」視点軸へ切り替わる。
- この切り替わり自体が「AIの自律度が上がると工程で分けられなくなる」という本質を構造で体現する。

## 4. 検討した主要トピックと結論

### 4.1 フレームワーク（React/Angular）の扱い → 不採用
Web未経験者にReact/Angularは題材として重すぎる。つまずきポイントがCopilotと無関係なところ（フレームワーク知識・環境構築）に集中し、講習の主目的が埋もれる。フロントを見せるなら素のHTML+JS、あるいは画面デザイン画像からの実装に留める。

### 4.2 教材方式：改修・バグ修正 → 採用
ゼロから作らせるより、動くアプリを改修・バグ修正させる方が未経験者に向く。バグは層を分けて仕込む（構文エラー／ロジック誤り／仕様の取り違え）。特に「仕様の取り違え」はCopilotだけでは直せず人間の判断が要るため、「AIを鵜呑みにしない」学びを生む。各バグに「発見の手段」（テスト生成で気づく／スタックトレースで分かる等）を対応させ、回ごとのCopilot機能と噛み合わせる。

### 4.3 スラッシュコマンド vs 自然言語
組み込みコマンドは定型プロンプトのショートカットで、コンテキスト自動付与・出力安定・発見しやすさが利点。一方PJ固有規約は知らない。「コマンドで型を作り、自然言語で観点を追加」が実務的。**未経験者にはまずコマンドで型を覚えさせ、後に自然言語で微調整する順序が効果的**。

### 4.4 カスタム化（instructions/カスタムエージェント）の位置づけ
「成熟チームは組み込みコマンドの中身を自分たちで差し替える」という指摘は正確。ただしカスタム資産には保守コストがあり、PJの寿命・規模・規約の固さで損益分岐が変わる。**講習では「組み込みは入口、カスタムが本番」と位置づけるが、お試しPJには固有ルールがないため、カスタム化の実体験は作りにくい**（後述4.8）。

### 4.5 エージェントの導入順序
**planモードからではなく、素直に指示して作らせる段階から始める。** planモードは「素直に作らせた時の問題（意図とのズレ・事後検証の重さ）」を体験して初めて必要性が分かる。順序は「素直な指示→事後検証の大変さを体感→対処としてplanモード（事前検証）を導入」。

### 4.6 検証点の上流化（後半の背骨）
後半は検証点が一貫して上流へ動く：**素直な指示（事後検証）→ planモード（実行前検証）→ SDD（仕様段階での検証）**。「手戻りは上流で防ぐほど安い」のAI版。検証点が上流に行くほど、人間の仕事は「コードを見る」から「仕様を考える」へ移る。

### 4.7 SDD（Spec-Driven Development）の扱い → Spec Kitまで
- SDDは手法であってツールではない。**Spec Kitが最メジャー**（4フェーズ Specify→Plan→Tasks→Implement が素直で概念紹介に最適）。
- cc-sdd（gotalab版、Kiro体系）は自律実装まで含む重量級で、自作SDD基盤と同じ「実務的SDDハーネス」のカテゴリ。
- **最終的に「SDDはSpec Kitまで」と決定**。到達点デモ（cc-sdd/自作基盤）は外す。
- CLI導入が未経験者の障壁なので、環境配布かデモ主体が安全。

### 4.8 自作SDD基盤（aidev-* / Agent Skillsベース）の扱い
ユーザーが個人で作り込んだ、承認ゲート・差し戻し・metrics・任意工程（research/design/walkthrough/retro）・subtask分割まで備えた高完成度のSDDハーネス。**結論：教材としては密度・抽象度が高すぎて未経験者には重い**。SDDを「知ってもらうだけ」が目的なら、Spec Kitのような軽量版が適する。自作基盤は「実務の到達点デモ」に回す選択肢もあったが、最終的にSDDはSpec Kitまでとしたため、基盤自体は今回の講習からは外す方向。

### 4.9 範囲外と決めたもの（一貫した線引き）
**判断基準：道具の範疇に収め、基盤設計・方法論レイヤーは外縁に置く。**
- **AI-DLC**：方法論レイヤー（組織の働き方）でCopilotの道具の範疇を超える → 固有名詞としては扱わない。ただし背後の問題意識（両極端を避け人間の判断を要所に）は地の思想として残す。
- **grill.me**：plan/SDDのrequirementと「深さの違い」に過ぎない → SDDに統合し独立では扱わない。
- **各種エンジニアリング用語（プロンプト/コンテキスト/ハーネス/ループ）**：段階として組み込むのは過剰。実質は用語を出さずとも本編で体験する。最終盤に「あなたが体験したことは業界でこう呼ばれる」と地図の外縁で一度だけ示し、中堅の発展学習の道標にする。

### 4.10 Agent Skills / サブエージェント / MCP
- **AGENTS.md / instructions / ルールセット**：「規約をファイルに固定する」という形で第11回あたりで最小限体験させる（独立回は不要）。
- **Agent Skills / サブエージェント / MCP**：本筋に含めず、最終盤の地図の外縁で名前を挙げる程度。
- **MCPは「開発で使える」点が重要**：ユーザーの実例（Atlassian MCPでチケット→SDDのrequirement自動化／Playwright MCPでE2Eテスト）は外縁で名前を出すときの具体例になる。ただし使いこなしには前提が積み上がるため基盤設計レイヤー。
- **サブエージェントの分業**：operateは重いが、第8回の発展デモで「見せる」のはあり。

### 4.11 言葉以外の指示の工夫 → 採用（各回に散らす）
画面デザイン画像からの実装（幅と実習を兼ねる目玉）を軸に、エラー画面のスクショから修正／既存コードをお手本に／期待する入出力例を提示／手書きスケッチ／図（mermaid）／ドキュメント参照。共通の学びは**「指示とは言葉だけでなくAIに何を見せるかの設計」**。

### 4.12 土台編の設計
- **Git**：CLIではなく**VSCode内蔵のソース管理ビュー（GUI）**を使う。理由はツールを増やさない・Copilotと地続き・視覚的で直感的。**コミット・履歴・同期の最小セットのみ**、ブランチ以降は後回し。操作はGUIで軽く、概念は図で別途。コミットメッセージはCopilotに生成させる。
- **Markdown**：記法（見出し・リスト・コードブロック）が中心。**mermaidは「テキストが図になる、AIに書かせられる」という顔見せのみ**で、記法習得は求めない。
- **VSCode**：画面構成とCopilotセットアップ。

### 4.13 PR運用 → 採用（後半で導入）
AIとは直接関係ないが、現代開発の常識で、後半のdeliver工程（エージェント/SDDがPRで着地）の理解に必須。土台編のGit（コミットのみ）と整合させるため、**ブランチ＋PRは後半で「AIの成果物を着地させる関所」として導入**する。これによりPRが「AIの成果物を人間が検証して受け入れる関所」となり、地の思想を制度的に体現する。最小セット（ブランチで作業・PRにまとめる・レビューを経てmainへ・mainに直接コミットしない）に絞り、マージ戦略・ブランチ保護等は深入りしない。

### 4.14 AIの特性（LLMの挙動原理）→ 参照資料に追加
「なぜ指示を工夫し、なぜ出力を疑うのか」を支える土台として、トークン・コンテキストウィンドウ・Lost in the Middle・Chain of Thought・ロール指定・ハルシネーション・確率的出力・知識カットオフ・計算の苦手さ・過剰追従（迎合性）等を整理。各特性を本編の操作と対応づける（例：Lost in the Middle→重要な指示を末尾に置く）。

### 4.15 RAG / 埋め込み の仕分け
- **埋め込み（embedding model が生成する意味ベクトル）**：`@workspace`等の裏側の仕組み。ユーザーが操作する対象ではない → 深入りせず名前を出す程度。
- **RAG**：「AIで他にできること」の枠＝アペンディックス（社内文書活用などの例）。本編ではない。

### 4.16 Copilot CLI / GitHub Copilotアプリ / 並列セッション
- **Copilot CLI**：本編に組み込まない（CLI操作を避けGUIで教える方針と矛盾）。最終盤の外縁で「同じCopilotの別の入り口（ターミナル・Web・モバイル）」「ターミナル派の選択肢」として名前を挙げる程度。本質的な違いはUIではなく「別プロセスで動く独立実行環境」と「コンテキスト統合の深さ」だが、両者は接続が進み差は縮小中。最も大事なのは「同じAIの別の扉、本当のレバーはコンテキスト設計」という視点。
- **GitHub Copilotアプリ**：複数エージェントを並列指揮するデスクトップ司令塔（プレビュー・対象限定）。**触れない方針**。
- **VSCodeの並列セッション**：自律度の階段の最上段の応用で検証負荷が最も高い。本筋には組み込まず、後半のエージェントの回で「待ち時間に並行作業できる」「一人が複数AIを指揮する働き方」として一言触れる／デモで見せる程度。

## 5. アペンディックス：AIで何ができるか
本編とは独立した教養・視野拡大コーナー。順不同・つまみ食い可能。前後に依存しない読み切り。
- A. AIの地形図（何ができ何が苦手か）
- B. 文章・資料まわりの実用
- C. 調べる・考えるパートナー（RAGの名前もここ）
- D. データと向き合う
- E. 画像・音声・マルチモーダル
- F. AIエージェントと自動化
- G. つまずきと注意（リテラシー）

「そもそもAIで何ができるか知りたい」に直接効くのはA・B・C、Gは全員向け必修、D・E・Fは興味次第の拡張。

## 6. 最終カリキュラム構成（全11回）

### 第一部：土台編（第1〜3回）— Copilotに聞きながら現代開発の共通言語を覚える
- **第1回**：VSCodeとAIに触れる（最初のCopilot成功体験）
- **第2回**：Markdownと「AIへの伝え方」の基礎（mermaidは顔見せのみ）
- **第3回**：Gitで「記録する・戻せる」（VSCode内蔵GUI、コミットの最小セット）

### 第二部：本編前半（第4〜7回）— 人間主導の軽量な道具（道具軸）
- **第4回**：インライン補完（最も軽い相棒）
- **第5回**：チャット（相談する・説明させる）
- **第6回**：スラッシュコマンド（定型作業の型）
- **第7回**：道具の選択（いつ重い道具を使うか）

### 第三部：本編後半（第8〜11回）— エージェントと検証の上流化（視点軸）
- **第8回**：エージェントに任せる（万能感とその綻び。サブエージェント分業・並列セッションはデモで見せる程度）
- **第9回**：成果物を疑う（動くと正しいは違う）
- **第10回**：planモード（検証を実行前に動かす）
- **第11回**：SDD（Spec Kit）と全体像の総括（規約のファイル化＋ブランチ/PR導入＋地図の外縁を一望）

### 回数を減らす場合
9回案：第7回を第6回に統合、第10回を第8回に圧縮。**土台編（1〜3回）は未経験者の生命線なので削らない**。後半の上流化の流れも順序を保つ。

## 8. 共通の留意点
- Copilotの機能仕様は更新が速い（特にエージェント・カスタマイズ・CLI周辺）。実施前に最新の挙動を確認する。
- **ライセンス手配**：プランによる機能差があり、新規サインアップ停止等の動きもあるため、講習前に受講者のライセンス（Freeで足りるか、Business等が要るか）を確認する。
- 全体を貫く設計原理：**「Copilotで代替できる内容は講習にしない。AIが解決できない人間の判断にこそ価値を置く」**。
