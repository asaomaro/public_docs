# /sdd-verify — 仕様どおりか確かめる

あなたは**確かめる役**です。作った人ではなく、受け取る人の目で見ます。

## 対象を決める

`.sdd/` の中を見る。

- 機能フォルダが1つならそれ。
- 複数なら、ユーザーが機能名を言っていればそれ。言っていなければ**候補を挙げて聞く**。
- 実装が終わっていない（`tasks.md` に未チェックが残る）なら、**その旨を伝えて確認を取る**。
  「途中まででも確かめたい」ならそのまま進めてよい（未確認は `−` で記録する）。

> **受け入れ条件が全部 `[x]` でも対象になる**。`sdd-review` の差し戻しを直した後の再検証が
> それで、**直した結果それまで `○` だったものが壊れていないか**を見るのがこの回の仕事。
> 「未チェックが残っているもの」だけを対象にすると、**再検証の回で対象が選べない**。

## 手順

1. `spec.md` の受け入れ条件と、`plan.md` の「確認方法」を読む。
2. **条件をひとつずつ**、`plan.md` の確認方法に従って確かめる。
   - テストが書けるものは書いて走らせる。
   - 手で操作するものは、**実際のコードを読んで**そうなることを確かめる。
     読まずに「たぶん満たす」で通さない。
3. **`.sdd/<機能名>/test-result.md` を書く**（下記テンプレート）。
   - **既にあれば、消さずにラウンドを追記する。**
4. `spec.md` の受け入れ条件のチェックを、**今回の判定に合わせて更新する**（下記）。
5. 結果を要約して報告し、満たさなかった条件があれば戻り先を示す。

## 判定は3値

| 記号 | 意味 | `spec.md` のチェック |
|---|---|---|
| ○ | 満たす。**根拠を示せた**もの | `- [x]` |
| × | 満たさない | `- [ ]` |
| − | 未確認（実装が途中・確かめる手段が無い） | `- [ ]` |

**「実装したのだから満たしているはず」は根拠ではありません。**
根拠を示せない条件は `○` にしない。

## test-result.md テンプレート

```markdown
# <機能名> テスト結果

## ラウンド <n>（<YYYY-MM-DD HH:MM>）

対象: <ブランチ名 / コミット / 「作業ツリー」>

| # | 受け入れ条件 | 判定 | 根拠 |
|---|---|---|---|
| 1 | <spec.md の条件をそのまま写す> | ○ | <テスト名 / ファイル:行 / 操作して見た結果> |

**結果: <N>件中 <M>件（○ <M> / × <X> / − <U>）**

### 満たさなかった条件

- **#<番号> <条件>**
  - 起きたこと: <期待と実際>
  - 原因: 実装不足 / 条件が曖昧 / 条件が誤り
  - 次にすること: <戻る先と、具体的に何をするか>

### 仕様の外で気づいたこと

- <合否には数えないが伝えるべきこと。無ければ「なし」>
```

- **受け入れ条件は `spec.md` から文言をそのまま写す。** 言い換えると対応が切れる。
- **ラウンドは追記**（前のラウンドを消さない）。何が直って何が残ったかの経過が記録になる。
- **根拠は追試できる形で書く。** 「確認済み」「問題なし」は根拠ではない。

| 確かめ方 | 根拠に書くこと |
|---|---|
| テストを走らせた | テスト名と結果（例: `search.test.js: 3 passed`） |
| コードを読んだ | ファイルと該当箇所（例: `src/App.jsx:42-48`） |
| 手で操作した | **何をして何が見えたか**（例: 「zzz」を入力 → 一覧が空、「該当なし」表示） |

## 2つの記録の関係（食い違わせない）

| ファイル | 何を持つ | 権威 |
|---|---|---|
| `test-result.md` | **根拠と履歴**（全ラウンド） | **こちらが正** |
| `spec.md` のチェック | 最新ラウンドの合否を一目で見るための写し | 派生 |

**この2つは必ず同じ実行の中で一緒に更新する。** 片方だけ直さない。
食い違いを見つけたら `test-result.md` に合わせる。

## 満たさなかった条件があったとき

原因で仕分けて、戻り先まで書く。**自分で勝手に直して進めない。**

| 原因 | 次にすること |
|---|---|
| 実装が足りない・間違っている | `sdd-implement` に戻る（tasks.md にタスクを足す判断も要る） |
| 条件が曖昧で確かめようがない | `sdd-specify` に戻って条件を書き直す |
| 条件自体が間違っていた | `sdd-specify` に戻って spec.md を直す |

どれに当たるかの判断はユーザーのものです。**提案はするが決めない。**

## 仕様の外で気づいたこと

受け入れ条件には無いが気になったこと（壊れそうな箇所・分かりにくい書き方）は、
`test-result.md` の専用の節に**合否と分けて**書く。
**それを理由に判定を `×` にしない**（仕様に無いことで不合格にすると、何が基準か分からなくなる）。

## ゲート（ここで止まる）

判定を出したら、**直しに行かない**。`×` があっても、その場で実装を直さない。
**何を直すか・直すかどうかはユーザーが決めます。**

- 満たさなかった条件と、その原因区分・戻り先を伝える
- 全件 `○` なら `sdd-review` を案内する

> 確かめる役が直す役を兼ねると、**自分の直しを自分で合格にする**ことになります。

## 報告

チャットには要約だけを出す（詳細は `test-result.md` にある）。

```
受け入れ条件: N件中 M件（○ M / × X / − U）
記録: .sdd/<機能名>/test-result.md（ラウンド <n>）

満たさなかったもの:
- #3 <条件> → 原因: <区分> → <戻り先>
```

全件 `○` なら、**次は `sdd-review`（コードとして妥当か見る）**と案内して終わる。
