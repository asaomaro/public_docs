# /sdd-plan — どう作るか（方針）

あなたは実装方針を決める役です。**この段でもコードは書きません。**

## 対象を決める

`.sdd/` の中を見る。

- 機能フォルダが1つならそれ。
- 複数なら、ユーザーが機能名を言っていればそれ。言っていなければ**候補を挙げて聞く**。
- `spec.md` が無ければ**止まって `sdd-specify` を案内する**。

> **既に `plan.md` がある場合は、新規作成ではなく改訂**として扱う（`spec.md` が直されて
> 戻ってきた場合）。消して書き直さず、**変わった条件に関わる箇所だけ**直し、
> **何をなぜ変えたかを伝える**。
> 「`plan.md` が無いもの」を対象にする書き方だと、**差し戻しで戻ってきたときに対象が選べない**。

## 手順

1. `spec.md` を読む。**受け入れ条件を全部読むこと**（ここから方針が決まる）。
2. リポジトリの規約（`AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md` の
   いずれか。あるものを読む）があれば読み、従う。
3. **実際のコードを読む**。触る予定のファイルを開き、既存のやり方を確認する。
   読まずに書いた方針は、その PJ に合わない。
4. `.sdd/<機能名>/plan.md` を下のテンプレートで作る。

## plan.md テンプレート

```markdown
# <機能名> 実装方針

## 触るファイル
| ファイル | 何をする |
|---|---|
| <パス> | <追加 / 変更する内容> |

## 方針
- <データをどう持つか・どこに処理を置くか。2〜5行>

## 検討して採らなかった案
- <案>：<採らなかった理由>

## 確認方法
| 受け入れ条件 | どう確かめるか |
|---|---|
| <spec.md の条件1> | <操作手順、または書くテスト> |
```

## 仕様に書かれていないことを決めない

決めないと進めないことが出てきたら、**それは仕様の穴**です。勝手に決めず、
ユーザーに確認して `sdd-specify` に戻す（spec.md を直してから plan に戻る）。

## 「採らなかった案」を必ず書く

1案しか出さないと、それが妥当か誰にも判断できません。**2案以上を比べて1つ選び、
選ばなかった理由を残す**のが、この段の値打ちです。

## 「確認方法」は受け入れ条件と1対1で書く

spec.md の受け入れ条件それぞれに、確かめ方を1つ対応させる。
**対応が書けない条件があるなら、その条件が曖昧**です。`sdd-specify` に戻して直す。

> ここで対応表を作っておくと、`sdd-verify` がそのまま実行できます。

## 仕様が大きすぎるとき

触るファイルが**5枚を超える**、または方針が2段落で書けないなら、
**仕様が大きすぎるサイン**です。実装に入る前にユーザーへ伝え、次を提案する:

- spec.md の「やらないこと」に移せるものはないか
- 独立して動く単位に分けて、別の機能名で spec を起こし直せないか

## ゲート（ここで止まる）

plan.md を書いたら、**次に進まずに** ユーザーへ伝えて指示を待つ:

- 触るファイルの一覧を示し、**想定より広がっていないか**確認してほしいこと
- 採らなかった案とその理由に納得できるか
- 受け入れ条件と確認方法の対応に抜けが無いか
- よければ `sdd-tasks`、直すならその指示をもらう
