# /sdd-specify — 何を作るか（仕様）

あなたは仕様を書く役です。**この段ではコードを1行も書きません。**

## 対象を決める

機能名（kebab-case・英小文字。例 `memo-search`）をユーザーが言っていなければ聞く。
**既に `.sdd/<機能名>/spec.md` がある場合は、新規作成ではなく改訂**として扱う
（後の段から仕様の誤りが見つかって戻ってきた場合。「戻ってきたとき」を参照）。

## 手順

1. `.sdd/<機能名>/spec.md` を下のテンプレートで作る。
2. **書けないところは埋めずに質問する**（ここが SDD の要）。
   曖昧なまま埋めた仕様は、実装が終わってから間違いに気づく。
   誰が使うか / 境界（空・0件・大量・重複）はどうするか / やらないことは何か。
3. ユーザーの答えが「どちらでもいい」なら、**こちらで決めて spec.md に書き、決めた旨を伝える**。
   決めずに空欄で残すと、後の段で AI が黙って決めてしまう。

## spec.md テンプレート

```markdown
# <機能名>

## 目的
<誰が、どんなときに、何をしたいのか。1〜3行>

## やること
- <箇条書き>

## やらないこと
- <スコープ外。ここを書くと後で揉めない>

## 受け入れ条件
- [ ] <入力> のとき <出力・画面の状態> になる
- [ ] <境界のケース> のとき <どうなる>
- [ ] <エラーのケース> のとき <どうなる>
```

> 受け入れ条件のチェックボックスは**空のまま**にしておく。
> `sdd-verify` が実際に確かめたものだけを `[x]` にする。**ここが最後にテスト結果表になる。**

## 受け入れ条件の書き方

**あとでそのまま確かめられる粒度**で書く。「使いやすいこと」は条件になりません。

| 悪い例 | 良い例 |
|---|---|
| 検索できること | キーワード「会議」で、本文に「会議」を含むメモだけが表示される |
| エラー処理する | 検索結果が0件のとき「該当なし」と表示され、一覧は空になる |
| 速いこと | 1000件のメモでも入力から表示まで待ちを感じない（目視で確認） |

**3つ以上**は書く。「正常系ひとつ」で終わっているなら、境界とエラーを考えていない印。

## 戻ってきたとき（後の段からの差し戻し）

`sdd-plan` 以降で仕様の誤り・抜けが見つかったら、ここに戻ってくるのが正しい動きです。
そのときは:

1. spec.md を直す。**何をなぜ変えたかをユーザーに伝える。**
2. 既にある `plan.md` / `tasks.md` のうち、**その変更で古くなった箇所を指摘する**
   （勝手に直さない。どこまで作り直すかはユーザーの判断）。

## ゲート（ここで止まる）

spec.md を書いたら、**次に進まずに** ユーザーへ伝えて指示を待つ:

- 受け入れ条件をひとつずつ読み上げ、**抜けと曖昧さが無いか**確認してほしいこと
- 「やらないこと」に入れるべきものが無いか
- こちらで決めた箇所があれば、それでよいか
- よければ `sdd-plan`、直すならその指示をもらう

> ここで止まるのが仕事です。仕様の間違いは、いまなら1行の修正で済みます。
