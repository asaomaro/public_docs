# /sdd-implement — 作る

ここで初めてコードを書きます。

## 対象を決める

`.sdd/` の中を見る。

- 機能フォルダが1つならそれ。
- 複数なら、ユーザーが機能名を言っていればそれ。言っていなければ**候補を挙げて聞く**。
- `tasks.md` が無ければ**止まって `sdd-tasks` を案内する**。

> **`tasks.md` が全部 `- [x]` でも対象になる**。差し戻しで戻ってきた場合がそれで、
> やることは未着手タスクではなく**指摘の消し込み**（下記「差し戻しで戻ってきた場合」）。
> 「未チェックが残っているもの」だけを対象にすると、**差し戻しの回で対象が選べない**。

## 手順

1. `spec.md` / `plan.md` / `tasks.md` を読む。
2. リポジトリの規約（`AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md` の
   いずれか。あるものを読む）があれば読み、従う。
3. **未チェックのタスクを、上から順に**実装する。
   - 1つ終えるごとに `tasks.md` の該当行を `- [x]` にする。
   - **タスクごとに、何をしたかを1行で報告する。** まとめて最後に報告しない
     （途中で方向がずれていても気づけなくなる）。
4. 全タスクが終わったら、**`sdd-verify` を案内して止まる**。
   **自分で「できました」と宣言しない。**

**差し戻しで戻ってきた場合**（`test-result.md` の `×` / `review-result.md` の must・should）は、
その指摘を1件ずつ潰す。**指摘の番号と、何をしたかを対応させて報告する**
（次のラウンドで「対応」を埋められるようにするため）。直したら再び `sdd-verify` → `sdd-review`。

## ゲート（途中で止まる条件）

この段だけはゲートが末尾ではなく**途中に何度もあります**。作る役なので、
進みながら「ここから先は判断が要る」に当たったらその都度止まります。

次に当たったら、**進めずにユーザーへ報告して指示を待つ**。

| 状況 | なぜ止まるか |
|---|---|
| `plan.md` の「触るファイル」に無いファイルを触りたくなった | 方針から外れた印。広がりはここでしか止められない |
| 実装してみて **spec.md が間違っている**と分かった | 下記「仕様と食い違ったとき」 |
| タスクの前提が崩れた（先のタスクが成り立たない） | 分け方が誤っていた。tasks.md を直す判断が要る |
| 同じ箇所で2回続けて詰まった | 方針が合っていない可能性。1人で粘らない |

## 仕様と食い違ったとき

実装してみて仕様がおかしいと分かることがあります。**それは失敗ではなく発見です。**
黙って実装を変えず、どちらかを選んでユーザーに伝える:

- 仕様が正しく、実装が間違っている → 実装を直す
- 実装から見て仕様が間違っている → **`sdd-specify` に戻って spec.md を直す**（そのうえで実装する）

**コードだけ直して spec.md を古いまま残さない。** それをやると、次に読む人が嘘の仕様を読みます。

## やらないこと

- **受け入れ条件のチェックボックスを触らない。** あれは `sdd-verify` が付けるもの。
  実装した本人が付けると、確かめずに付いてしまう。
- **`test-result.md` / `review-result.md` を書かない。** それぞれ `sdd-verify` と
  `sdd-review` の持ち物。作った本人が合否を書く形にしない。
- `spec.md` の「やらないこと」に書かれたものを、ついでに作らない。

## 報告

- 終えたタスクと、それぞれ何をしたか
- 止まった場合はその理由と、判断してほしいこと
- 全部終わったら「`sdd-verify` で受け入れ条件を確かめてください」
- 差し戻し対応なら、**指摘の番号 → 何をしたか**の対応
