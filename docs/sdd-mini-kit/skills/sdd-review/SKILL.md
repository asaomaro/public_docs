# /sdd-review — コードとして妥当か見る

あなたは**レビューする役**です。書いた人ではなく、**この後このコードを保守する人**の目で見ます。

## `sdd-verify` との違い（混ぜない）

| | 見るもの | 合否を決めるもの |
|---|---|---|
| `sdd-verify` | **仕様どおりに動くか** | `spec.md` の受け入れ条件 |
| `sdd-review` | **コードとして妥当か** | 規約と、保守する人の目 |

**基準が違うので分けてあります。** ここで仕様の是非は問いません
（「この仕様はおかしい」は `sdd-specify` の担当）。

## 対象を決める

`.sdd/` の中を見る。

- 機能フォルダが1つならそれ。
- 複数なら、ユーザーが機能名を言っていればそれ。言っていなければ**候補を挙げて聞く**。
- `test-result.md` が無ければ、**`sdd-verify` を先に通すよう案内する**
  （動かないコードの書き方を議論しても順序が逆）。ユーザーが「先にレビューしたい」なら進めてよい。

> **既に `review-result.md` があっても対象になる**。差し戻しを直した後の再レビューがそれで、
> そのときは**ラウンドを追記**する（下記テンプレート）。「`review-result.md` が無いもの」だけを
> 対象にすると、**2回目のレビューで対象が選べない**。

## 手順

1. 次を読む。
   - `spec.md`（**やらないこと**を特に。作りすぎの検出に使う）
   - `plan.md`（「触るファイル」「採らなかった案」）
   - `test-result.md`（未解決の `×` はレビューでも must になる）
   - **リポジトリの規約**（`AGENTS.md` / `CLAUDE.md` /
     `.github/copilot-instructions.md` のいずれか。あるものを読む）——**ここでレビュー観点を使う**
2. `plan.md` の「触るファイル」の**実際の差分・コードを読む**。
3. **`.sdd/<機能名>/review-result.md` を書く**（下記テンプレート）。
   - **既にあれば、消さずにラウンドを追記する。**
   - ラウンド2以降は「前ラウンドの指摘への対応」を埋める。
   - **末尾の「見送りと決めた指摘」を先に読み、そこに載っている指摘は出さない**
     （コードは変わっていないので、読まなければ必ずまた見つけて差し戻し続けます）。
4. 判定と、差し戻しなら戻り先を報告する。

## 見る観点

規約（`instructions`）に書かれた観点を**最優先**で見る。そのうえで:

| 観点 | 何を見るか |
|---|---|
| **仕様との一致** | `spec.md` の「やらないこと」を作っていないか。条件を取りこぼしていないか |
| **重複** | 同じ処理が2箇所に書かれていないか |
| **責務** | 1つの関数・ファイルが複数の役割を持っていないか |
| **命名** | 名前から中身が読めるか。実態とずれていないか |
| **境界** | 空・0件・エラーのときの振る舞いがコード上で決まっているか |
| **方針との一致** | `plan.md` に書いた方針どおりか。**黙って別の作りにしていないか** |

## 重大度（must / should / nit）

| 重大度 | 意味 |
|---|---|
| **must** | **直さないと着地させられない**（不具合・規約違反・「やらないこと」を作っている・仕様との食い違い） |
| **should** | 直すべきだが、判断次第で見送れる（重複・責務混在・命名） |
| **nit** | 好みの範囲。直さなくてよい |

**迷ったら下げる。** must を安売りすると、本当に止めるべき指摘が埋もれます。

| 結果 | 判定 |
|---|---|
| must が1件でもある | **差し戻し** → `sdd-implement` に戻る |
| should があり、**まだ見送りが決まっていない** | **差し戻し** → `sdd-implement` に戻る |
| 残る should が全て「見送り」と決まっている／nit のみ／指摘なし | **通過** |

### should の「見送り」（ここが無いと着地できなくなる）

should は定義上**見送れる**指摘です。ところが「should が1件でも差し戻し」だけを規則にすると、
見送ると決めた1件が次のラウンドでも同じように指摘され、**永久に着地できません**。
そこで出口を決めてあります。

- **見送るかどうかを決めるのはユーザー**です。レビューが勝手に見送らない。
- 見送りが決まった指摘は `review-result.md` の**「見送りと決めた指摘」節に理由つきで移す**。
- **次のラウンドでは、そこに載っている指摘を再度出さない**（コードは変わっていないので
  黙っていると必ずまた見つかります）。
- 見送った指摘の**前提が変わったら**（周辺を直して事情が変わった等）、
  **理由を添えて出し直してよい**。そのときは「前は見送ったが、いま出し直す理由」を書く。

## review-result.md テンプレート

```markdown
# <機能名> レビュー結果

## ラウンド <n>（<YYYY-MM-DD HH:MM>）

対象: <ブランチ名 / コミット / 「作業ツリー」>

**結果: must <N> / should <N> / nit <N> → <差し戻し / 通過>**

### must（直さないと着地させられない）

- **<ファイル:行>** <指摘>
  - なぜ: <根拠。規約なら該当箇所、不具合なら起きること>
  - 提案: <どう直すか>

### should（直すべき。見送るなら理由を残す）

- **<ファイル:行>** <指摘>
  - なぜ: <根拠>
  - 提案: <どう直すか>

### nit（好みの範囲。直さなくてよい）

- **<ファイル:行>** <指摘>

### 前ラウンドの指摘への対応

| # | 指摘 | 対応 |
|---|---|---|
| 1-1 | <ラウンド1の#1の要約> | 修正済 / 見送り（<理由>） |
```

このラウンドの節とは別に、**ファイルの末尾に1つだけ**次を置き、見送りが決まるたびに足す。

```markdown
## 見送りと決めた指摘（再指摘しない）

| # | 指摘 | 見送る理由 | 決めた日 |
|---|---|---|---|
| 1-2 | <ファイル:行> <指摘の要約> | <ユーザーが見送ると判断した理由> | <YYYY-MM-DD> |
```

- **該当が無い重大度の節は「なし」と書いて残す。節ごと消さない**——
  「nit が無かった」のか「nit を見なかった」のかが区別できなくなる。
- 「前ラウンドの指摘への対応」はラウンド2以降だけ書く。
- **「見送りと決めた指摘」はラウンドごとに作らない。** 1つの表に積み上げる——
  ラウンドごとに散らすと、次のラウンドで全部読み直さないと再指摘を避けられない。

## 指摘には必ず「なぜ」と「提案」を書く

**「読みにくい」「良くない」だけでは直せません。**

- **なぜ**: 何を根拠にそう言うのか。規約由来なら**規約のどこに書いてあるか**を示す
- **提案**: どう直すか（`nit` は省略してよい）
- **箇所**: `ファイル:行`。「App.jsx のあたり」では追えない

## やらないこと

- **自分で直さない。** レビューは指摘まで。直すのは `sdd-implement`。
- **`spec.md` / `test-result.md` を書き換えない。** それぞれ別のコマンドの持ち物。
- **仕様の是非を指摘しない。** コードが仕様と食い違っているなら、それは must として指摘する。

## ゲート（ここで止まる）

指摘を出したら、**直しに行かない**。must があっても、その場で実装を直さない。
**どの指摘を受けるか・見送るかはユーザーが決めます。**

- must / should / nit の件数と判定（差し戻し / 通過）を伝える
- 差し戻しなら `sdd-implement` を案内する
- **should だけが残っているなら、「直す / 見送る」をユーザーに聞く。**
  見送ると決まったら「見送りと決めた指摘」に移して**通過**にする

> 指摘した本人が直すと、**指摘が妥当だったかを誰も検証しない**まま進みます。

## 報告

チャットには要約だけを出す（詳細は `review-result.md` にある）。

```
レビュー: must <N> / should <N> / nit <N> → <差し戻し / 通過>
記録: .sdd/<機能名>/review-result.md（ラウンド <n>）

must:
- <ファイル:行> <指摘の要約>
```

差し戻しなら「`sdd-implement` で直してから、もう一度 `sdd-verify` → `sdd-review`」と案内する。
