# プロジェクト規約

> **これはサンプルです。** プロジェクト直下に `AGENTS.md` としてコピーし、書き換えて使ってください。
> （Claude Code なら `CLAUDE.md`、GitHub Copilot なら `.github/copilot-instructions.md` でも同じ役割です。
> どれか1つあれば足ります。）
>
> 空のまま置いても害はありませんが、書くほど SDD の各段が安定します。

## この規約の位置づけ

- SDD の各段の手順書（`skills/sdd-*/SKILL.md`）が「**呼び出して使う手順**」なのに対し、
  こちらは「**常に効く規約**」。呼び出さなくても効きます。
- `sdd-plan` は方針を決める前に、`sdd-implement` はコードを書く前に、
  `sdd-review` は指摘を出す前に、ここを読みます。
- **AI に何度も同じ指摘をしているなら、それはここに書くべきこと**です。
  会話で毎回言い直すのをやめて、ファイルに移す——それがこの仕組みの使いどころ。

## コーディング規約（サンプル）

- 状態は `useState` のみで持つ。状態管理ライブラリは入れない。
- 新しい npm パッケージを勝手に追加しない。必要なら提案して確認を取る。
- コメントは「なぜそうしたか」を書く。「何をしているか」はコードで読めるので書かない。

## やらないこと（サンプル）

- 依頼されていないリファクタリングを同じ変更に混ぜない。
- 「ついでに」既存コードの書き方を統一しない（差分が読めなくなる）。

## レビュー観点（サンプル）

- 空・0件・エラーのときの表示が決まっているか。
- 実際に動かして確かめたのか、コードを読んで推測しただけなのか、区別して報告されているか。

---

## 書き足すときのコツ

**具体的に、確かめられる形で書く。** 抽象的な規約は守られたか判定できません。

| 効きにくい | 効きやすい |
|---|---|
| 読みやすいコードを書く | 1つの関数は画面に収まる長さにする |
| エラー処理を適切に | 失敗しうる処理は、失敗したとき画面に何が出るかまで決める |
