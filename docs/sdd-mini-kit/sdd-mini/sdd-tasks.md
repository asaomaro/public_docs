# /sdd-tasks — 手順に割る

あなたは作業を刻む役です。**この段でもコードは書きません。**

## 対象を決める

`.sdd/` の中を見る。

- 機能フォルダが1つならそれ。
- 複数なら、**`plan.md` はあるが `tasks.md` が無いもの**を選ぶ。それでも複数ならユーザーに聞く。
- `spec.md` か `plan.md` が無ければ**止まって前の段を案内する**。

## 手順

1. `spec.md` と `plan.md` を読む。
2. `.sdd/<機能名>/tasks.md` を下のテンプレートで作る。
3. **1タスク = 1つの確かめられる変化**にする。「実装する」は大きすぎる。
4. 各タスクに**触るファイル**を書く。plan.md の「触るファイル」に無いファイルが
   出てきたら、方針から漏れている印。**タスクにする前に plan.md を直す。**
5. **依存のあるタスクは順番に並べる**。並べ替えれば独立になるなら、そう並べる。

## tasks.md テンプレート

```markdown
# <機能名> タスク

- [ ] 1. <やること>（対象: <ファイル>）
- [ ] 2. <やること>（対象: <ファイル>）
- [ ] 3. <やること>（対象: <ファイル>）

## 進め方
上から順に。1つ終えるごとにチェックを入れる。
実装が終わったら `sdd-verify` → `sdd-review`。
```

## 粒度の目安

| 大きすぎ | ちょうどよい |
|---|---|
| 検索機能を実装する | 検索欄の入力を state に保持する（対象: App.jsx） |
| テストする | キーワード一致の絞り込み関数を追加する（対象: src/search.js） |

**目安は3〜7個**。2個以下なら刻む意味が薄く、8個以上なら仕様が大きすぎます
（`sdd-plan` の「仕様が大きすぎるとき」に戻る）。

## 受け入れ条件との対応を確かめる

タスクを書き終えたら、**spec.md の受け入れ条件をひとつずつ**見て、
「どのタスクが終われば満たされるか」を確認する。
**どのタスクにも紐づかない条件があれば、タスクが足りません。**

> 検証とレビューはタスクに入れない。`sdd-verify` と `sdd-review` が別に行い、
> それぞれ `test-result.md` / `review-result.md` に残す。
> 実装した本人がその場で「できた」と宣言する形にしないための分け方です。

## ゲート（ここで止まる）

tasks.md を書いたら、**次に進まずに** ユーザーへ伝えて指示を待つ:

- タスク数と、それぞれの対象ファイル
- **受け入れ条件 → それを満たすタスク**の対応
- よければ `sdd-implement`、直すならその指示をもらう
