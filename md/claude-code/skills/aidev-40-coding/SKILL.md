AI 開発ワークフローの **coding（実装）工程**を実行する。
plan / tasks に沿ってコードを書く。`tasks.md` の未チェック項目を 1 つずつ実装し、
完了したらチェックを付けて進捗を更新する。

**開始前に共通プロトコル `../aidev-00-start/protocol.md` と、PJ 固有のコーディング規約を読むこと。**

## 前提

- `plan.md` と `tasks.md` が存在すること。無ければ実行を中止し、plan 工程を促す。

## 入力

- 対象フォルダの `tasks.md` / `plan.md` / `spec.md`。
- あれば `research.md`（「実装アンカー」「実装時の注意」）と `design.md`（構造設計）。
  探索の起点として使う（`research` 工程の出力は spec 向けだけでなく coding 向けでもある）。
- 既存コードと PJ 固有のコーディング規約（AGENTS.md 等。存在すれば優先して従う）。

## 出力

- 実装コード（リポジトリ本体への変更）。
- 進捗を反映した `tasks.md`（完了タスクにチェック）。
- 設計から外れた判断をした場合は `decisions.md` に記録。
- タスク点検（手順5）を行った場合は `review.md` の「タスク点検ログ」節。

## 手順

1. protocol.md「1. 対象作業の特定」に従い対象フォルダを確定。`aidev guard coding` で前提を検査する
   （exit≠0＝未充足。目視確認で代替しない——guard は三層モデルの第二層＝ハードなので、
   呼ぶ行が手順に無いと第一層＝散文だけで運用することになる。protocol.md「2.10」）。
   `research.md` / `design.md` があれば、先に「実装アンカー」「実装時の注意」に目を通す。
   - **対象が subtask（state.yml に `parent` あり）か親かを見分ける**（`protocol-subtask.md` を読む）。
     subtask の coding は**その slice 単独**の実装で、`plan.md` / `tasks.md` は子のものを使う
     （親のものは継承しない）。review からの差し戻しで戻ってくる先がここになる。
2. `tasks.md` の未チェック項目のうち、**`依存:` が全て済んでいるものの集合＝現在のウェーブ**を求め、
   そこから着手するタスクを選ぶ（ウェーブは `依存:` から導出する。ラベルは書かれていない。`aidev-30-plan`）。
   - **既定は直列**（ウェーブから1つ選んで消化し、次を求め直す）。
   - **並行してよいのは、次を全て満たすときだけ**（満たさなければ直列に戻す）:
     同一ウェーブである／**`対象` のファイルが重ならない**／両方とも `対象` が特定済み
     （`対象: 未特定` は触る範囲が読めないので**必ず直列**）。
   - 並行させる場合は protocol.md「2.6」に従って委譲する。**`tasks.md` のチェック・承認・state 記録は
     主エージェント**が行う（委譲の不変条件）。
   - 実装中に**ウェーブ外のファイルへ触ることになったら並行をやめて直列に戻す**（`対象` が外れた合図。
     手順3の `unplanned_lookups` と同じ事象で、`profile: light` なら昇格トリガでもある）。
   - `依存:` が存在しないタスク ID を指している / 循環している（A→B→A）ときは、**plan の誤り**として
     差し戻す（推測で順序を決めない）。
3. タスクの `対象` アンカー（無ければ `research.md` の「実装アンカー」）から実装箇所を開く。
   `対象: 未特定` のタスクは、この工程で探索する。
   - アンカーは**探索（どこを見るか）の省略**であって、**読解（何が書いてあるか）の省略ではない**。
     編集する対象コードは必ず実物を読んでから変更する。
   - **アンカー付きのタスクで探索が必要になったら数える**（アンカーが外れていた / 記述が足りなかった場合）。
     その回数を工程終了時に `unplanned_lookups` として記録する。`対象: 未特定` のタスクでの探索は
     想定内なので数えない。
4. PJ のコーディング規約に従って実装する。周辺コードのスタイルに合わせる。
5. **タスク単位の独立点検**（protocol.md「3.3」(b)・条件付き）。次のいずれかに当たるタスクは、
   実装した**そのタスクの差分だけ**を別コンテキストに点検させてから次へ進む。
   - `mode: autonomous`（人間の目が入らないので**全タスク**）／ `対象: 未特定` だったタスク／
     アンカーが外れて探索し直したタスク（手順3で数えたもの）／共有モジュール・公開 API に触れたタスク
     （`.aidev/config.yml` の `sharedFiles` があればそれを使う）。
   - **観点は正確性・規約適合の2つだけ**。要件適合・価値適合は work 全体の文脈が要るので review 工程に残す
     （前倒しすると観点が落ちる）。**根拠（`file:line`）の無い指摘は採らない**。
   - 指摘はその場で直す。同一タスクの「点検 → 修正」は `.aidev/config.yml` の `maxTaskCheckRounds`
     （既定 2）まで。超えたら深追いせず `decisions.md` に経緯を残して次のタスクへ進む（判断は review 工程に委ねる）。
   - 直した指摘の**内容**は `review.md` の「タスク点検ログ」節に1件1行で追記する
     （書式は protocol.md「8.」。無ければ生成する）。**点検した数と直した数を工程終了時まで数えておく**。
   - `profile: light` では行わない。委譲機構が無ければ同一セッションで観点を切り替えて読み直す。
6. タスク完了ごとに `tasks.md` の該当項目にチェックを付ける（**点検を委譲しても、チェックを書くのは主エージェント**）。
7. 仕様から逸脱する判断をした場合は `decisions.md` に理由を残す（後続工程・レビューのため）。
8. 区切り（全タスク完了、または一区切り）で、protocol.md「3. 工程終了プロトコル」に従って終了する（次工程: `test`）。
   承認は `aidev approve coding tasks_done=<チェック済みタスク数> unplanned_lookups=<手順3で数えた回数>
   task_checks=<手順5で点検したタスク数> task_check_findings=<点検で直した指摘の件数>`
   （protocol.md「3.」「8.」）。探索し直しが 0 なら `unplanned_lookups=0`、点検を1件も行わなかったなら
   `task_checks=0` を明示的に記録する（省略すると「測っていない」と区別できない）。

## 留意点

- 1 度に多くのタスクをまとめて進めず、検証可能な単位で刻む。**並行実行は「速く終わらせる」ためであって、
  刻みを粗くしてよい理由ではない**（1 タスク = 1 つの検証可能な変更は変わらない）。迷ったら直列にする。
- **タスク点検（手順5）は review 工程を置き換えない**。点検が見るのは正確性・規約適合までで、
  差分全体の整合・要件適合・価値適合は review 工程が見る。点検したから review を軽くしてよい、ではない。
- 全タスクが終わっていなくても、区切りで中断してよい（`tasks.md` のチェック状態がレジューム点になる）。
- review / test からの差し戻しでこの工程に戻ることがある。その場合は指摘に対応するタスクを処理する。
- **文書に書かれていない ＝ 存在しない、ではない**。`research.md` は調査時点で「関係する」と判断された範囲の抜粋であり、
  漏れは coding 側からは見えない。アンカーが外れている・記述が実物と食い違うときは、**コードを正**として扱い、
  自分で調べ直す（文書の記述を優先して実装しない）。
- `research.md` は**変更前のスナップショット**。差し戻し・再開でこの工程に戻った場合、
  既に自分が変更した箇所については記述が古い。
- 上記により文書と実物のズレを見つけたら、`decisions.md` に残す（review / retro が拾える形にする）。
- **`profile: light` の昇格トリガ**（protocol.md「11.」）: 想定外のファイルに触った / 影響が広がった /
  共有モジュールに手を入れることになった、のいずれかに至ったら **`aidev escalate` で full に昇格**する。
  昇格は片方向で、省略していた節を各文書に足すだけでよい（書き換えは不要）。
  昇格したら `decisions.md` に経緯を残し、この工程の承認に `escalated_from_light=1` を付ける。
  **light のまま押し切らない**——昇格漏れは後から気付けず、insights の「light の手戻り率」が
  実態より良く見えてしまう。

## decisions.md テンプレート

設計から逸脱した判断や、後続工程・レビューに影響する決定を**追記式**で残す。
1 決定 = 1 エントリ。ID は `D1`, `D2`… と連番。既存エントリは編集せず、新しい決定を追記する。

```markdown
# 決定記録

## D<連番>: <決定の要約（一文）>

- 背景: <なぜこの判断が必要になったか>
- 決定: <何を決めたか>
- 理由 / 代替案: <採用理由。退けた代替案があれば添える>
- 影響: <spec/plan など他成果物への影響。差し戻し起点なら経緯も>
```

## 完了の目安

- `tasks.md` の対象タスクが全てチェック済み。
- spec の受け入れ基準を満たすコードが書けている（検証は test 工程）。
