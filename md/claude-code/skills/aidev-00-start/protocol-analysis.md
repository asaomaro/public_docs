# 導出できる指標と解釈（`protocol.md`「8」の詳細）

> **読む条件**: retro / insights で定量分析するとき。工程の実行中は読まなくてよい。
> 核となる規約と要約は `protocol.md`「8」。ここはその詳細を切り出したもの
> （工程ごとの読み込み量を抑えるため。`protocol.md`「0.」の付録一覧を参照）。


- **各工程の経過時間**：その工程の**全ラウンドの合計**（各 start から approved / sent_back まで）。
  `aidev metrics --phases` は `start`＝初回・`approved`＝最後・`elapsed_sec`＝合計・`rounds`＝start の回数を出す。
  **`rounds` が 2 以上の工程は差し戻しがあった工程**で、そこが重いのが普通。
- **手戻り回数（reworks）**：`start` の**回数の合計から工程数を引いた値**（`Σ max(0, start回数−1)`）。
  「差し戻し回数」ではない——1 回の review→coding 差し戻しで coding/test/review が再開すれば **3** になる。
  規模あたりの手戻りの分子はこの値なので、`sent_backs` と混同しないこと。
  ※差し戻しで coding を再開する際に `aidev event coding start` を記録しないと、この指標は手戻りを取りこぼす（「3.」差し戻し分岐）。
- **差し戻し回数**：sent_back の件数（工程別）。**`aidev unapprove` も `sent_back` を刻む**ので、
  1 回の差し戻しで「差し戻した工程」と「承認を取り消した後工程」の両方が数に入る。
  「何回やり直したか」を見たいときは `reworks`、「どこで止まったか」を見たいときは工程別の内訳を使う。
- **リードタイム**：最初の start 〜 deliver の approved。
- **任意工程の使用**：research / design の start 有無。
- **アンカー的中率**：`1 − unplanned_lookups / tasks_anchored`（research/plan の位置特定がどれだけ当たったか）。
  低ければ research の問いが的外れ、常に 100% なら research が過剰——**任意工程の発火条件を調整する材料**になる。
- **規模あたりの手戻り**：手戻り回数 ÷（`insertions` + `deletions`）。tasks 数は粒度の癖でぶれるため、
  work 間を比較するときはこちらで正規化する。
- **タスク点検の検出率**：`task_check_findings / task_checks`（「3.3」(b) の独立点検が1タスクあたり何件拾ったか）。
  **分母は `tasks_done` ではない**——点検しなかったタスクを分母に入れると、発火条件の良し悪しが消える。
  読み方は2軸で、片方だけでは判断できない。
  - `task_checks / tasks_done` が高いのに検出率が低い → **発火条件が広すぎる**（点検のコストが空振りしている）。
  - 検出率が高いまま review の `must` も減らない → **点検の観点がずれている**（正確性・規約適合の外を見ている、
    または根拠なき指摘を採っている）。両方が減って初めて効いている。
  - 点検で潰れた欠陥は `review.md` のラウンド指摘に現れない。**`must` の推移を条項の効果として読むときは、
    `task_check_findings` を併せて見る**（「12.」の判定バイアス）。
  - **ラウンドの `must` は点検の有効性の指標にならない**。点検は「工程に到達する前に潰す」ものなので、
    点検が効いているほどラウンドの `must` は 0 に張り付く（実測で 6 work すべて 0、点検ログ側には must 相当が 4 件）。
    見るのは `task_check_findings` と、その内訳（点検ログ節の severity）。
- **壁時計値の限界（autonomous でも）**：`elapsed_sec` は工程の重さではなく**ツール呼び出しの間隔**を測る。
  同一コマンド列で `event start` と `approve` を続けて打つと、成果物を書いた時間は区間の外に落ちて 0 になる
  （実測で 129 行の design.md を伴う design 工程が 0 秒だった）。autonomous 同士でも、
  比較に使う前に `rounds` と成果物の実在を見ること。

> 注意: 経過時間は承認待ち・セッション中断を含む壁時計値であり、純粋な作業時間ではない。
> 品質傾向としては**手戻り回数**の方が示唆に富む（上流工程の弱さを示すため）。
> 経過時間を比較するときは `state.yml` の `mode` で**層別する**（interactive は人間の承認待ちが支配的で、
> 工程の重さをほとんど反映しない。比較が成立するのは autonomous 同士）。

## 受け入れ基準の被覆（`ac` / `ac_drift`）

`aidev metrics` の per-work 表に出る 2 列。出所は `approve` が自動で刻む被覆メトリクス（`protocol.md`「8.」）。

- **`ac`** = 最後に刻まれた `ac_total`（受け入れ基準の総数）。**要求側の規模の分母**として使う。
  これまで分母は実装側（`files_changed`）と分解側（`tasks_planned`）しか無く、
  「`AC` 1件あたりの手戻り・リードタイム」が出せなかった。
  ただし `AC` の粒度は書き手の癖に依存するので、**work 間の比較は同じ書き手・同じ PJ の中で**行う。
- **被覆率そのものを目標値（KPI）にしない**。plan の承認前ゲート（`aidev coverage --strict`）で
  100% が強制されるので値は常に張り付き、**動くのはゲートを迂回したときだけ**。
  率を目標にすると「率を守るために `AC` を書かない」＝**分母を減らす**方向に力がかかる
  （条項の効果測定で踏んだ「検出器と発生率を分離する」と同じ罠。`protocol.md`「12.」）。
  読むのは率ではなく**差分**（`ac_drift`）の方。
- **`ac_drift`** = 「**plan 以降に増えた gap の数**」。
  最後の刻印の `(ac_total - ac_covered) + tasks_no_ac` から、最初の刻印の同じ値を引いたもの。
  - `0` = plan で決めた被覆のまま着地した。
  - 正の値 = **spec と実装が乖離した**。典型は coding 中に足したタスクが `AC:` を持たない
    （`tasks_no_ac` が増える）、または `AC` に対応するタスクが消えた（`ac_covered` が減る）。
    どこで乖離したかは `aidev coverage <slug>` と `git log -p -- tasks.md` で特定する。
  - 負の値 = plan 時に残っていた穴が後から埋まった（ゲートを迂回して plan を承認した場合に起きる）。
  - **`-`** = 刻印が1点しか無く**測れない**（`0` と書かない——測れないことと乖離が無いことは違う）。

**`tasks_ac_none`（`AC: なし` の割合）の読み方**: 受け入れ基準に紐づかない作業の比率。
高いなら (a) 要件に書かれていない作業をしている（スコープクリープ）か、(b) 要件の書き漏れ。
どちらかは `tasks.md` の当該タスクを読めば分かる。**低いことが良いとは限らない**——
下準備・リファクタは正当に `AC: なし` になる。**work をまたいで同じ性質の作業が毎回はみ出しているなら、
それは条項（`protocol.md`「12.」）の材料**。
