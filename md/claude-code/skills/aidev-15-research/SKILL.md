AI 開発ワークフローの **research（事前調査）工程**（任意）。
spec を書く前に、既存コード・外部情報・実現性を調査し、不確実性を事実で解消する。
手戻り（誤った spec → 差し戻し）の予防が目的。

**開始前に共通プロトコル `../aidev-00-start/protocol.md` を読み、その規約に従うこと。**

## 位置づけ

- 任意工程（番号末尾5、requirement と spec の間に差し込む）。毎回は不要。
- 起動経路は2つ（protocol.md「4.5」）: ユーザー指定、または requirement 終了時の AI検知＋推奨。
- 重く対話の少ない調査が多いため、サブエージェントへの委譲（protocol.md「2.6」）と好相性。

## 起動判定（検知ロジック）

requirement 終了時（requirement 工程の終了ゲート）に、以下の**いずれか1つ以上**に該当したら research を発火対象とする。

- requirement の「未確定事項」に、**調査で解消すべき**項目（仕様・既存挙動・実現性に関するもの）が1つ以上残っている。
- 変更が**未検証の既存挙動**（既存コードの現在の振る舞い・暗黙の前提）に依存する。
- 技術的**実現性が未確認**（使える API/ライブラリ・制約が不明）。
- **影響が横断的**（複数モジュール／言語同居の副作用など、範囲が requirement だけでは読めない）。
- **利用者が操作する部品を作る**（ポップオーバー・ピッカー・一覧・ダイアログ等）。
  この場合は**確立したパターンの調査が必須**——下記「UI の規範」。

- **interactive**: 上記検知時、遷移ゲートに `承認して research(任意) を挟む`（推奨）を理由付きで加える。却下されれば spec へ直行。
- **autonomous**: 上記検知時、**推奨ではなく自動で実施**する（protocol.md「10.」）。いずれにも該当しなければスキップして spec へ進む。

## 前提

- `requirement.md` が存在すること。

## 入力

- 対象フォルダの `requirement.md`（特に「未確定事項」）。
- 既存コード、外部ドキュメント、PJ ルール。

## 出力

対象フォルダに `research.md` を生成する（**spec と coding の両方の入力になる**）。

- **spec 向け**: 設計判断（how）の材料となる事実。
- **coding 向け**: 実装の起点となる**実装アンカー**（`file:line` / シンボル名）と、コードに書かれていない注意点。
  実装工程が同じ探索をやり直さずに済むことが、この工程の回収ポイントの1つ
  （中断からの再開・test/review からの差し戻しで特に効く）。

## 手順

1. protocol.md「1. 対象作業の特定」に従い対象フォルダを確定。「2. 前提チェック」で `requirement.md` を確認。
2. 調査すべき問い（unknowns）を列挙する。典型例:
   - 既存コードの実装把握 / 影響範囲（どのコードが対象挙動を担うか、変更が波及する箇所）
   - **出力先の仕様（生成・変更する対象のスキーマ・型・フォーマット・既存実装）**。
     成果物が既存の型/スキーマに準拠する必要がある場合、その定義を必ず読む
     （外部情報源だけでなく、PJ 内の出力先仕様を確認しないと後段で手戻りになりやすい）。
   - 技術的実現性（API・ライブラリで実現可能か）
   - **UI の規範**（利用者が操作する部品を作るとき。**プロトコルや既存コードと同じ重みで調べる**）:
     - **確立したパターンは何か**（WAI-ARIA APG の該当パターン・OS のネイティブ部品・
       広く使われている実装が 2〜3 個）。**開く / 確定 / 取り消し / キーボード / フォーカスの行き先**を、
       それぞれがどう決めているかを並べる。
     - **食い違うなら、どちらを採るか理由を書く**（この画面に固有の事情があるなら明記する）。
     - **調べずに作ると、後から作り直しになる。** 実装は動いてしまうので test も review も通り、
       **利用者が実物に触った時点で初めて分かる**——そのときには deliver 済みで、
       指摘のたびに 1 往復ずつ増える。
       実例（`20260826-datetime-picker`）: 規範を調べたのは利用者に「一般的ですか？」と
       聞かれてからで、調べたら**当時の作りはどの流儀にも当てはまらなかった**。
       追補は経過時間の 76%・コミット 8 本。**spec の前に 10 分読めば済んでいた。**
   - requirement の未確定事項のうち、調査で解消すべきもの
   - **実装の起点はどこか**（変更・参照することになる具体的なファイル / シンボル）。
     位置が特定できたものは「実装アンカー」として残し、coding が同じ探索をやり直さずに済むようにする。
3. 各問いを調査し、**事実**で答える（推測と区別する）。重い調査はサブエージェントに委譲してよい。
   - 委譲する場合、**探索の過程（空振りの検索結果・無関係なファイルの中身）は持ち帰らず、
     根拠付きの結論だけを `research.md` に残す**。後続工程のコンテキストを汚さないことがこの委譲の主目的。
4. 下記テンプレートに沿って `research.md` を記述する。設計判断（how）は spec に回す。
   既存構造・呼び出し関係・影響範囲は、明確になるなら mermaid で図示する（protocol.md「9.」）。
   - **全ての事実に根拠（`file:line` / シンボル名 / 出典）を添える**。この文書は下流（spec → plan → tasks → coding）で
     要約を重ねられるため、後続工程が記述を疑ったときに**一次資料へ戻れること**が唯一の保険になる。
     「要約」ではなく「**索引付き要約**」にする。
   - 記述は**変更前のスナップショット**である。「判明した事実 / 実装アンカー」（現状）と
     「spec への申し送り」（変更後の想定）を混ぜない。
5. protocol.md「3. 工程終了プロトコル」に従って終了する（次工程: `spec`）。

## research.md テンプレート

```markdown
# 調査: <タイトル>

## 調査の問い
- Q1: <明らかにしたいこと>

## 判明した事実
- F1: <Q1 に対する事実。根拠（ファイル/行・出典）を添える>

## 影響範囲
- <変更が波及する箇所・関連コンポーネント>

## 実現性 / リスク
- <技術的に可能か。制約・懸念>

## 実装アンカー
<coding の起点。位置が特定できたものだけを書き、特定できなかったものは「未特定」と明記する>
- A1: <何をする箇所か>（`path/to/file.ts:120` `symbolName`）— <そこに何があるか>
- A2: <何をする箇所か>（未特定 — coding 側で探索が必要）

## 実装時の注意
<コードを読んでも分からない / 読み落としやすいこと。spec には載らないが実装者が知りたいこと>
- <触ってはいけない箇所とその理由 / 暗黙の前提 / 周辺の慣習 / 踏みやすい罠>

## spec への申し送り
- <設計時に踏まえるべき点。残った未確定事項>
```

## 完了の目安

- requirement の「調査で解消すべき未確定事項」が事実で埋まっている。
- **UI を作る work では、確立したパターンとの突き合わせが済んでいる**
  （requirement の「相互作用の受け入れ基準」に答えが出せる状態になっている）。
- spec が誤った前提で書かれるリスクが下がっている。
- 実装の起点が「実装アンカー」として特定できている（**特定できなかったものは「未特定」と明示**されている。
  空欄にすると coding 側が「調査済みで対象なし」と誤読する）。
